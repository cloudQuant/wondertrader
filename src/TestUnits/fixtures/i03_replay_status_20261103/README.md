# Replay status V1

The fixed-width C-compatible snapshot declares idle, preparing, prepared, running and terminal states. `generation` advances on an accepted prepare. A terminal state is visible inside `handle_replay_done` and terminal notification callbacks, while `WT_REPLAY_STATUS_FINAL` remains clear until the hook and notifier have returned and running admission reopens. Completion and notification exceptions change the terminal state to failed; a terminal state without FINAL may therefore change. The callback is called at most once per generation. Active error reports preserve the first error; finalizing reports are ignored. Reports made outside an active run retain the old internal abort flag without rewriting a completed snapshot. `prepare` validates its initial date using checked mapping, which requires the relevant session/calendar data.

An in-range bar or actually dispatched HFT event is required for bar/tick replay; a loaded bar outside the interval and an HFT bucket with only filtered events return `FAILED/NO_SOURCE` instead of success. A valid task schedule may succeed without market-data events. If a notifier throws while attempting a terminal event, the code cannot tell whether delivery happened: it marks the snapshot failed and rethrows without retrying a potentially duplicate or contradictory notification.
