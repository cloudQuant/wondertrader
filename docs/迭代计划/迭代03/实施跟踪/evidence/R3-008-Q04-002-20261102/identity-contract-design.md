2026-11-02。此文不表示设计已实现，不证明 SDK 行为，也不改变既有风险或授权；动态测试范围见同目录 README。该工作需与 `../../NEW008-N05订单身份链审计.md`、L01-014 的身份与账户准入方案共同实现，不能新造彼此冲突的并行账本。

## 仓内可证实的数据链

- `src/WtCore/TraderAdapter.cpp:94`、`src/WtUftCore/TraderAdapter.cpp:187` 的 localid 以当前时间估算值初始化的进程静态 `uint32_t` 原子递增，分别在 `:1221`、`:1172` 拼入 `otp.<adapter>.<id>` / `wtp.<adapter>.<id>`。同进程首次种子为零时调为 1，但随后的 `fetch_add` 无跨重启持久性或绕回保护；在同秒或跨进程重复不能仅靠目前 token 排除。仅把进程内 localid 当永久键无法证明安全。
- `src/Includes/ITraderApi.h:140-175` 给 entrust/order/trade 回调传对象，order 查询仅数组，既无回报序号/快照 cutoff，也无查询完成错误状态或请求代次。`WTSTradeInfo` 有 `tradeID`、`refOrder`、`userTag`、`tradeDate` 字段（`src/Includes/WTSTradeDef.hpp:486-488,536-537`），但此通用接口不承诺这些字段非空、全局唯一、稳定或以何范围唯一。不能默认一个 tradeID 就跨账户/交易所/交易日唯一，也不能按日期清理去重记录而无 provider 迟到边界。
- CTP 下单先把 entrustID → usertag 放入持久缓存（`src/TraderCTP/TraderCTP.cpp:548-587`），订单转换用该缓存找 tag，再以 orderID 填 oid → tag（`:1334-1352`）；成交转换只用 oid 缓存找 tag（`:1415-1464`）。成交先于对应订单建立映射、缓存不可用、查不到合约，均可能出现空 tag 或不产生 WTS 对象。当前 Adapter 无法凭空恢复未知关联；必须由 provider/宿主在丢弃前捕获并隔离原始事件。CTP 负返回反映 `ReqOrderInsert` 同步非零（`:629-637`），仍不推出其他 provider 的语义。
- Femas 直接把可容纳 tag 写入 `UserOrderLocalID`（`src/TraderFemas/TraderFemas.cpp:426-458`），订单/委托转换有字段取回（`:1150-1220`）；但成交转换在 `:1280` 仅查询 `m_mapOrderTag`，全仓仅声明及此处读取，没有写入，因此源码层面当前无法通过该 map 恢复成交 tag。`ReqOrderInsert` 非零时只记日志、无论结果返回 0（`:496-502`）；`OnErrRtnOrderInsert` 是空实现（`:1297`）。这些是静态代码观察，未以真实 SDK 试验，也不证明对所有拒单/成交情况都有同样时序。
- CTP `OnRspQryOrder`（`:1218-1247`）和 Femas（`:921-949`）在最后一帧将数组交给 `onRspOrders`；两者都使用 `!IsErrorRspInfo` 过滤当前行但调用 SPI 时未传错误或快照切点。订单转换查不到基础合约会返回空并跳过该行；因此现行 SPI 的空/部分数组不能证明查询完整。两 Adapter 的 `onRspOrders` 分别在 `src/WtCore/TraderAdapter.cpp:2370-2490`、`src/WtUftCore/TraderAdapter.cpp:2233-2366` 清空聚合量并从数组重建，随后推进查成交/查资金并进入 READY；仅加锁不使快照与实时事件建立因果顺序。
- Adapter 的撤单和成交目前直接按 tag 前缀更新合约总量（WtCore `:2856-2871,3080-3086`；UFT `:2551-2564,2752-2763`），拒单只按聚合值是否非零判断（WtCore `:2235-2245`；UFT `:2118-2151`）。`_orderids` 只用于其他统计/冻结逻辑，不是这些账本更新的逐事件幂等锁。WtCore 合约量有符号表示买卖净额，UFT 四个提交入口均增加绝对量；两个原接口含义不同，不能直接替换成同一个数值合同。

## 候选实现顺序及拒绝条件

1. 增加可协商的 provider 能力（独立版本化接口、保留旧 ABI）：返回值区分“确定未发出”“已提交待确认”和“结果不明”；回报能携带账户命名空间、可持久恢复的订单身份；成交身份及其唯一范围明确；明确订单查询成功/空/部分/失败、快照切点和回调排空/序列化合同。不支持这些能力的旧 provider 不得自动进入声称完整账本一致性的模式，按已确认的账户准入规则隔离与对账。现有 `int` 及无序查询回调不足以推导这些承诺。
2. 出口处逐拆单在调用外部 API 前生成并持久登记不可重用 intent / owner / 账户绑定、合约、方向与量，分配额度并线性化状态更新后释放账本锁再调用外部 API。同步 callback 可以先到；返回和回调都针对同一 intent 进行条件状态转换。确定未发出可取消该 intent 的未完成贡献，矛盾或未知结果进入人工对账，不可简单减整个合约，也不可把同步负返回与重入拒单各扣一次。
3. 订单以不可变映射关联 intent 和 provider 订单标识；订单状态与累计成交量先验证，允许重复和可证明的乱序，非法倒退/冲突或未知身份先保留原始事件并停账户。对成交按已确认作用域的唯一键幂等入账，与订单累计成交建立统一规则，避免“部分成交事件”和“订单终态中的累计成交”重复扣减。账户持仓/风险与 owner 级订单量分开；账本状态变更和去重记录需同一事务或可证明的恢复协议。
4. 快照仅在 provider 给出可证明完整性和事件水位/原子屏障时接入：先暂存校验整份结果，随后按水位合并同一账户实时事件并一次发布；无法证明切点时不得从观测顺序猜测，应保留待对账和限制交易。历史无主单、部分查询、空查询、恢复失败不得当作已确认空集。幂等记录只可在明确的 provider 迟到边界、已确认终态、重启恢复和 durable checkpoint 均满足后回收；达到资源上限但不能安全回收时受控停账户，而不是无界增长或丢旧键。
5. 先用针对上述协议的独立假 provider 覆盖同步重入/负返回、乱序重复和两笔同标的、部分成交与终态、快照切点前后/部分失败、重启和持久失败；在供应商版本材料与实际环境允许时，再分别验证真实 SDK，不用 fake 证明 SDK 保证。已有 `events-run*` 反例需转绿，但不能单凭这些用例关闭原项。

结论：目前没有足够的跨 provider 事件身份、快照与回收合同支持安全全链修复。本次未对产品实施按合约回滚或假定 tag 唯一的局部补丁；待上述准入及 provider 合同闭合后再实施。
