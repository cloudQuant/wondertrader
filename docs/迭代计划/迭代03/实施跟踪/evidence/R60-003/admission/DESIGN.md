# R60-003: full lifecycle design for review

This is a proposed design, not implemented or accepted. It preserves the existing `ITraderApi` vtable and explicitly distinguishes a stop request from completed teardown.

## State, admission and per-generation resources

Use a synchronized state machine `UNINITIALIZED -> READY(N) -> RUNNING(N) -> STOP_REQUESTED(N) -> DRAINING(N) -> STOPPED(N)`. `init` may create the first READY generation; known existing deferred semantics allow six requests to enqueue in READY before connect. A later `init` may create generation N+1 only after the prior generation has actually reached STOPPED and its callback, socket, work queue and thread barriers have completed. An active or STOPPING init returns false. Config/account identity, retained order state and positions must be tied to the appropriate mocker/account identity; changing IDs cannot silently inherit another account. Same-ID open orders and persistence semantics require an explicit compatible contract: never silently clear, reissue or claim an order resolved.

Admission and enqueue must be one mutex-protected linearization point. Calls admitted before stop are recorded as accepted; calls after the stop transition return a negative value for order and query APIs (the current `TraderAdapter` treats values <0 as failed). `connect()` is void, so its rejection needs a documented observable nonzero connection event or separate status capability; it cannot report asynchronous vendor connection success. The callback gate closes in an order compatible with owner SPI lifetime, and API calls hold object lifetime only under an explicit owner contract.

Give each generation its own stable shared state containing its io_context, work guard, socket, matcher, listener lease, retained order/tick/trade state and stop signal. Worker and currently executing callback hold strong references to that state; queued handlers refer to state through weak references to avoid `state -> io_context -> handler -> state` cycles, while capturing retained WTSEntrust/WTSEntrustAction in RAII holders with exact retain/release. A failed post, canceled queue or destroyed unexecuted handler must release its payload once. Every handler validates the generation/admission boundary before side effects; stale queued orders must never execute in a later generation. Socket cancellation and close must precede destruction of its receive buffer/state, and no canceled old receive may reconnect a new socket.

Once closed to new submissions, distinguish already-admitted active work from queued work. Draining actual orders during shutdown can create unwanted side effects; silently discarding previously accepted orders can lose acknowledged requests. The product contract must choose an explicit cancellation/result or reconciliation mechanism, including what happens when the existing owner has called `registerSpi(NULL)` before release. Until such semantics exist do not claim that stopping/destroying io_context is a complete orderly shutdown. Provider callbacks and callback-generated commands are part of the in-flight accounting. No queue lock or lifecycle lock may be held across an external SPI/strategy callback or join.

## External and reentrant shutdown

From an external owner thread: atomically close admission; request matcher and socket stop; resolve the previously admitted queue according to the chosen contract; wait for admitted SPI callback leases and active handlers to finish; join both worker/matcher; destroy old io_context/queue and release retained inputs; confirm resources and generation are quiescent; only then mark STOPPED. A permanently blocked SPI callback cannot be safely force-killed: expose timeout/failure and retain dependent objects/module instead of reporting successful teardown or freeing them.

From an io/matcher callback: a synchronous wait for its own callback/worker is impossible. It may request stop but cannot truthfully claim a drain barrier before returning. The current raw `ITraderApi::release()` is void: an owner can call `release()` and immediately `deleteTrader`/unload the module. `WtCore/TraderAdapter.cpp` does exactly this on its release path, while the mocker's handlers currently capture raw `this`. A safe architecture therefore needs an independently versioned lifecycle capability (without changing the old vtable) such as `requestStop()` and `waitStopped()`/status, and owner integration that keeps the API object, SPI/config and plugin module alive when called from a callback and completes waiting/deletion from an external owner thread. WtUftCore already has an adapter callback admission/wait concept, but it must still consume the provider's actual stop barrier. Old ABI callers that immediately destroy or dlclose in a callback cannot be made safe merely by returning early from void release. No detached worker may retain a raw facade pointer; even state-only asynchronous work requires the plugin's code module to remain loaded through its final instruction. The owner must manage that module lifetime or use a deliberately pinned module with explicitly documented resource tradeoffs.

## Required tests before closing

- Both existing failure cases: same-instance two-cycle handshake with stable warmed FD set, port released each cycle and baseline restored after destructor; before-release queued and after-release attempts cannot mutate or callback in next generation. Cover inputs that were accepted before shutdown and their specified cancellation/drain outcomes.
- Controlled blocked SPI handler + concurrently queued retained order and cancel, STOPPING admission race, disconnect/release/reinit overlap, cancellation error injection and exact once retain/release. Repeated release and concurrent external stops must not double-join, free, or allow reinitialization before STOPPED.
- Reentrant stop and owner delete from connect/login/order/trade callback: owner requests only in callback; external reaper waits; no callback/worker uses facade, SPI, data manager or plugin code after deletion/unload. If unsupported legacy host does this, reject/retain safely and report rather than pretend completion.
- Verify current account and same/different mocker-ID state recovery and no duplicate order execution, response or cancel across cycles. Test UDP cancellation/late packets from old endpoint, matcher termination and reconnected new endpoint.
- Run applicable ASan/UBSan, TSan, reference-count/destructor controls, bounded hang probes and real platform/provider tests; record unsupported sanitizer runtimes. Full regression is deferred until the 213 tasks are repaired.
