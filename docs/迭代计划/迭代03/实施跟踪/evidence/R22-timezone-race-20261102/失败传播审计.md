# 时区读取失败传播审计（静态分析，未修复）

本文件依据当前工作树的 `TimeUtils.hpp` 与各调用点，不代表已做整链故障注入。时区初始化局部测试见同目录 `README.md`：平台函数失败时 `getTZOffset()` 返回 `99`、不缓存失败，后续调用可以重试。**当前生产调用方未检查该值；失败期间仍可能计算并使用错误日期和时间。** 本审计不声称 `99` 是可供现有业务安全消费的失败协议，也不把局部线程安全测试视为本问题关闭。

## 传播链和具体风险

1. `src/Share/TimeUtils.hpp:199,215,235,250,317,345,384` 的 `getLocalTime`、`getYYYYMMDDhhmmss`、`getDateTime`、`getCurDate`、`getCurMin`、`makeTime(...,true)` 和 `getNextDate` 将 `getTZOffset()` 直接作为小时偏移参与运算。`99` 在 `fasttime` 中会被当成四天零三小时的有效偏移，既不是异常也不是 UTC。`getDateTime` 的 `void`、其他值返回接口本身无失败位；`getLocalTimeNow()` 对 `clock_gettime()` 的返回值亦未检查，是相邻但独立的失败来源。
2. `src/WtDtCore/StateMonitor.cpp:177-188` 初始化时分别读取日期和分钟并写交易日；`:610-621` 再将读取结果交给 `advanceOnce` 和后续缓存清理，`:486` 状态推进可触发历史数据转换。因为两个查询分开进行，首次失败后立即重试成功时，日期和时间甚至可能来自不一致的两次结果；仅在循环中跳过一次不保证初始化原子性或行情接收关闭。
3. `src/WtCore/WtEngine.cpp:81-88`、`src/WtUftCore/WtUftEngine.cpp:167-176` 在构造阶段直接发布日期时间给 `WtHelper`；`src/WtCore/WtCtaTicker.cpp:47`、`WtHftTicker.cpp:75`、`WtSelTicker.cpp:57` 同样读取值。它们的现有构造接口没有可观察的时间初始化失败返回，因此只改变 TimeUtils 返回值不能使交易启动自动拒绝。
4. `src/WtCore/TraderAdapter.cpp:99-111` 和 `src/WtUftCore/TraderAdapter.cpp:187-200` 通过当前日期计算 local ID 初始种子；错误日期可能被固化进进程静态计数器。账户订单身份、重启和冲突还受 NEW-008/N05-003/L01-014 约束；此处不能简单使用新哨兵继续分配 ID。
5. `src/TraderCTPOpt/TraderCTPOpt.cpp:1851-1867` 在发送结算确认前读取日期，并固定从 `getLocalTime().c_str()` 复制 8 字节。若只将时间失败映射为空字符串而不改调用方，则可能越界读取；若填入零值并继续发送，则未证明对端会拒绝。该具体发送路径需要在构造请求和 SDK 调用之前判断失败并返回错误，且需验证没有副作用。
6. `src/WtBtCore/HisDataReplayer.cpp:1727,1893-1895,1935-1937` 使用 `getNextDate` 作为循环步进；直接把失败变成 `0` 并继续可能导致错误范围或无法终止。`src/WtDataStorage/WtDataWriter.cpp:319,500-530,2022,3120` 也用日期选择合约、存储块、写入日期和输出文件名，不能假设零值自动安全。完整调用面远超这些例子：当前树内有数十个相关源码文件，仍需逐一登记。

## 候选迁移顺序与验收条件

1. 在不破坏既有函数签名的前提下增加明确返回成功位的时钟/时区及日期快照接口；失败时不发布输出，不能把 `99`、零或空文本解释为成功。一次读取应得到同源日期和时间，保证同一快照使用同一次已验证时钟和时区；缓存仍需明确 TZ 改变、DST、半小时时区及每翻译单元独立缓存的现有局限。时钟系统调用、UTC/本地分解、`mktime` 和 `fasttime` 的失败均需可注入，`mktime == -1` 与合法 epoch `-1` 的歧义须明确合同。
2. 在监控器初始化前先取得有效快照，校验所需日期计算，再允许修改交易日或发布状态；任何失败都要保持初始化事务性、停止接收/暂停状态可观察，明确谁重试及恢复后如何对账。运行中检查失败时不得推进状态、生成 writer 事件或自动宣称安全恢复；必须由 owner 的状态机协调行情接收及生命周期，不能仅依赖一次 `continue`。
3. 引擎/ticker 的创建和启动、订单 ID 分配、结算确认等各自引入可观察失败并在副作用前中止或暂停；对已启动组件及在途交易保留 owner 和对账路径。对于已公开的 `void` 或无错误返回接口，应通过兼容的 checked 接口或版本化结果向实际调用方传播；旧接口的处理及外部 ABI 需逐项决定，不能声称新 helper 自身已保护旧调用方。
4. 回放和存储调用方在日期计算失败时终止当前操作并报告错误，循环必须保证有界退出、无部分发布；可恢复的读写操作需按各自事务合同处理。对日志格式化、固定长度 memcpy 和既有零值合法含义分别做兼容审查，而不是全局替换返回值。
5. 以独立测试先注入每个系统调用失败、首次失败后重试、并发首次读取、跨午夜以及 clock/timezone 连续变化；再用真实监控器、ticker/engine、订单 ID、确认入口和回放/存储路径测试“无副作用、错误可见、状态不被覆盖、恢复后行为正确”。外部 provider、Windows 和真实挂钟/时区变更须单独验证。所有受影响入口与遗留调用方完成前，R22-002 与时间失败传播仍未闭合。

以上是风险定位和候选任务顺序，不是已实现的接口设计或供应商保证；本次未修改产品源码、未运行新的故障测试。
