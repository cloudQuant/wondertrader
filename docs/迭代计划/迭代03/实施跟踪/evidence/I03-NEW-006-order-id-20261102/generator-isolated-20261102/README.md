脚本从三个工作树源文件逐一原样抽取生成器的函数体（不保留 UFT 外层 `inline` 链接属性），在临时实体目录中分别编译，与受控 `TimeUtils` 替身链接并分进程运行；结果及各完整源文件 SHA256 见 `result.txt`。退出码 0 表示实验观测到预期行为，**并非修复通过**。测试没有接入订单、provider、动态库或操作系统真实故障，不能代替上一级目录中的真实 Core/UFT fake 路径和 dyld 证据。

- 正控：健康时首次分配为 50；12 线程并发生成 12000 个连续不重复 ID，只覆盖健康初始化和计数。
- 初始化失败反控：模拟年初 `mktime` 失败而现有 `makeTime` 返回 0。三者均把失败结果计算成 3598981426；模拟恢复后返回 3598981427，而全新健康进程首个结果为 50。这说明首次失败固化进 `once_flag`，没有重试初始化。受控时钟值用于可复现性，不声称现实系统实际发生了这一故障。
- 回绕反控：模拟不同的墙钟值和同一年初转换失败，使首个结果恰好接近边界；三者继续分配 `UINT32_MAX`、`0`、`1`，没有保留值或回绕拒绝保护。该实验不证明线上已有重复订单。

## 可执行的迁移方案与门槛（尚未实现）

1. 先确定并记录三类宿主及混合加载的 ID 作用域、旧导出调用方、历史未终结订单和回放/重启的保留范围，明确旧二进制是否仍须获准发单。针对加载集和顺序分别确认绑定，不能把某一次 dyld 结果推广为跨平台合同。跨重启唯一性须与 NEW-008/N05-003/L01-014 的身份和恢复方案统一。
2. 在共同的、明确拥有者的生成器上引入版本化 checked 能力；时间单次采样，校验年初转换、单位和运算范围，在失败时不发布初始化状态，允许重试。排除 0 和约定的失败哨兵，耗尽时拒绝而非绕回。原 `makeLocalOrderID()` 符号和调用约定须保留并经旧二进制验证；新检查和真正分配必须由同一解析的生成器实例完成，不能分别对各 TU 私有状态做预检。
3. 先在不触发 provider 和 undone 的阶段确定一次请求真实需要的拆单计划，并在同一状态中为实际订单意图做原子准入；不能通过分配后丢弃一个 ID 来测试可用性。对同步重入、行情或持仓在调用外部函数期间变化的情况，先确定计划失效及未提交意图如何处理，避免隐式改变旧的拆单与回报合同。不得持有生成器或账本锁跨 provider 调用；不得按合约整体回滚。订单登记、撤销/拒绝、未知结果及恢复与身份账本共同设计。
4. 三类宿主迁移所有真实订单入口：Core buy/sell 的聚合 undone 更新之前以及直接开平仓入口；UFT 四个开平仓入口更新之前；BtCore 的 HftMocker、UftMocker、MatchEngine 在插入订单或触发回报之前。失败应返回各入口明确的失败形态，集合不含失败 ID，且没有 provider `makeEntrustID`/`orderInsert`、订单插入、undone 或通知副作用。
5. 旧 ABI 只有无状态 `uint32_t` 返回值，仓内旧调用方并非都检查失败哨兵：例如 `MatchEngine` 直接用 ID 写 `_orders`，`UftMocker` 也直接建单。因此保留符号并简单返回失败值不能保证旧调用方安全。对不能升级的旧调用者，要么取得明确的宿主隔离/禁用交易合同，要么实现并验证兼容适配；在此之前无法声称“所有订单入口失败时均无副作用”。
6. 使用实际生成器和实际调用路径，分别验证三类单宿主与可重现混宿主：故障首次并发、恢复重试、分配耗尽、拆单、同步回调重入和已有订单并存；编译运行旧客户端对新库的 ABI 正反控，再覆盖目标平台、供应商 SDK 及真实部署。隔离 fake 和本实验均不能替代这些验收。
