# BUG-R41-003 WtCore notifier worker, bounded local candidate

2026-11-01, macOS arm64. Scope is WtCore/EventNotifier, not WtBtCore's similarly named component. This candidate retains an io_context work guard while running; serializes admission/check/post with stopAccepting under one mutex; closes admission and resets the guard before externally joining; and destroys the MQ server after join. A single worker runs queued handlers. Each handler catches exceptions, emits a topic-specific stderr diagnostic, and lets subsequent handlers run. Post failure emits a diagnostic and is rethrown; notification rejected during stopping emits a diagnostic. A successful post is the only meaning of “accepted”: the public notify APIs return void and provide neither delivery acknowledgement nor durable or exactly-once guarantee. No detached thread is introduced.

## Before/after black-box audit

Before this candidate, `/tmp/wt-i03-r41-audit/audit-before` was compiled with the prior notifier and current atomic stop-flag subfix. `/tmp/wt-i03-r41-audit/input-before.sha256` plus its input-check.log record that snapshot; the compiled object and old result logs remain there. The harness uses the real init-created worker, a local fake MQ and a controlled publisher. It is a diagnostic whose return values encode expectations of the OLD behavior, not acceptance tests for the new implementation. Copy of the old output: results.log, early.log, idle.log, idle-stop.log, guard.log, pending.log, throw.log. The candidate binary was linked via audit-build.sh and run via audit-after-run.sh; see audit-after-results.log and audit-*.log.

- Early post with an external guard: delivered before and after.
- With no external guard, old context became stopped after idle and a later notification was not delivered. The candidate remained active and delivered it. The old diagnostic exits 0 when it observes the defect; the candidate exits 1 because it no longer sees that defect.
- With the first publisher blocked, an event and order were queued and then external destruction requested. Old behavior completed the first callback but dropped the two later publications; the retained order was nevertheless destroyed once. Candidate published all three in FIFO order and destroyed the retained order once. Old diagnostic exit 0 means old drop observed; candidate exit 1 means that old expectation failed.
- A publisher throw on the old worker invoked a custom terminate handler with exit 88. Candidate reports `GRP_EVENT handler failed: test publisher`, survives, and the old terminate-expecting diagnostic returns 1. The dedicated new test separately proves a later handler runs.
- With an unrelated externally held guard, observed destructor had not returned within 150 ms; releasing that guard let it return, before and after the candidate. This is a bounded local observation, not proof of any absolute hang duration.

## Limits

System Apple clang TSan failed to run even an empty main and a known-race control, both exit 139 without diagnostics. Empty ASan control timed out under the 20-second alarm (exit 142); original control evidence is `/tmp/wt-i03-r41-stop/tsan-*-{run.log,exit.txt}` and `asan-benign-*`. No sanitizer success, and no dynamic TSan red/green, is claimed. Other precompiled libraries are not sanitizer-instrumented.

A publisher that never returns, another party's unreleased work guard, or a blocking stderr write can make stop/join unbounded. Concurrent calls must finish while the object is alive; owners must quiesce raw-pointer producers before destruction. A callback that destroys its own notifier still cannot safely join itself: no detach or early unload is used. The worker catches ordinary C++ exceptions from individual handler bodies, not signals, process termination, memory corruption or asynchronous work inside a third-party plugin. Calling publisher to completion does not establish SDK callback drain. Concurrent/repeated init and module lifetime are separate unclosed issues; no Windows/Linux, real SDK, final-tree or full regression claim is made. `git diff --check` for owned files passed (diff-check.log).

The post-review fake service destruction check was also repeated in ten separate processes; service-repeat-results.log and service-repeat/*/result.xml show 10/10. Each run checks destroy_server is not called while the controlled publisher is blocked and is called once after it returns.
