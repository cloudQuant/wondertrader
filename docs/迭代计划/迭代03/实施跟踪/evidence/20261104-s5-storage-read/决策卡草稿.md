## S5-A：V1→V2 分钟键迁移的接入合同（BUG-R100-003 / BUG-R32-003；关联卡 13c）

**现状（已核对）**：`LMDBBarKeyV2.hpp`（16+32+8 字节、64 位大端时间）与 `LMDBBarMigration.hpp`（离线 staging：只读源 env、独立目标 env、逐条“独立时间证据”、4096 条/批、可恢复 manifest）均为孤立组件，生产读写未引用。卡 13 子任务已让 writer 对 `bar.time > UINT32_MAX` 拒写；本包让三个 AD 读端对 2033 起的分钟 cutoff/minute-end 明确拒绝（不回绕），日线按日期键不受影响。卡 13c=A 只给出“取得版本来源才迁移、未知格式隔离”，没有回答以下产品问题。

**要决定什么**：
1. 是否现在接入 V2，还是先维持 V1 + 2033 起明确拒绝（截至 2032-12-31 可用）。
2. 若接入：V2 存放位置（独立 env 目录，如 `min1v2/<exchg>/`，或带版本标识的命名 DB）、读端切换规则（manifest=Complete 才读 V2；V2 未完成时是否双读 V1）、writer 切换点与回滚（V2 已接受新写后不可回退 V1）。
3. 迁移“独立证据”来源：现组件要求时间证据独立于 V1 键和值。对当前已知版本 writer 写出的 V1 数据，是否接受“值内 64 位 time 与键尾 32 位一致”作为版本来源证据（卡 13c 意义上的“已知格式”），不一致者隔离。
4. 部署门禁：迁移前停 writer、阻止旧二进制；各交易所×周期分 env，切换非原子，部分完成如何恢复。

**选项**：A 暂不接入（现状 + 文档化 2032 上限，后续版本迁移）；B 接入独立 V2 env + 离线迁移 + manifest 切换；C 原 DB 内混写 56 字节键（审计已否决：破坏键序与范围查询）。

**建议**：短期 A（已 fail-closed，不静默回绕）；在 2032 年前另立版本做 B，证据规则按第 3 点“已知版本 writer 的自洽键值即版本来源，不一致隔离”。需要用户确认 A 是否可作为本迭代 R100-003/R32-003 的验收口径（否则两项保持阻塞）。

**影响**：BUG-R100-003、BUG-R32-003；BUG-R122-002 的“分钟 key uint32 日期上界”子项；P05-010 不受影响（历史 10 字节交易所键仍需真实样本，X）。

## S5-B：HOT/custom 规则跨换约的数据来源与切换边界（BUG-R122-002）

**现状（已核对 `WtDataReaderAD.cpp`）**：
- `readKlineSlice` 首载用 `cInfo._code`（HOT 为品种码，如 `rb`）读 LMDB 预合并历史；无该历史时拒绝回落到物理合约（fail-closed，已有测试）。
- 之后的增量 `update_cache_from_lmdb` 与 RT 缓存读取用 `getCustomRawCode` 得到的**物理合约**（如 `rb2405`）；`onMinuteEnd` 的增量与 RT 读取却用**品种码** `cInfo._code`。同一缓存的两条更新路径读取不同键；live writer 只按物理合约写 LMDB/RT 缓存，品种键只能由外部导入维护。
- 换约当日新合约的增量直接拼接在旧合约历史之后，无复权、无切换边界规则。

**要决定什么**：HOT/custom 序列的权威来源、切换时点、是否复权、预合并历史与增量的兼容。

**选项**：
- A 物理分段：按 hot 规则的换约区间拼接各物理合约 K 线（与非 AD `WtDataReader`/回放器一致），可选复权因子；不依赖品种键预合并历史。
- B 预合并历史 + 物理增量：品种键由外部作业每日维护，读端在换约日按规则切换增量来源；要求作业与读端对边界一致。
- C 在 A/B 落地前，AD 读端对 HOT/custom 一律 fail-closed（返回 NULL + ERROR）。

**建议**：先 C（消除品种键/物理键混源），再实施 A。需用户确认是否接受 C 的行为变化（当前有预合并历史的 HOT 读取会失败）。

**影响**：BUG-R122-002（HOT 子项）；本包已完成的有界暂存、损坏不部分提交、只读目录缺库三项不受此卡影响。

## S5-C：RdmDtReaderAD 增量游标与历史修订可见性（R21-BUG-07；迭代02 撤回的游标候选）

**现状**：`readKlineSliceByRange` 的 `_last_bar_time` 从未赋值，非空缓存每次全量扫描 `[0,0xffffffff]`，因此同键修订（含最早的 bar）总可见。本包只做了**不改变可见性**的部分：记录扫描快照的 LMDB 已提交事务号（`mdb_env_info.me_last_txnid`，扫描前后一致才记录），环境无新提交时复用缓存不扫描；任一提交（含其他进程）仍全量重扫。实盘有 writer 持续提交时仍为 O(全量)/次。

**要决定什么**：有新提交时是否允许只读游标之后（O(新增)），以及更早 bar 的修订何时可见。

**选项**：
- A 维持全量重扫（现状）：修订即时可见，代价 O(N)/次。
- B 末 bar 游标（含末 bar 重读）：只读 `[last_bar, +∞)`；更早的修订在 `clearCache`/显式失效前不可见；需公开文档与失效 API。
- C B + 有界陈旧：交易日切换或距上次全量超过阈值时全量校验，修订在有界时间内可见。

**建议**：C；若产品明确“历史只追加、修订只发生在末 bar”，可选 B。切片悬空问题已由卡 11 解决，不再是阻碍。

**影响**：R21-BUG-07。

## S5-D：RT HFT 读端是否可见最后一个已发布槽（BUG-R100-004）

**现状**：卡 13 已实现跨进程发布协议（载荷写完后对 `_size` 做 release 存储；读端规则 `visible = min(acquire(_size), acquire(_capacity), 本进程映射记录数)`）。`WtDataReader` 的 RT 读取已改用该规则并**包含**最后一个已发布槽；`WtRdmDtReader` 的 RT 委托队列/明细/成交以 `find_rt_hft_end_index(items, _size - 1, …)` 显式排除最后一槽（注释“final slot is still writer-owned”）；其 RT tick/K 线以 `lower_bound(…, _size - 1)` 加回退判断，实际可包含末槽；以上均为普通读取 `_size`，未 acquire、未按本进程映射钳制。同一 reader 内及两个 reader 之间对末槽的可见性不一致。现有 `R100RdmCrossDayTest.R100RdmRtHftCrossDateBackoff`（期望 3 实得 2）、`R70Rdm*RangeClips` 仍按“末槽可见”断言失败（本包未改 oracle）。

**选项**：
- A 末槽可见：`WtRdmDtReader` RT 路径统一改用卡 13 的 `visibleRecords`（acquire + 映射钳制），区间搜索覆盖 `[0, visible)`；现有失败断言随之转绿，无需改 oracle。
- B 末槽归 writer：两读端统一排除末槽（`WtDataReader` 需回退），并按该合同改写上述 oracle。

**建议**：A。卡 13 协议已保证已发布槽完整（协议外：旧 writer、非合作进程、原地更新的最后一根 K 线仍可能撕裂，已在卡 13 记录）。需用户确认后实施，并补跨进程尾槽/扩容重映射用例（可复用 `i03_storage_multiwriter_20261104` 的两进程夹具）。

**影响**：BUG-R100-004；另报新问题：`WtRdmDtReader` RT 路径未采用卡 13 读者可见性规则（普通读 `_size`、未钳制映射）。

## S5-E：CMP_V2 历史块解压的资源预算与拒绝策略（BUG-R132-001）

**现状**：`proc_block_data`、`decode_his_compressed_items` 与 `WtRdmDtReader` 三处 V2 分支按 zstd 帧头声明的 content size 一次性分配（`WTSCmpHelper::uncompress_data` → `resize`）；仅校验 UNKNOWN/ERROR、`max_size()` 与记录整除，未设上限。几十字节的恶意/损坏帧可声明数十 GB，`bad_alloc` 被捕获返回失败，但在允许超额分配的系统上会先触发巨额零填充。块头只有压缩长度，没有记录数可交叉校验。

**要决定什么**：单块解压上限（绝对值、相对压缩比、是否可配置）与超限处置。

**选项**：A 绝对上限（可配置，默认如 1 GiB）；B 压缩比上限（如 ≤1000:1）+ 绝对上限；C 按记录类型的每交易日上限（如 tick ≤ N 条）。超限一律：不分配、返回失败、ERROR 日志、不部分缓存。

**建议**：B（默认值需用户给出，或接受建议值：绝对 1 GiB、比率 1000:1，配置项可覆盖）。

**另**：同条剩余的“历史块 12 字节打包头导致记录数组未对齐（UB）”是实现项，不需裁定：需把 `Hist*BlockPair` 的记录改存对齐缓冲（类似已有 `copy_his_items_aligned`）并同步切片 owner；本包未实施，见 README。
