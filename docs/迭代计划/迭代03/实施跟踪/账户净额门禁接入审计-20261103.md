# 账户净额门禁接入审计（2026-11-03）

用户已确认：每个实际合约分别限制账户净持仓绝对值，与组限额同时生效，任一超限拒绝。本记录是当前源码的只读接入分析，不是已实现的账户门禁或真实交易验收。

## 当前接入边界

- `TraderAdapter.cpp:830` 起，一个 adapter 绑定一个 trader API；但 adapter 的配置 ID 并非经核验的物理账户身份。`WtRunner.cpp:1264` 起可按不同配置 ID 建立多个 adapter，同一账号是否重复配置没有统一证明。多个执行器也可共用一个 adapter。
- `TraderAdapter.cpp:2121` 起，登录后依次查持仓、订单、成交、资金再置 ready。`ITraderApi.h:143` 起的旧查询回调没有查询 ID、成功/完整性状态或快照水位。空结果仍可进入下一阶段；重连快照与实时推送的顺序、旧持仓清理及完整性未闭合。不能把 ready 直接当作可信账户快照。
- `TraderAdapter.cpp:2403` 起的订单查询仅累计本 adapter tag 的活单；`_undone_qty` 是买减卖的净数，不能覆盖另一 adapter 或外部客户端的活单，也不能反映买卖两侧各自的最大成交风险。`getPosition()` 对未知合约返回零，缺少可信/未知状态。
- `TraderAdapter.cpp:2881` 起，成交推送先更新持仓，再调用重复成交检查；该检查不能撤销此前的持仓更新。当前不能据此声明账户持仓已去重且与订单余量原子更新。

## 后续实施约束

共同下单拦截点是 `TraderAdapter::doEntrust`（约1213行）：在调用外部 `orderInsert` 前，已经能看到子单方向、开平、数量及解析后的合约。需要以可信账户身份和实际交易所/合约为键，原子检查并预留额度。父级 buy/sell 目前提前更新未完成量且可能拆单失败，必须一并修正，不能只在这一点加一个数值比较。

额度必须纳入已核验净仓和全部活单的两侧未成交量。例如净仓为 P、在途买量为 B、卖量为 S，应分别考察 P+B 与 P-S，不能先将 B 与 S 抵消。未知提交结果、撤单请求或超时不能自行释放预留；只有可信拒绝、终态或对账结果才能改变其归属。成交增加持仓与对应订单减少余量必须在同一一致性范围内按稳定身份处理。

至少还需：稳定物理账户键、实际合约和交易所别名映射、完整快照与水位、稳定订单/成交身份、每单提交和终态、查询期推送协调、并发预留以及重连恢复。存在无法纳入协调的其他进程或外部客户端交易时，本进程的局部锁无法保证全账户上限。

`DiffOrderOwnershipV1` 提供了部分身份/WAL组件，但尚未接入生产 TraderAdapter 回报与提交链；owner 路由 helper 也不能替代真实能力协商。连续合约的上游解析并不覆盖所有 adapter 入口，账户键必须来自本次真实子单核验后的物理合约，不能直接使用 HOT 等订阅码。

本轮 Local/Arbi 的组目标与组限额验证不关闭上述账户门禁事项。未连接 provider、未发送交易、未运行跨进程或真实账户测试。
