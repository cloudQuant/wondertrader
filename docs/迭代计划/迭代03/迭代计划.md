本迭代实际状态见[执行跟踪](执行跟踪.json)与[执行记录](实施跟踪/执行记录.md)；基线快照中的原状态不随实施结果改写。

这 213 条是跟踪条目，并非 213 个独立产品缺陷；其中包含产品、测试、合同及关联事项。同一根因可以一起实施，但每条都必须独立对照原验收条件，保留关联关系，不能以删除、合并或改变状态制造进度。固定基线之后，新发现问题另建编号并记录与本轮任务的关系，不擅自改变 213 的分母；并发工作导致原清单更新时，以快照识别变化并逐项复核，不覆盖其他工作。

本计划不把迭代 02 的 `TEST_PASS` 等同于整体验收，也不把本机测试、fake SDK 或局部组件通过外推为供应商、跨平台或生产通过。当前工作区存在大量未提交修改，实施前须记录分支、HEAD、工作区内容和源文件哈希；不得清理或覆盖已有工作。

## 2. 前置合同与实施约束

- **插件兼容**：沿用已确认的执行器插件决策，保持旧虚函数签名、旧基类 vtable 和调用 ABI；通过独立版本接口或版本化导出报告初始化结果。无法证明初始化成功的旧插件仍应可按旧 ABI 加载，但须有诊断、拒绝注册及运行。分别验证 Local、Diff、Arbi、回测入口及失败后安全重试；具体实现与当前状态需核查最新代码，不能照搬早期计划中的历史状态。
- **股票 VWAP**：按标的已知最小合法交易单位处理；不能执行的余量保留为未完成，不能标记完成或发送不合法整手订单。覆盖买卖、T+1、目标变化和重复行情；未取得具体市场规则前不假设允许零股。
- **禁止创建符号链接**：使用实体头文件、插件和独立测试目录；`NEW-133`、`NEW-137` 原依赖符号链接的负控须寻找满足该约束且语义等价的验证方式，否则明确记为未运行和阻塞，不视为通过。历史路径当前是链接不证明历史运行时一定如此；相关项须按现有保守状态重新核验。
- **待定合同**：限频窗口及恢复、端点包含关系、Session 跨日、回调与关闭、持久化恢复、借用切片与并发等，以公开接口、现有真实调用者、已确认决定及版本匹配的供应商材料为依据。先利用既有复现与静态分析推进隔离设计；无法确定时记录选项、影响和所需决定，保留阻塞，不弱化断言来取得绿色结果。[历史待决列表](../迭代02/复核185/待用户决策.md)是线索，需逐条确认是否仍适用。
- **安全边界**：本地测试不触发真实下单、撤单或结算；真实 provider、柜台和部署验证需要相应环境与授权。外部版本条款须与实际 SDK 精确匹配，fake 只证明构造输入的本地行为。

## 3. 分阶段执行

### 阶段门和顺序

1. **集中修复 213 项**：先逐项复核、设计并完成所有需要的产品和测试代码修改，按下述工作包解决依赖。修复期间可以运行与这 213 项直接对应的失败用例，以及验证相关修复所必需的定向正反控；其他 5000 多个无关用例先不运行。对仅缺证据的事项，按原要求重编并运行对应的定向验证。记录具体运行范围和结果，不能根据编译成功标记修复通过。
2. **第一轮集中回归**：只有 213 项均已完成必要修改、相关定向验证，或已有充分依据证明无需修改，并完成修复集成后，冻结源码及构建输入，进行干净构建，再将这 213 项对应测试和此前暂缓的其他全部用例一起运行，覆盖逐项、跨入口及整合回归。记录所有失败、信号、超时、跳过、禁用及排除，形成问题清单，不边跑边修改该轮冻结快照。
3. **集中复修回归问题**：第一轮结束后归因并汇总全部问题，集中修复产品、测试、构建或环境问题；保留原失败与修复记录。复修期间可运行所修问题对应的失败用例及必要的定向正反控；其他用例留待下一轮整体回归，不能通过弱化正确断言掩盖问题。
4. **整体回归验收**：复修完成后重新冻结最终源码、构建输入和测试清单，执行干净构建、完整逐项及整体回归，并按适用范围执行 sanitizer、资源及并发验收。若仍发现问题，重新按“集中归因和修复 → 冻结 → 整体回归”的方式循环，直到门槛满足；每轮证据与源码版本分开。

未解决的产品或测试修改、合同不明、外部条件不足均不能冒充第一阶段完成。若某项确需用户决策、供应商资料、Windows 环境或受现有约束禁止的操作才能推进，明确记为阻塞并继续处理其他可做项；在解除之前不得宣布 213 项全部修复，也不得把部分回归称为第一轮完整回归或整体验收。需改变这一顺序时以用户后续明确指示为准。

这里的 213 是任务条目数，并不等于 213 个测试用例：一条任务可能需要多个入口或正反控，也可能需要补充测试，多个条目也可能关联同一个用例。每次定向运行须记录其关联任务和选择的用例，不将无关测试混入修复阶段，也不把定向通过当作完整回归通过。

任务清单的每个编号应明确归属工作包；跨包依赖只指定一个主责任，其他包记录关联，避免重复修复。以下 WP0–WP4 为第一阶段的工作划分，WP5 负责后续集中回归和验收；可独立修复的模块和测试可并行，修改同一文件或共享构建目录须先明确所有权并串行整合。

### WP0：冻结基线与恢复可信构建

1. 冻结 213 条编号、输入状态和剩余事项，保存来源文件哈希、源/测试快照及工作树基线；核对 ID 唯一且总数匹配。
2. 配置实体 Boost 头目录和独立空构建目录，记录编译器、依赖版本、构建选项、产物及哈希；不得把当前构建的产物混入另一个快照的证据。
3. 对因历史 Boost bridge 路径未能证明无链接而退回 `IN_PROGRESS` 的条目，登记当前源码、所需重编目标及重跑用例，并在集中修复阶段重编、运行对应定向测试；若条目仍有其他失败或合同缺口，继续保持未完成。完整测试集合留待第一轮集中回归。
4. 根据既有日志和静态分析排查测试共享状态、动态库和 fixture 问题，使用独立进程和隔离目录运行相关定向用例；保存反例、正控、命令、退出码与日志。原有 v7 汇总是旧快照诊断，不作为当前树通过证据。

**阶段交付**：快照及清单可一一映射；构建依赖及本阶段定向测试证据可追溯；对未能修改或验证的路径写明原因和后续工作。完整测试集合的证据在集中回归阶段取得。

### WP1：交易身份、风险控制与订单账本

优先处理 `NEW-008`、`N05-003` 的 owner/版本身份在发单、回报、订单快照、自动撤单和重启恢复之间的闭环；`L01-014`、`R54-001` 未知身份/解析失败事件的隔离、持久化、账户暂停与人工对账恢复；`R3-008`、`Q04-002` 的逐订单未完成量、拆单、同步失败、重复和迟到回报；`NEW-154` 的快照与实时回报协调，以及 `R3-002`、`R3-003`、`NEW-180` 的限流合同。

先固定身份、持久化和并发语义，再进行实现，避免仅按合约聚合数量或简单回滚产生重复记账。验收应有双执行器同账户同合约隔离、部分成交、同步重入、重复/乱序回报、限流窗口恢复、快照查询失败与空结果区别、异常重启和恢复正反控。WAL 组件通过不能代替真实生产回报路径及账户门禁；无法可靠跨硬重启保存的条件必须如实说明。

### WP2：初始化、插件生命周期与关闭

处理 runner、engine、parser、writer、trader、执行器和动态库的初始化失败传播、ready 门禁、注册、回调所有权、停止、排空、join、释放及可重试性。按实际依赖从叶子错误传播到 manager/runner 入口，防止失败对象进入运行态；对插件 ABI 采用上述已确认决策。

每条路径分别验证正常启动、缺符号/初始化失败、重复初始化和释放、并发活动回调、关闭重入及已发生副作用后的重试边界。线程/资源相关项使用适用的 sanitizer 与有界超时；供应商是否保证 callback drain 以精确版本证据单列，fake 不能证明真实 SDK 行为。

### WP3：行情、历史存储与回放

处理 `R122-002` 的连续合约跨换约数据源和大区间内存、`NEW-067`/`NEW-120` 的缓存清理与借用 slice 生命周期，以及其他 reader/writer、LMDB、共享内存、数据恢复、行情区间和回放工作。先确定文件格式、时间边界、损坏数据策略与发布/所有权合同，再构建真实 reader/writer 路径的正负控；不要用裸 `clear` 使在用 slice 悬空，也不能把一次性全量暂存称为有界内存。

验收覆盖交易日和换约边界、空/短/损坏输入、等值时间端点、扩容失败与重启、同键更新、并发读写和合法数据正常对照。跨进程、故障注入与真实断电各按实际证据分别标注，不由进程退出测试代替断电持久性。

### WP4：接口合同、平台与供应商

对时间/日期、Session、字段联合体、配置输出、副作用、C API 返回对象和 SDK 回调等待定事项逐条审查来源和调用链；在仓库证据可以确定时形成兼容的合同、实现和待运行回归，真正需要产品选择时列出受影响行为与可选方案。外部 SDK 条款、Windows/MSVC 和其他不可用环境按编号登记获取方式与责任，按实际条件开展，不将无环境项标记为完成。历史取证清单可从[外部环境阻塞](../迭代02/复核185/外部环境阻塞.md)起步，需再次核对适用版本和当前状态。

### WP5：集中回归、复修与最终验收

先按阶段门完成第一轮集中回归，汇总所有问题并集中复修；复修后记录最终源码及构建输入哈希，用与最终树一致的隔离构建完成受影响目标编译，再整体回归验收。单项行为在多入口存在时分别测量，按需要进行 ASan/UBSan、TSan、泄漏、停机和资源边界测试。保存目标数、用例数、失败、信号、超时、跳过、禁用、构建排除及策略排除；任何未执行或不适用必须说明，不能计为 PASS。

## 4. 逐项执行和状态规则

每条任务保留输入状态，并另行记录本迭代状态、责任人、依赖及关联编号、合同/影响、修复前反例或静态起点、具体修改、构建与测试命令、退出码、证据路径、仍未验证项及下一步。产品修复和测试纠偏分别说明；缺少修复前运行证据时如实写静态分析，不能补称红控。

推荐状态：`待复核` → `实施中` → `待验证` → `本地验证通过` → `已验收`；合同、环境或外部证据不足时使用 `阻塞`，并给出可执行解除条件。`本地验证通过` 仅表示所列范围通过，不自动满足 Windows、供应商或生产验收。用户主动决定调整范围时单独记录，不静默移除原任务；需要保留外部阻塞的条目保留原编号和未完成状态。

每个条目的关闭要求：合同可追溯；产品问题有针对性反例、修复后正反控；所有约定受影响入口得到验证；适用的并发、资源和失败恢复证据齐备；剩余限制明确。确认测试问题或非缺陷时，必须保存足够的归因证据并说明为何不需要产品修改，不能仅因测试失败或通过而判断。
