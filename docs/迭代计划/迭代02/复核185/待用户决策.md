# 需要用户决定的接口与兼容策略

这些事项不构成已验证通过的产品验收。完整依据见[第二轮逐条复核](复核总表.md)。

## BUG-P12-005

- **待决问题**：通用 extractDayData 遇到 WTSBarStruct.add/ask union 时，应按何种权威信息选择跨日聚合语义？
- **可选方案**：增加明确 instrument/field 模式，期货 add 求和、期权 ask 取末值；该函数只支持期货 add，并在调用边界拒绝期权数据；统一保留最后日字段值，另提供期货专用的增仓累计接口
- **建议**：推荐先确认权威类型/字段来源；若同一 API 需要支持两类语义，再采用显式 instrument/field 模式分别表达。合同和测试 oracle 未确认前，不固定 6/16/11 或期权末值为当前行为要求。
- **影响**：改变 day resample API 的 source/ABI 使用方式或调用者路由；若选择全局求和会破坏期权 ask，若保留全局末值会丢失期货跨日增仓。
- 下一步：先由权威调用者/文档明确 extractDayData 如何获知 instrument kind 或字段聚合语义。若合同要求同一 API 支持期货 add 与期权 ask，则增加显式模式或类型来源后再分别实现；合同未确定前不把全局求和或末值替换定为修复。
- 验收：合同必须明确 add/ask 的有效输入类型及其聚合规则，并说明通用入口如何区分；之后按该合同为每种受支持类型建立正反对照。具体数值期望须由确认后的规则与 fixture 派生，不能作为当前测试已验证的结论。

## BUG-P11-001

- **待决问题**：initExt 接入的外部 ITraderApi 由谁负责登录，以及成功 WTE_Connect 是否应由 TraderAdapter 调 login？
- **可选方案**：外部 API 自行登录；Adapter 在 initExt 模式下不自动 login。；TraderAdapter 负责登录；initExt 新增明确的配置/凭据输入并执行一次 login。
- **建议**：采用第二种并把凭据来源加入 initExt 的显式 API；若现有注入者已自行登录，则提供明确模式参数以避免双重登录。
- **影响**：改变外部 API 接入签名/配置方式；现有依赖 API 自登录者需迁移，依赖 Adapter 自动 login 者需提供凭据。认证重复或缺失会影响通道就绪与交易可用性。
- 下一步：按选择实现：若 Adapter 负责认证，给 initExt 增加显式 config/credential source 并验证其生命周期；若注入 API 自行认证，明确标志并在 WTE_Connect 时跳过 Adapter login。避免仅空指针判空后静默继续。
- 验收：按确认的 API ownership 走 initExt->run->registerSpi->connect->WTE_Connect 正常事件链；成功和失败事件均不崩溃，登录恰好一次、凭据来源正确，内部 init(config) 行为不变。

## BUG-P11-007

- **待决问题**：TraderAdapter::initExt 是否应该无条件启用 CSV/rtdata 持久化，还是要允许调用方关闭并指定 per-adapter 目录？
- **可选方案**：保留当前 always-on 行为并把文件路径和副作用写入接口合同。；改为默认关闭，由调用方显式启用并提供输出目录。；新增 savedata/输出目录配置，当前版本保留兼容默认，按迁移计划逐步显式化。
- **建议**：选择第三种；增加 per-adapter 开关和目录，先保留当前默认以免破坏既有 CSV/快照消费者，再计划迁移到显式配置。
- **影响**：影响 latency 工具和外部 API 调用者产生的文件、依赖 CSV/快照的分析流程、测试 fixture 清理路径，以及不同 adapter 间的输出隔离。
- 下一步：按决定保留并文档化 always-on；或新增 savedata 与输出目录配置并定义默认迁移策略。推荐提供显式 per-adapter 开关和路径，但本版本保留现有兼容默认，再由调用方逐步选择。
- 验收：策略确定后，分别验证启用时 CSV/rtdata 写入目标目录、禁用时不创建/修改文件、自定义目录隔离多个 adapter，且既有配置默认行为符合选定兼容规则。

## BUG-N02-003

- **待决问题**：IExecCommand/ExecCmdPtr 是否承诺允许第三方通过 IExecCommand 基类裸指针取得并释放派生执行器所有权？
- **可选方案**：增加 virtual destructor，要求所有依赖模块重编；保持 ABI，明确仅可从 shared_ptr<Derived>/Derived* 构造 ExecCmdPtr
- **建议**：若 IExecCommand 是第三方扩展接口，建议选择增加 virtual destructor 并统一重编；若二进制兼容不可破坏，则选择第二项并收紧所有权构造API。
- **影响**：第一项改变基类 vtable/ABI，需要重新构建并分发所有使用该接口的插件；第二项保持二进制布局，但要求外部调用者不能从基类裸指针重新创建默认删除器的 owning shared_ptr。
- 下一步：若允许基类拥有权，增加 virtual ~IExecCommand 并要求所有外部扩展重编；若 ABI 必须保持，明确禁止由 IExecCommand* 构造默认删除所有权，提供/要求 shared_ptr<Derived> 到 ExecCmdPtr 的安全转换入口。
- 验收：选择增加析构时，用唯一派生析构计数验证 ExecCmdPtr/base-owned destruction 调用派生析构一次并在重建所有插件后通过；选择限制所有权时，文档/API 明确限制并为推荐构造方式加测试。

## R21-BUG-04

- **待决问题**：readTickSliceByRange 的 etime 等于某笔 tick 时是否包含该笔？
- **可选方案**：闭区间 [stime,etime]，包含等值；左闭右开 [stime,etime)，排除等值
- **建议**：左闭右开，与 AD/history 当前表现一致，需调整 RT。
- **影响**：闭区间改变 AD/history 等值结果；半开区间改变 RT 等值结果。
- 下一步：建议统一左闭右开，和 AD/history 一致且避免相邻窗口重复；若选闭区间则改 AD/history 并评估调用者。
- 验收：用 before/equal/after 与相邻窗口 fixture，在 AD/history/RT 验证同一所选合同。

## BUG-R83-002

- **待决问题**：WtBtPorter 的 hft_buy/hft_sell 是否允许并发调用，返回 WtString 在何时失效？
- **可选方案**：仅允许串行策略回调线程调用，返回指针在同函数下一次调用时失效。；允许多线程并发调用，返回指针在同线程下一次同函数调用时失效。；调用方可以跨后续调用保留结果，需要调用方缓冲或显式所有权 API。
- **建议**：选择第二项，保留现有 C ABI 类型，使用 thread_local 缓冲并在头文件说明指针有效期；调用方需长期保存时立即复制。
- **影响**：第二项修复跨线程共享缓冲竞争，不改变返回文本和函数签名；第三项需要增加 API/所有权规则，兼容影响较大。当前无外部 SDK 阻塞，缺的是仓库维护者对公开 C ABI 的调用契约选择。
- 下一步：先选定并写明调用线程与返回指针有效期。推荐把 buy/sell 返回缓冲改为 thread_local，并规定指针到同线程下一次相同函数调用前有效；如果需要更长保留，则提供调用方缓冲或明确所有权的新 API。
- 验收：根据选定契约增加有效商品/非空订单 ID 的用例。若支持并发，两个线程并发调用并在各自线程的下一次同函数调用前读取结果，ID 不互串且没有共享缓冲数据竞争；若允许跨调用保留，则验证新增所有权/输出缓冲 API 的生命周期。

## BUG-R19-003

- **待决问题**：delete_section 后段槽何时必须可复用？
- **可选方案**：立即复用；显式压缩后复用；下次 init_master 回收

- 下一步：明确立即复用、显式 compact 或下次 init_master 回收，再按合同实现兼容的回收协议。

## BUG-R19-012

- **待决问题**：省略 init_cmder path 时不同 name 应隔离还是共用 .cmd？
- **可选方案**：按 name 隔离；默认全局共享
- **建议**：默认按 name 隔离；共享由调用方显式传同一路径。
- **影响**：改变默认文件名可能影响现有依赖全局 .cmd 的调用方。
- 下一步：确认语义；若 name 表示队列隔离则对 name 安全编码为文件名，若全局共享则文档说明并提供显式共享参数。
- 验收：两个不同 name 省略路径时按选定契约共享/隔离；显式同路径另测。

## BUG-T27-007

- **待决问题**：ParserXTP 是否必须输出 XTP_TBT_STATE（上海新债券 Level2 状态订单）？
- **可选方案**：在 ParserXTP/WTS 中增加统一状态订单表示与回调；明确暂不支持并提供可观测忽略/告警
- **建议**：先不支持，直到产品确认 WTS 状态订单记录与下游消费合同；当前通用 SPI 没有状态订单回调。
- **影响**：支持会新增公共数据语义并影响存储、回放和消费者；不支持则对该证券类别明确能力边界。
- 下一步：决定产品范围。若支持，先确定 WTS 记录、排序、持久化与回放语义后新增映射；若不支持，明确标注上海新债券 State 回报不支持，并提供可观测诊断。
- 验收：能力决定后，支持时验证每个 SDK 字段映射及回放/落库；不支持时验证回报被计数/告警且不被误认为已消费。
