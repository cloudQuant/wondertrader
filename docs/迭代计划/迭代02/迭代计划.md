## 5. 已发现的测试纠偏原则

### 5.1 完整行情字段与增量字段

`BUG-R32-002` 的旧测试新日首笔未填 `pre_interest`，却要求 `60 - 50 = 10`。`WTSTickStruct::pre_interest` 是上日总持，`procFlag=1` 分支按完整快照字段求差；当前接口没有规定 0 为缺省哨兵。应显式输入 50 并断言增仓 10，同时独立覆盖真实上日持仓为 0 时增仓为 60。原“必须回退到上一笔缓存”的主张撤回。

该 writer 另有真实的 `_async_task` 未初始化问题（`R4-BUG-01`）；测试夹具通过堆块清零/复用不能消除未初始化读取。上述纠偏用例在该产品前置问题解决前禁用，标记 **运行 BLOCKED**，不能记作 PASS。该阻塞仍作为产品主项保留。

### 5.2 午夜时钟与收盘标签

`minuteToTime(1440) == 2400` 是 Session 保留收盘端点的既有表示；不能将其强行改成 0 来迎合测试。修正 R202 两个工具层用例，分别验证收盘标签为 2400、时钟偏移为 0。ticker 对这两种表示混用的跨日/收盘风险独立保留，后续必须使用合法 `23:59:59.xxx` 输入验证日期和 `on_session_end`；旧 `23:59:60` 输入无效。

### 5.3 其余逐项纠偏

对静态对象零初始化掩盖成员缺省、回调前未建立委托/合约、跳过就绪门禁、构造非法压缩格式、缺失 session、错误 bar period、重复释放和只写 `SUCCEED()` 的占位测试，按模块裁定逐项处置。缺少回归不等于测试误报；未定义的返回值、NULL 或所有权合同不能由测试作者自行规定。

### 6.3 订单查询结果必须区分“已确认空单”与“查询状态未知”

本轮代码复核确认，当前 `ITraderSpi::onRspOrders(const WTSArray*)` 没有独立的查询结果状态或错误码。多个柜台适配器在终态回调时都可能传 `NULL`：它既可能表示成功但无订单，也可能表示查询失败；部分实现还可能在查询中遇到错误后，将已经累积的部分订单数组作为终态结果返回。`TraderAdapter::onRspOrders` 收到 `NULL` 时仍可能推进查询状态，而旧 `_orders` 快照并未必失效；因此调用方可能遇到两种错误判断：无历史快照时无法区分正常空单与失败，有历史快照时可能把旧单据误当成当前有效结果。股票 VWAP 将不可用订单表按 fail-closed 处理是正确的安全边界，但当前接口可能使一个成功的空单查询也永久不可用。此项为已定位的产品/API 契约问题，**版本化状态接口及 provider 更新尚未实施，不能计为完成**。

修复设计应保留 `ITraderApi`、`ITraderSpi` 现有虚函数签名与 vtable ABI，新增 sibling 版本接口或版本化 C 函数表，不在旧基类中追加虚函数。新版订单查询请求携带查询 token；结果显式包含 token、终态 `SUCCESS/FAILED`、provider 错误信息，以及完整订单集合。只有收到匹配当前会话和查询 token 的成功终态，才能发布为有效快照；显式 `SUCCESS + empty array` 表示已确认无挂单。查询失败、超时、同步拒绝、未知结果或旧 token 的回报必须使当前快照不可供交易执行器消费，不能退回使用先前成功快照。成功终态必须证明集合完整，不能把部分累积数组因其非空就当成有效结果。

旧 ABI provider 继续按原接口运行，但旧回调的 `NULL` 只能解释为 `UNKNOWN/FAILED` 并 fail-closed；旧 ABI 下非空数组也需确认其对应成功的完整终态，不能在 provider 可能“部分数组 + 失败终态”的情况下无条件视作成功。对依赖有效挂单快照的交易执行器，未提供可验证查询状态的旧插件应显式报告不可用并停止该次交易；不得把未知状态伪装成空订单集合。新版 provider 可用经验证的成功空数组恢复空单场景正常运行。适配器还需清除旧快照有效标志并按 token/session 丢弃迟到回报，避免重连或新查询被旧响应覆盖。

实施和验收分层如下：

1. 先以 fake provider 验证旧 ABI 可加载、旧 vtable 不变；旧 `NULL`、部分结果后失败、同步拒绝及超时均令查询状态未知、快照不可消费且 VWAP 不发单。
2. 验证新版接口的成功空数组会产生有效空快照；成功非空完整数组保留订单 ID/未完成量；失败结果会使之前成功快照失效；旧 token/旧 session 回报不能覆盖新快照。
3. 用 CTP API stub 分别覆盖“成功终态但无行”与“终态 ErrorID 非零”，并证明前者为 `SUCCESS + empty`、后者为 `FAILED`，不能再落为同一个 `NULL` 回调。其他 provider 按各自 SDK 的查询结束和错误语义分别适配和验证，不能用 CTP 的结论代替。
4. 真实供应商/SDK 语义仍属外部验收：CTP、CTPMini、CTPOpt、Femas、HuaX、XTP、XTPXAlgo 等需核对终态错误、超时与是否可能返回部分集合；OES 的 `queryOrders()` 返回值及无记录时游标终结方式需要其正式 SDK 文档、样例或供应商确认。取得外部证据前仅能记录本地 fake/stub 结果，provider 实盘验收保持 `NOT_RUN`。

### 6.4 交易通知关闭还必须排空执行器异步工作

本轮生命周期复核确认，`TraderAdapter` 的 stop/wait 屏障只等待 adapter 到 sink 的同步回调返回。Local、Diff、Arbi 收到订单、成交、持仓、行情或通道事件后，还可能把工作放入按合约运行的队列和线程池；同步 sink 回调退出不表示这些后续工作已经结束。若此时释放交易 API，已排队或正在执行的插件任务仍可能通过保留的 `TraderAdapter` 指针调用下单、撤单或订单查询。只排空 adapter 广播、仅调用 `pool->wait()` 于执行器析构时，或清空队列后继续释放 API，都不能证明这个路径安全；清队列还可能丢失尚未处理的账务及状态事件。

因此当前 runner 关闭草稿仍为 **IN_PROGRESS / NOT_RUN**，不能按已有的 adapter barrier 定向测试视为完成。关闭路径需保持 adapter、执行器、策略 context 和插件对象存活，并按可证明的顺序执行：先禁止新的配置及外部输入；向所有 trader adapter 发出非阻塞 stop 请求；停止 parser、行情和其他外部 producer，同时保留 sink owner；从非回调控制线程等待 adapter 通知排空；再向 Local、Diff、Arbi 及其他接收 adapter 通知的执行器发出 stop/drain 请求，禁止新任务入队并等待已接受任务完成；确认所有同步及异步工作都不再调用 trader API 后才可释放 API。若 wait 从该 adapter 的 sink callback 或执行器 worker 自身调用，必须立即报告未完成并保留资源，交由控制线程继续；不得在 callback 栈中 join 自己，也不得将尚未完成的关闭报告为成功。

执行器 drain 接口必须覆盖真实事件链的后代任务，而非只等待同步 sink 函数。stop 与 drain 之间需有原子 ingress gate，避免并发 `schedule()` 在 drain 检查后再次提交工作；停止时须保留并处理已接收的订单/成交/委托/持仓状态事件，不能把清空队列当作 drain。配置失败及重复配置也需闭合：若存在旧 engine、executer manager 或 sink owner，要么拒绝再次配置并保持原运行时有效，要么按同一完整屏障停止、排空并销毁旧 owners 后再替换 adapter，不能仅释放 API 或把 engine 指针设空。

验收至少包括：

1. 用真实 adapter sink 回调触发 Local、Diff、Arbi 的异步 drain，在任务被 gate 阻塞时关闭；证明 API 未释放、执行器/context/adapter 仍有效，释放 gate 后已接受任务完成且 API 才释放。
2. 并发提交新的行情、委托、成交、持仓和通道事件于 stop/drain 边界；证明 ingress gate 关闭后的事件被明确拒绝或按合同交付，关闭前已接受的账务事件没有丢失，drain 完成后没有任何 API 调用。
3. 覆盖 callback worker 内重入 release、控制线程二次完成关闭、多 adapter 先 request-all 后 wait-all、parser 停止、正常退出、初始化/配置失败回滚及重复 config；以超时和状态断言确认没有自等待、锁反转、悬挂 owner 或释放后的裸指针访问。
4. 对插件执行单元自有线程，新增可验证的版本化 `quiesce/stop-and-join` 合同及 fake 插件测试。旧插件没有该合同且宿主无法证明其后台任务已静止时，相关 API 和 owner 必须 fail-closed 保留，不能因 `destroy()` 或 adapter barrier 已返回就推断插件线程退出。
5. 适配器到 sink 的屏障不能证明交易 API 插件释放后不再调用 `ITraderSpi`，parser 插件释放后也不保证 parser 回调排空。需按具体插件版本取得 shutdown/unregister/join 契约，或以带可控迟到回调的 fake 明确覆盖宿主的防护策略；供应商合同缺失时保持外部验收 `NOT_RUN`。

以上是由下游异步队列及 runner 生命周期复核发现的新产品风险和验收要求，runner 接线、执行器 drain、插件 quiesce 协议及相关测试尚未完成；此项状态保持 **IN_PROGRESS / NOT_RUN**，不改变执行清单计数，也不能由单个 adapter 的 13/13 或 7/7 测试外推到完整关闭链。

### 6.5 UFT runner 与延迟工具的关闭生命周期仍未验收

UFT 使用独立的 `WtUftCore::TraderAdapter`、`WtUftRunner` 和 `UftLatencyTool`，不能将普通 `WtCore` runner 的屏障结果直接外推到 UFT。近期复审发现下列关闭与状态风险；相关修改即使通过适配器局部测试，仍不能代表 runner 生命周期已安全：

1. **策略回调可能在 ticker 线程内重入 shutdown，造成线程自 join。** `WtUftEngine::stop()` 会停止 ticker 并 join 工作线程；若策略回调由该 ticker 线程调用 `shutdown()`，同步 stop 会尝试 join 当前线程。关闭入口必须先识别当前是否位于 ticker/策略回调线程；回调内只发出非阻塞 stop 请求并返回未完成状态，由外部控制线程完成 join 和资源释放。不得在 callback 栈中销毁 runner 或 engine。
2. **`UftLatencyTool::run()` 与 shutdown 未由一个生命周期状态保护。** 只保护 parser simulation 的局部标志不足以序列化整个 run 启动和 teardown。当前全局 `theParser` 为裸指针，run 可以在读取后被 shutdown 置空，随后解引用；shutdown 也可能与 parser/trader/engine 的 run 并发。需用同一生命周期锁或 operation lease 覆盖整个 run 流程，并在锁内捕获有明确所有权的 parser 引用；shutdown 等待运行操作结束，callback/worker 自身不能等待自己。
3. **共享参数 watcher 可能在 runner 销毁后访问 engine。** `ShareManager` worker 使用全局 runner/engine 指针处理参数更新；仅销毁 UFT engine 或 runner 不会自动停止该 watcher。配置了共享域时，shutdown 必须先禁止新的 watcher 工作，再 stop-and-join watcher 并清除 engine 绑定，随后才允许释放 engine/context。未启用共享域时不应误触发不相关 watcher。
4. **配置失败和重复配置没有形成 fail-closed 生命周期。** `WtUftRunner::config()` 可能在 parser/trader 初始化失败时仍返回成功，`initTraders()` 也需要逐项传播 adapter 初始化和 manager 注册失败。重复 config 或 shutdown 后再次 config 可能覆盖旧配置、遗留旧 context/adapter，或在 `_shutdown_complete` 状态下重新启动 ticker。应明确 runner 为 one-shot 并拒绝重复/关闭后配置；或实现完整的旧 runtime drain、owner 清理和状态重置后再允许重新配置。任何部分初始化失败都须阻止 `run()`，并按可证明的顺序回滚已创建资源。

UFT 的关闭路径应有真实并发验收，而不只检查函数返回值：在策略 ticker callback 中重入 shutdown 时，确认不会自 join、API 与 context 保持有效且状态明确为 pending；由控制线程再次 shutdown 后才 join 并释放。对 `UftLatencyTool` 同时覆盖 run 与 shutdown 竞争及 parser 指针失效窗口；对共享域覆盖 watcher 被停止并 join、engine 解绑发生在销毁之前。配置验收需注入 `init`/`addAdapter` 失败并证明 config 返回失败且 run 不启动，还要验证重复 config 和 shutdown 后 reconfig 的明确拒绝路径。Ready 注册顺序应在 context 已登记后再 addSink，并使用已 READY 的适配器让测试实际观察到 READY 回调中的 owner。

本节状态保持 **IN_PROGRESS / NOT_RUN**。UFT adapter 的 ready/lost 顺序、在途调用 drain 和生命周期 gate 的定向测试，不能证明 ticker、共享 watcher、runner config 或 latency run/shutdown 已安全；UFT runner/latency 的新关闭测试仍需编译并运行。adapter barrier 也不能证明 vendor API `release()` 后不存在异步迟到的 `ITraderSpi` 回调；旧 SPI 缺少会话 token 时，重连后迟到的旧登录响应还依赖 provider 的顺序保证。未取得 provider 关闭及会话回报合同前，实盘/供应商生命周期验收维持 `NOT_RUN`。
