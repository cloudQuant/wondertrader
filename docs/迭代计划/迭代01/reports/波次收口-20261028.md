## R27 复核 + 一项需要 owner 评审的取缝技术

主控独立重跑 `tools/lane_gate.sh CoverageTests_t_ParserXTP`：
**枚举 61 条 ⇒ 59 PASS / 2 FAIL / 0 CRASH**（lane 自述 62 枚举含 1 条 `NORUN`，
那条是 `DISABLED_` 挂 suite 名的行，我已把枚举过滤改成 `grep -vE '(^|\.)DISABLED_'`，
所以两边数字在这里对得上）。R27 自述的 `ParserXTP.cpp` 未覆盖 266→45 与「2 条 FAIL 属兄弟 lane T1」
均与实测一致：那两条红在 `t_ParserXTP/cov_parserxtp_spi_test.cpp:405 / :525`，是 T1 的用例，R27 没代改。

**需要评审的技术**：XTP 在本机**没有 macOS 版厂商库**（`src/API/XTP2.2.32.2/` 只有 linux/x64/x86），
`ParserXTP::init()` L131 必然对 NULL 的 `m_pUserAPI` 解引用。R27 为了进 `init()`/`DoLogin()` 的内部状态，
用了一份**从 `ParserXTP.h` 抄来的类布局镜像**灌进那 9 个字段，再配本地 FakeApi，
并写 `static_assert(sizeof==)` + SetUp 里 11 个成员锚点断言来证明镜像与真头一致。
它只走公开入口，没有用 `#define private public`，也没有改产品代码。

我的判断（不是结论，交给评审）：
- 好处：拿到 221 行真实覆盖，且锚点断言让「镜像漂移」会当场失败而不是静默跑偏；
- 风险：跨翻译单元的类型双关在 C++ 里没有标准保证，若将来 `ParserXTP.h` 改了成员顺序而锚点没覆盖到新字段，
  用例可能**继续绿但在读脏内存**；这类用例的结论不能当作产品行为证据。
- 处置：本迭代不删它（它换来的是真实覆盖），但已把「布局镜像」写进派工禁止项，
  后续 lane 一律不准再用；要不要保留这 3 个 `t27_` 文件请评审定。删除成本很低：只删 `t_ParserXTP/t27_*` 三个文件即可，其它用例不依赖它。
