## A-04 p08/p03 的 comminfo 返回 NULL（4+ 条 FAIL，同族还牵连多条「数值为 0」）—— ③夹具键形不对

证据链（全部本轮实读，不是推测）：
1. 用例查的合约串：`p08_uft_order_position_test.cpp:87` → `static const char* kFut = "SHFE.rb2405";`（**两段式**）

   即 `SHFE.rb`
3. 产品查表路径：`WtBtCore/UftMocker.cpp:972-975` `stra_get_comminfo → _replayer->get_commodity_info(stdCode)`；
   `HisDataReplayer.cpp:2915-2919` 先 `CodeHelper::extractStdCode(stdCode,&_hot_mgr)` 再 `_bd_mgr.getCommodity(exchg, product)`；
   `Share/CodeHelper.hpp:610-616` 对**两段式**串把「点号后的整段」当 product ⇒ `product = "rb2405"`

`CodeHelper.hpp:601-607` 的注释写明了正确形：分月合约要三段（`CFFEX.IF.2112` 那种），
所以要么把夹具注册键改成 `SHFE.rb2405`，要么用例统一改用 `SHFE.rb.2405` 形态（后者更贴近产品真实用法）。

我顺手量了一下「两段式带月份」字符串在测试里的分布：45 个文件、369 处，另有 232 处三段式；

因为它们的取数路径**不经过** `extractStdCode`→`getCommodity`。所以**不能**做全局串形替换，

## A-05 `P03SelTradePath.*` 的浮点与算术笔误 —— ②用例侧改正（含一处期望值实质改正）

p03 的 Sel 族两条 FAIL 拆成两种性质，不能一起处理：

1. **累加残差**：`1.2` vs `1.1999999999999744`、`-0.2` vs `-0.20000000000000018`、`6.6` 同形。
   `EXPECT_DOUBLE_EQ` 默认 4ULP，比业务累加残差更紧 ⇒ 正常结果被判失败。
   处置：这 5 处改为 `EXPECT_NEAR(期望, 实际, 1e-9)`，**比较值一字未动**；
   1e-9 比最小可检查金额量（一手一分钱，1e-2）小 7 个数量级，真实口径错误仍会被证伪。
2. **期望值本身算错**：`p03_sel_trade_path_test.cpp:168` 期望 `_dynprofit == 4.0`，
   但它自己前一步喂的是 `proc_tick(code, 10.06, 10.04)` ⇒ 现价 10.04，剩余 60 手开仓 10.01
   ⇒ `60*(10.04-10.01)=1.8`。原期望 4.0 既不对应这个价（10.06 时才是 3.0），也不是「等比缩放」的算法。
   产品给的 1.8 与输入一致 ⇒ 期望值 4.0 改为 **1.8**，并在用例里写清算式。
   这一条**不是**放宽：改的错误的期望值本身，改完仍是精确相等断言（后面再包一层 NEAR 是因为 1.8 也有 4e-14 残差）。

**没有把任何一条实质分歧（差 2.2）伪装成容差问题** —— 这正是第 2 条与第 1 条的区别所在。

## A-10 「只过 -fsyntax-only 的 lane」会整族交付 gtest 运行期拒绝的用例（已修 2 处，实测 +12 PASS、0 回归）

## A-11 度量本身的两处假绿（已修，含控件验证）

在补跑 lane 交付时顺手审了 runner 的判决口径，发现**两处会把「什么都没跑」读成绿**：

**1）`DISABLED_` 挂在 suite 名上时没被滤掉。**
枚举过滤原来只写 `grep -v '\.DISABLED_'`，这只覆盖 `Suite.DISABLED_Case`；
而 `TEST_F(DISABLED_P01CtaCrashClass, …)` 这种把前缀挂在 suite 上的写法，id 形如
`DISABLED_P01CtaCrashClass.unchecked_null_pointers_segfault`，`.DISABLED_` 匹配不到 ⇒ 被枚举、被 xargs 跑，
gtest 自己跳过（日志里是 `Running 0 tests from 0 test suites`），进程退出码 0 ⇒
**旧 corpus 记成 PASS**。实测残留量（官方 corpus 日志扫描）：11 条日志是 0 tests ran，
按新滤法重算枚举数：wtcore 329→328、uftcore 88→80、主目标 705→699（共 15 条幽灵行）。
改法：`grep -vE '(^|\.)DISABLED_'`，并用「新滤法结果里再 grep DISABLED_ = 0」做反控件。

**2）退出码 0 不等于跑过用例。**
`case_runner.sh` 原来 `if [ $rc -eq 0 ] → PASS`。除了上面那种，`--gtest_filter` 打空（例如我今晚把
suite 行的尾点没去掉、拼成 `Suite..Case`）也是 exit 0 ⇒ 329 条全绿也不会露馅。
现在判 PASS 需要**同时**满足：`rc==0` 且日志里有 `^\[  PASSED  \] [1-9][0-9]* test`；
否则记 **NORUN**。第一版我写成 `[0-9]+ test`，控件立刻证明它是错的（`[  PASSED  ] 0 tests.` 照样匹配），
已改成 `[1-9][0-9]*`。

**新增判决类 `SUITECONF`**（A-10 那族）：日志含 `must use the same test fixture` 时单独成类，
不再混进 FAIL 诱导读用例的人去改断言。

**控件（7 个臂，逐个独立干净 rc 目录，脚本 `/tmp/ctrl/fakebin`）**：
pass→PASS、norun→NORUN、suiteconf→SUITECONF、fail→FAIL(rc=1)、crash→CRASH(rc=139,sig=11)；
真二进制正控件 `R21LmdbKeys.ReverseEndian16SwapsTheTwoBytes`→PASS；
真二进制负控件 `NoSuchSuite.NoSuchCase`→NORUN。**七个臂全部符合预期。**

**`coverage.sh` 的非通过合计改成恒等式** `nonpass = rows − PASS`，不再 `FAIL+CRASH+HANG+RUNDIR` 相加 ——
否则新增判决类别一旦漏加就静默算通过（这正是本轮加 SUITECONF/NORUN 时会踩的坑）。

**对历史数字的影响（要把口径变化说清，别让读者以为用例数掉了）**：
下一轮全量度量的「枚举数/PASS 数」会比同一份代码在旧口径下少 15 条左右，因为幽灵 DISABLED-suite 行不再进分母；
非通过数不会因此增加（它们本来就不是真通过）。派工令里给 lane 的枚举片段以 `coverage.sh` 现在的写法为准。
