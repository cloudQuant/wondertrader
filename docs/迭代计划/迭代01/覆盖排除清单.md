### 2.1 2026-10-27 实测更正：EX-10～EX-12 默认「可测」，不得预先排除

先前判断「收发族要厂商 SDK 环境才能测」**不成立**，证据：

- 厂商头与静态库本来就在仓库里（`src/API/CTP6.6.9`、`CTP6.3.15`、`Femas3.02`、`AtpTradeApi` …），
  顶层构建**已经在编译并插桩**这些目录——它们在覆盖率分母里有行数（`TraderCTP` 1179、`CTPLoader` 831 等），只是覆盖为 0。
- harness 已按「一个目录 = 一个测试目标」补齐（`CoverageTests_t_<模块>`，从磁盘派生 27 个目录）：
  每个目录各自定义 `extern "C"` 的 `createParser/createTrader/deleteParser/deleteTrader`，
  两个目录同进一个二进制必然 duplicate symbol，所以必须分目标——这是形状约束，不是可测性约束。
- 探针实测：`src/TestUnits/coverage/t_TraderMocker/seam_tradermocker_test.cpp` 仅 2 条用例
  （构造 + `isConnected`/`release` + `makeEntrustID`），就让 `src/TraderMocker/TraderMocker.cpp`
  的 984 行里进了 **37 行覆盖**（该模块此前 0%）。

因此 EX-10～EX-12 的处理顺序改为：**先按 T01–T07 简报逐族试测**，只有确实需要活体柜台/网络的分支
才逐项申请排除，并在申请里附「已尝试的驱动方式与失败证据」。

### 2.2 可编译性实测（口径＝构建系统自身命令，不是自造 flags）

用 `ninja -C build-cov -t commands <对象>` 取每个收发/装载模块在真实构建里的编译命令，
把 `-o … -c` 换成 `-fsyntax-only` 逐个执行：

- 磁盘上有对象的收发/装载模块 **18 个**：`CTPLoader CTPOptLoader ParserCTP ParserCTPMini
  ParserCTPOpt ParserFemas ParserShm ParserUDP ParserXTP ParserXeleSkt TraderCTP TraderCTPMini
  TraderCTPOpt TraderDumper TraderFemas TraderMocker TraderXTP TraderYD`
- 结果 **18/18 可编译、0 失败** → 这一族的行数是真能靠单测推进的，不构成排除理由。
- 另外 9 个收发目录（`ParserHuaX ParserOES ParserYD TraderATP TraderDD TraderHTS TraderHuaX
  TraderOES TraderXTPXAlgo`）**没有对象文件**：不在顶层 `ADD_SUBDIRECTORY`，且部分缺厂商头
  （实测 `mds_api/mds_api.h`、`trade/atp_trade_types.h`、`API/FixApi/include/FixApi.h`、
  `API/HTS5.2.43.0/include/secitpdk.h`、`oes_api/oes_async_api.h` 全部 file not found）。
  它们不进构建也就不进 llvm-cov 分母；要覆盖它们得先做「是否纳入构建」的产品决策 → 评审项，
  不能由测试侧代为宣布排除。
- 反面教训（记此以免重犯）：同一批目录我用自造 flags 曾测出「22 个不可编译」，差别只在
  少了 `-std=gnu++17`/`-isystem`、多了 `-I.`/`-IAPI`。可编译性的判定口径必须来自构建系统本身。

### 2.3 带 `main()` 的可执行体：编译期重命名入口，已跑通并拿到覆盖

通路：目标的生产 TU 加 `COMPILE_DEFINITIONS main=wt_coverage_main_<模块小写>`，
测试按受控 argv 调用该入口，与 gtest 自己的 `main` 同链进一个测试二进制。
不改产品代码，也不需要先做 OBJECT 化决策。

实测证据（`CoverageTests_m_LoaderRunner` + `m_LoaderRunner/seam_loader_runner_test.cpp`）：
- 走 `--help` 分支（`LoaderRunner.cpp` 该分支 `return 0`，可终止、不阻塞），进程 exit=0；
- `llvm-cov report`：`LoaderRunner/LoaderRunner.cpp` **44 行里覆盖 28 行（63.64%）**，此前该模块 0%。

两条失败教训记此以免重犯：
① 第一版宏值写成 `${mod}_coverage_main`（大写开头）而测试声明是小写，直到链接期才报
   `Undefined symbols: loader_runner_coverage_main` —— 跨侧符号名必须单点定义。
② 判定「哪些模块可编译」必须用构建系统自身的命令；自造 flags 曾把 18 个正常模块误判成 22 个失败。

结论修正（我先前两处判断都不成立）：95% 的三个块 —— A 在建收发族 11,707 行、
B 带 main 的 1,524 行、C 其余 54,967 行 —— **都不需要产品改动就能进入测试射程**。
只有 §2.2 那 9 个「不在构建且缺厂商头」的目录需要先做构建范围决策，而它们本来也不在 llvm-cov 分母内。

### 2.4 2026-10-27 收发族波次前置：Boost 双版本 ABI 与逐模块门禁 flags

两件都在测试侧解决，**不改产品代码**，但都属于评审需要知道的口径：

1. **头/库版本一致性**（详见 `bugs/l00_build_graph.md` BUG-L00-006）：本机同时存在
   `/usr/local/include/boost`＝1.81 与 Homebrew＝1.88，链接走 `-L/opt/homebrew/lib`。
   测试目标因被链接目标上传来 `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES` 而多出一处
   `-isystem /opt/homebrew/include`；clang 对同一路径串去重且 `-isystem` 形态吞掉 `-I`，
   于是测试 TU 用 1.81 头编、链 1.88 库 → `CoverageTests_dtcore` 链接失败。
   解法：`src/TestUnits/coverage/CMakeLists.txt` 在构建目录建
   `cov_boost_include/boost -> ${Boost_INCLUDE_DIR}/boost` 符号链接并置于 `-I` 链首，
   只作用于测试目标。实测该目标由 exit=1 → exit=0。
   三臂对照（同一份 `boost/version.hpp`）：只有 `-I` → 1_88；只有 `-isystem` → 1_81；
   两者同时给（无论先后）→ 1_81。
2. **逐模块真实门禁 flags**：`tools/gen_gate_flags.py` 从 `ninja -t commands <对象>` 取每个
   收发模块测试对象在真实构建里的完整命令，生成 `tools/gate_flags/t_<模块>.sh`
   （`-fsyntax-only` + 项目原本的 `-Werror`）。本轮实测 **18/18 生成成功**，
   且正面/反面控件都验过：占位用例 `exit=0`、故意坏头文件 `exit=1`。
   lane 一律用它，不再自造 flags（§2.2 的教训）。
3. **第六波派工范围**：§2.2 那 18 个「在构建里」的收发目录按磁盘源码行数均衡分成 6 路
   （每路 2,898–3,402 行，`wc -l` 实测合计 18,443 行）；
   另外 9 个目录（`ParserHuaX ParserOES ParserYD TraderATP TraderDD TraderHTS TraderHuaX TraderOES TraderXTPXAlgo`）
   在派工文本里被**点名为禁止触碰**，避免 lane 去「顺手补齐」它们不存在的厂商头。

4. **厂商静态库按模块自动登记**：18 个 t_ 目标建起来后实测只有 3 个链接失败
   （`CoverageTests_t_CTPLoader / t_ParserCTP / t_TraderCTP`，未定义符号是
   `CThostFtdcTraderApi::CreateFtdcTraderApi` 与 `CThostFtdcMdApi::CreateFtdcMdApi`），
   另外 15 个收发目录不引厂商 `.a`。规则不手敲清单，而是从各模块自己的
   `CMakeLists.txt` 里正则抽 `API/...*.a` 再拼接 `${CMAKE_SOURCE_DIR}`，
   本机不存在的（产品文件里并列的 WIN32/Linux 分支）只 STATUS 跳过、不把配置弄死。
   实测双向对照：3 个 CTP 族目标的链接命令都带上各自归档且 `exit=0`；
   `t_TraderXTP`、`t_ParserUDP` 命令里归档数为 0（没有误挂）。
   全量 `cmake --build build-cov -- -k 0` 由 exit=1 → **exit=0，0 个 FAILED**，
   测试可执行文件数 16 → **34**。

## 5. 分母口径实测（2026-10-28，报表与构建系统双向核对）

「第一方覆盖率」这一句话必须先说清分母是什么。本轮实测（口径 = `xcrun llvm-cov report` 原始输出的
`src/**/*.cpp` 行，不是报表正文的未覆盖清单 —— 报表正文只列 `missed>0` 的文件，

|---|---|---|---|---|
| 已插桩、进入分母 | 803 个文件行（含头文件） | 报表合计 `lines=68373` | **是** | — |
| 厂商 SDK 本机缺失，产品 CMake 根本没有 `ADD_SUBDIRECTORY` | 9 | 9,551 | **否（连 .o 都编不出）** | 评审：这 9 个收发适配层要不要计入 95% 的分母？要的话必须在装了 SDK 的机器/Linux CI 上测 |
| 内嵌第三方（`WTSUtils/yamlcpp`、`StackTracer`、`lmdb`、`zstdlib`） | 31 | 7,057 | 否（`EXCLUDED` 口径排除） | 确认口径即可 |

- 「有没有进分母」：把 `coverage_report.py:find_objects(build)` 得到的 369 个 `-object` 逐个喂
