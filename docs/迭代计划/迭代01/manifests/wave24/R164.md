## 1. 关键发现与运行约束

- `R154UdpCasterTest` 的三条 active 用例在最新一轮全部 `CRASH(rc=139,sig=11)`：崩溃点在
  `~UDPCaster` 销毁 `m_sktSubscribe` 时的 `kqueue_reactor::deregister_descriptor`。
  成员声明顺序使 `m_ioservice`（`UDPCaster.h:96`）先于 socket 容器（`UDPCaster.h:88-95`）析构，
  active init 只要建过 socket，对象析构必崩（BUG-R164-001，附系统崩溃报告取证）。
  因此 R154 声称打的 `62-143/145-220/288-400` 实际都停在 0，UDPCaster.cpp 仍是 70/476。
- 本 lane 的 UDP 用例改用 `r164::LeakyCaster`：只 `stop()` join 产品线程，**不 delete**
  UDPCaster。每个用例由 `case_runner` 单独进程执行，进程退出回收；这样既覆盖 socket
  相关行，又绕开已登记的析构缺陷。`DISABLED_ActiveStartThenDestructorCrashes` 保留
  缺陷触发占位，不放宽任何断言。
- 网络：只 bind `127.0.0.1`/`0.0.0.0` 的临时端口，客户端只向 `127.0.0.1` 发包；
  组播地址只用于 `addMRecver` 的 `join_group`，广播用例不配置 multicast，
  `do_broadcast` 从不向组播列表发送。
- 状态机：`run()` 按墙上时钟 1 秒节流，墙钟只作等待上限；目标状态由 auction/节假日
  模板保证与具体 HHMM 无关。非节假日序列周末跳过；节假日序列周末/工作日都成立。
- 语法门禁: `gate_flags/CoverageTests_dtcore.sh` 对 3 个 `.cpp` 均为 0 error
  （先以同目录 `.cpp` 符号链接过门禁，再改名，避免 `.tmp` 被 clang 当 linker 输入）。

## 3. 未覆盖行及原因

### UDPCaster.cpp

- 114-117：`start()` 的 socket 构造 catch。占用端口可触发，但紧接着 `do_receive()` 对 NULL
  `m_sktSubscribe` 解引用（BUG-R5-001），用例会崩，不启用。
- 150-154：`do_receive` 的 `ec` 分支；socket 关闭/取消只能由产品内部触发，公开 API 无接缝。
- 184-199：订阅命中合约且 `getCurTick != NULL` 的回包段。`DataManager::getCurTick` 在
  `_writer == NULL` 时直接返回 NULL（DataManager.cpp:200-206），writer 无公开注入点
  （R44-005 同族接缝）；只能覆盖到 L180-182 的 continue。
- 195-199、210-214：回包 `async_send_to` 的 `ec` 分支；回环发送成功，无错误注入点。
- 254-258、265：`addMRecver` join_group 成功后的分桶/return true。macOS 上是否成功取决于
  本机组播接口；用例已调用合法组地址且只断言“不抛异常”，不把环境差异写成失败。
- 321-322：`castData._data == NULL` 的 break。四个公开 broadcast 都在入口拒绝 NULL，
  队列里不可能出现空对象。
- 360-363：未知 `dataType` 的 break。公开包装只传 0x200/0x201/0x202/0x203。
- 371-376：raw 单播 `send_to` 的 `ec` 日志；回环接收方常驻，发送不失败。
- 379-388：`m_listRawGroup` 的组播发送循环；需 type=2 的合法组地址并向 239.x 发送，
  违反“不访问外网”，留白。
- 402-416：`handle_send_broad/handle_send_multi` 是 dead code（BUG-R5-004）。
- 析构路径：`~UDPCaster` 必崩，见 BUG-R164-001；本 lane 以不 delete 规避，未覆盖析构体本身。

### StateMonitor.cpp

- 341-345：`SS_RECEIVING -> SS_CLOSED`。需要 `offTime` 在两轮之间跨过 close；run 的轮次
  间隔固定 1 秒而 HHMM 只在分钟边界变化，同一模板无法既先进 RECEIVING 又确定性收盘。
- 348-369 的 PAUSED/市场收盘子分支：`SS_RECEIVING -> PAUSED` 需同一会话在两轮间离开交易
  区间；`offTime >= getCloseTime` 需 `isInSections` 为真却超过市场收盘，二者由 WTSSessionInfo
  的区间定义互斥。
- 390-398、413-423：`SS_PAUSED` 的节假日判断与 `PAUSED->RECEIVING/Holiday`。首轮进入
  PAUSED 的前提（非节假日且区间不覆盖当前时间）在次轮同一分钟内不翻转。
- 445-449：`isSessionProceeded()==true` 直接转 SS_PROCED。`DataManager` 无 writer 时恒为
  false，writer 无公开注入点（BUG-R44-005 同族）。
- 491-496：本 lane 的节假日用例已让有品种的 Holiday 进入 489-503 条件；若报告仍标 0，
  是复合条件的分支归并口径（左侧短路/右侧求值按列统计），不是未执行该状态分支。

### 周末与跨日

- 非节假日序列在周末 `isTradingDate` 恒 false，按 R154 惯例 `GTEST_SKIP`；
  节假日序列周末/工作日都保持 Holiday。23:58 之后初始化会跨过 inittime，跳过。
