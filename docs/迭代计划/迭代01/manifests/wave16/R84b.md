## 7. 留白面及原因

1. **`StateMonitor::run()` 整个状态机（`StateMonitor.cpp:145-530`，约 385 行）**：切换输入只有 `TimeUtils::getCurDate()/getCurMin()` 与 `StdThread` 内 `sleep_for(2ms)`，没有 `checkOnce(curDate, curMin)` 接缝；任务令明确禁止启动 run() 墙钟线程。既有 `r5_state_monitor_bdt_test.cpp::DISABLED_StateMachineAdvanceNeedsInjectableClockSeam` 与 BUG-R5-002 已登记。
2. **`stop()` 的 join 段（`StateMonitor.cpp:541-542`）**：`_thrd` 只有在 `run()` 之后才非空；不启动线程就无法执行 `join()`。`stop()` 未 run 的守卫已由 R44 覆盖。
3. **`StateMonitor.h` 的四个 inline 方法体（约 41 行）**：这是本 lane 重点核实后的结构性留白，不是没喂输入：
   - `coverage_report.py` 只统计产品对象，`/TestUnits/` 下的测试 TU 被排除；测试里直接调用 `StateInfo::isInSections` / `isInState` 只会在测试 TU 里生成一份内联副本，不计入产品覆盖率。
   - 产品对象 `StateMonitor.cpp.o` 只实例化 `isInSections` 与 `isAllInState`，调用点全部在 `run()` 内（L263/308/353/412/455/522），因此不起 run() 就恒为 0。
   - `isAnyInState` 在全仓库产品代码中**没有任何调用点**，产品对象根本不发射该函数；即使起 run() 也无法覆盖。
   - `isInState` 的唯一产品调用点是 `DataManager.cpp:244`；`DataManager.cpp.o` 的该调用行已执行，但头文件内联体的计数仍为 0（测试二进制链接时选中了测试 TU 的内联副本，其 profile 被报表排除）。
   - 证据：`llvm-cov report -object .../StateMonitor.cpp.o` 显示 `StateMonitor.h` 21 regions / 20 missed、51 lines / 43 missed；R18 的三条 `isInSections` 直接用例也没有让该数字变化。
   - 结论：要让 header 行数下降，需要产品侧改动（把 inline 体移到 `.cpp` 并显式实例化，或提供 `checkOnce` 之类可从产品对象驱动的入口）。本迭代不改生产代码，故只登记、不硬凑。
4. **`SS_Holiday` 状态切换**：只能在 `run()` 内由节假日/无品种分支置入；公有 API 没有状态注入入口，查询侧的 holiday 分支不可达。
5. **`_dt_mgr->transHisData` / `isSessionProceeded` 的收盘作业路径**：同样只在 `run()` 的 `SS_CLOSED` 分支里调用，且需要真实 DataManager 写手；本 lane 不启动状态机。
