## BUG-R69-001 WTSHotMgr::getHotTags 用函数内 static 缓存标签集，后装载的自定义规则被遮蔽

- 状态: 直接调用的静态缓存问题已由源码与定向用例确认；runner 重载影响未端到端验证
- 严重级别: 中（主要影响同进程后续规则加载；初次配置加载时规则先于首次查询装入）
- 模块/文件: `src/WTSTools/WTSHotMgr.cpp:148-159`；消费点 `src/WtPorter/WtRtRunner.cpp:562-580`
- 现象: `getHotTags()` 内部是
  `static std::vector<std::string> ayTags; if (ayTags.empty()) { for (auto& v : m_mapCustCodes) ... }`。
  该 vector 是**进程级**的，只在为空时重填，且重填源是「当次调用所属的 WTSHotMgr 实例」：
  - 第一次调用把 A 实例的标签集冻进 static；
  - 之后 B 实例 `loadCustomRules()` 新增的标签不会进入 static，`getHotTags()` 仍返回 A 的集合；
  - 若 A 的 map 为空，则 static 保持空，下一次调用又会从 B 重填——结果依赖「谁先调」。
  `WtRtRunner::config()` 会消费这个返回值做主力代码回填（`:562-580`）；后续配置受旧标签集
  影响是从源码调用关系推导，R69 没有端到端验证合约的 hotCode 是否遗漏。
- 相关测试: `r69_porter_runner_config_test.cpp:R69PorterRunnerConfig.DISABLED_HotTagsStaticCacheHidesRulesLoadedLater`
  （默认禁用；本次显式运行后在 `EXPECT_NE(R69LATE, tags.end())` 失败，确认直接调用序列
  会丢失后装载标签；尚未证明 runner 热重载端到端行为；测试源码注释仍标为 R69-002，需同步修正）
- 输入:
  ```
  WTSHotMgr hot;
  hot.loadCustomRules("R69FIRST", "hot.json");
  hot.getHotTags();                     // 冻结 {R69FIRST}
  hot.loadCustomRules("R69LATE", "hot.json");
  hot.getHotTags();                     // 期望含 R69LATE
  ```
- 期望: 每次调用返回当前 `m_mapCustCodes` 的标签集合，或在 `loadCustomRules()` 后使缓存失效。
- 实际: 在同一进程已填充 static 后，后续调用仍返回第一次生成的集合，`R69LATE` 未出现；
  直接用例本次观察到该断言失败。
- 复现步骤:
  1. 用任意 `WTSHotMgr` 实例先装载一个标签并调用一次 `getHotTags()`；
  2. 再装载第二个标签；
  3. 再调用 `getHotTags()`，观察第二个标签缺失。
- 影响: 首次配置查询前完成规则装载时，当前配置可进入缓存；若同进程再次装载规则，或
  由另一 `WTSHotMgr` 实例查询，已填充的进程级 static 可能继续提供旧集合。runner 的
  `config()` 消费该集合，但本次未做 runner 热重载端到端验证，因此不据此断言所有后续
  主力/次主力规则均失效。
- 备注: 修复方向是按实例即时返回标签，或使用实例级缓存并在规则变更时失效；避免静态
  跨实例状态。可保留启用的直接回归用例，并补充 runner 配置可观察性测试。

## BUG-R69-003 数据管理器初始化失败未传递给 WtRtRunner::config（测试未覆盖所称缺 data）

- 状态: 两处返回值丢弃由源码确认；现有测试实际覆盖空 data 对象的无 store 情况，不是缺 data；配置必需性与运行影响待契约确认
- 严重级别: 中（当前确认配置状态可能与调用方返回值不一致；未确认运行期故障）
- 模块/文件: `src/WtPorter/WtRtRunner.cpp:587`（`initDataMgr();` 返回值未接）、
  `:884-896`（缺 `data` 时返回 false；`_data_mgr.init()` 的 bool 也未检查）和
  `src/WtCore/WtDtMgr.cpp:89-101`（`store` 缺失时 `initStore()` 返回 false）
- 现象: `config()` 在 `initEngine()` 之后无条件调用 `initDataMgr()`，不判断返回值。
  当 `data` 缺失时，`initDataMgr()` 返回 false，但 `config()` 忽略它；当 `data:{}` 存在时，
  `_data_mgr.init()` 因 `store` 缺失而返回 false，但 `initDataMgr()` 忽略内层结果、仍记录
  “Data manager initialized”并返回 true。`WtDtMgr` 默认 `_reader`/`_engine` 为 NULL；空对象
  初始化会先设置 `_engine` 再因 store 缺失留下 `_reader` 为空，而缺整个 data 段则未调用
  `init()`，两个失败状态不同。公开配置契约未明确 data/store 是否必需。
- 相关测试: `r69_porter_runner_config_test.cpp:R69PorterRunnerConfig.MissingExecuterFileAndDataSectionStillReturnTrue`
  （本次通过；测试名/注释声称 data 段缺失，但 helper `tail()` 实际加入 `"data":{}`，
  且其中没有 `store`。源码显示此条件下 `_data_mgr.init()` 返回 false 并被
  `initDataMgr()` 吞掉；测试只观察外层 `config()` 返回 true。还同时缺 executers 文件，
  `strategies.cta` 也缺失，未隔离这些条件。）
- 测试中的实际输入（`tail()` 拼接的空 data 对象；删除 `"data":{}` 才是缺段输入）:
  ```
  {"basefiles":{}, "executers":"<不存在的文件>",
   "notifier":{"active":false}, "env":{"name":"cta"}, "data":{},
   "bspolicy":"<存在的 actions.json>"}
  ```
- 期望: 若 `data` 或其 `store` 是必需项，应向 `config()` 传播初始化失败并给出具体错误；
  若允许 no-reader 模式，应明示该模式并确保数据访问路径安全处理无 reader。
- 实际: 本次用例在空 `data:{}`、无 `store` 的配置下返回 true；源码可确认内层
  `_data_mgr.init()` false 被吞掉。缺整个 `data` 段时 `initDataMgr()` false 被 `config()`
  忽略是另一静态路径，本次没有动态运行。也没有运行该配置下的 `run()` 或数据访问，故不
  据此断言崩溃或返回空数据。
- 复现步骤:
  1. `new WtRtRunner()` 并 `init()`；
  2. 以缺 `data` 段的配置调用 `config()`，并独立确认其它配置项通过；
  3. 观测 `initDataMgr()` 返回 false 被忽略的结果。当前 R69 用例未执行这组步骤。
- 影响: 当前证据确认调用方可能拿到成功结果，而 manager 未建立 reader；是否构成配置故障
  取决于 data/store 契约。缺整个 data 段时 manager 的 `_engine` 仍为 NULL，部分 API 会访问
  它，但本次没有调用这些 API。与 BUG-R46-002 同属初始化失败未传播问题，子步骤不同。
- 备注: 修复方向是检查并传播 `_data_mgr.init()` 与 `initDataMgr()` 结果，或定义可用的无
  reader 模式。测试需分开覆盖“整个 data 缺失”和“data 存在但 store 缺失”，修正当前测试
  名称/注释并避免把两个不同状态合并成一个结果。
