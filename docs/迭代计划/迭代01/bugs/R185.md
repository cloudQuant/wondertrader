## 观察 1：WtDataReaderAD 刷新路径读取被 `std::move` 掏空的 LMDB 句柄

- 状态: 已合并（主编号 BUG-R144-002；BUG-P05-001、R4-BUG-02 为同源记录）
- 严重级别: Major（特定重复刷新输入下公开读 API 空句柄崩溃；沿用主记录 BUG-R144-002）
- 模块/文件:
  - `src/WtDataStorageAD/WtDataReaderAD.cpp:272-274`（`update_cache_from_lmdb` 无 `db == NULL` 检查）
  - `src/WtDataStorageAD/WtDataReaderAD.cpp:576-578`（`get_k_db` 命中时 `return std::move(it->second)`）
  - 调用点 `:444-456`（RT bar 越过 etime 的二次回源）、`:287-290`（同时间戳覆盖）
- 相关用例（R185 改 `DISABLED_`，输入与断言保留）:
  - `CoverageTests_adstorage` → `R172AdTest.R172ReaderADRtCacheBarAheadOfEtime`
  - `CoverageTests_adstorage` → `R172AdTest.R172ReaderADRtCacheBarPromotedToLmdb`
- 现象:
  1. `cacheBarsFromStorage` 首次打开并存入 kline DB 句柄；之后 `get_k_db` 命中时以
     `std::move(it->second)` 返回，map 槽位变空，但本次拿到的 shared pointer 仍有效。
  2. 因此某次刷新首次命中空槽之前仍可成功；只有后续再次命中同一槽位才返回空
     `WtLMDBPtr`。R172 Ahead/Promoted 的具体调用次数按其各自读取序列而定，不能推广成
     “第二次刷新必崩”。
  3. 空指针进入 `update_cache_from_lmdb` 后，`WtLMDBQuery query(*db)` 在
     `WtLMDB.hpp:107-112` 调用 `db.is_readonly()`。R185 保存的 lldb 记录报告 `this=0x0`、
     `EXC_BAD_ACCESS (address=0x10)`、rc=139；这是既有记录，不是本次复核重新运行得到的动态结果。
- 期望: `get_k_db` 命中缓存时返回 `it->second`（共享所有权副本），不要移动 map 元素；
  `update_cache_from_lmdb` 也应检查空句柄并安全返回，作为防御性处理。`get_t_db` 的键不一致
  属于另一个既有问题（BUG-P05-003），不解释本条 kline 崩溃。
- 影响: 同一 reader、同一 `(exchg, period)` 的 map 槽位被移空后再次刷新时，可能因空句柄崩溃。
  `:444-456` 与 `:287-290` 是可达的刷新路径；故障在后续查询空槽位时发生，不能说这些分支
  在公开 API 下不可达。R203 的隔离 reader 用例覆盖了 `:450-456` / `:459-461` 路径，
  但不覆盖同一 reader 上重复命中已移空槽位的情形。
- 交叉引用: `bugs/R144.md` BUG-R144-002（同一根因、同一崩溃栈）、
  `bugs/p05_datastorage2.md` BUG-P05-001、`bugs/R4_adstorage.md` R4-BUG-02。
- 备注: R185 manifest 记录修复前 profdata 中 `:290`、`:451-455` 计数为 0；零计数只反映
  当时的 profile 结果，不证明分支在公开 API 下不可达，也不是缺陷已修复的证据。产品修复后应
  在同一 reader 上重复刷新，再启用 `DISABLED_` 用例复核。

## 观察 2：WtRdmDtReaderAD 首次载入把末笔覆写回首笔

- 状态: 已合并（主编号 BUG-R32-001）
- 严重级别: Blocker（沿用 BUG-R32-001：静默数据损坏；具体切片结果依赖输入窗口）
- 模块/文件: `src/WtDataStorageAD/WtRdmDtReaderAD.cpp:135-144`（`readTickSliceByRange` 的
  `isEmpty` 分支，重点 `:137` 与 `:140`）
- 相关用例（R185 改 `DISABLED_`，输入与断言保留）:
  - `CoverageTests_adstorage` → `R172AdTest.R172RdmADTickRangeStartsAtFirstTick`
- 现象: `WTSTickStruct& curTs = tickList._ticks.front();` 之后执行
  `curTs = tickList._ticks.back();`。`curTs` 是指向 `_ticks[0]` 的引用，该赋值不是重新绑定，
  而是把末笔整体复制回首笔。R185 保存的 lldb 记录报告一次加载中首末两笔为
  `[09:31:00, 09:32:00]`，加载后首项也变成 `09:32:00`；R185 manifest 另记录指定
  `[09:31,09:32]` 用例 `slice->size()==0`。这两项是历史记录，本次复核未重跑。对于该输入，
  `:232` 的首笔条件进入 if 臂，`:236-247` 的第二次 lower_bound 被跳过；不能据此说这些行对
  所有输入都不可达。
- 期望: `_ticks` 保持载入时的升序，首笔不被后续步骤改写。
- 影响: 首次加载至少两笔时，缓存首项会被末项覆盖，缓存不再满足有序性；依赖该缓存排序的
  子窗查询可能错位或漏笔。R185 记录的目标窗口返回 0 条是特定输入结果，不应外推为所有区间
  查询均返回 0，且失序后 `lower_bound` 的结果不具一般保证。
- 交叉引用: `bugs/R32_adstorage.md` BUG-R32-001（同根因，R32 已取证 3 笔变
  `[末笔, 中间笔, 末笔]`）。
- 备注: 修复方向 `:140` 改为 `const WTSTickStruct& curTs = tickList._ticks.back();`（一行）。
  修复前 `:236-247` 计数为 0，禁用不造成覆盖率回退。

## 观察 3：历史逐笔三个入口共用 `_his_ordque_map` 做装载判断（夹具已绕行）

- 状态: 已合并（主编号 BUG-R74-001；R1_wtdatastorage.md §2 为对应记录）
- 严重级别: Major（同一 reader 在同一 stdCode/交易日上只能成功装载 queue/orders/trans 之一）
- 模块/文件:
  - `src/WtDataStorage/WtRdmDtReader.cpp:701`（queue）、`:876`（orders）、`:1050`（trans）
    均以 `_his_ordque_map.find(key)` 判断是否已装载；
  - `src/WtDataStorage/WtDataReader.cpp:533`（queue）、`:690`（orders）、`:847`（trans）同型。
- 相关用例（R185 manifest 记载最终夹具 5/5 PASS；该结果不覆盖同 reader 缓存序列）:
  - `CoverageTests` → `R172RdmMixedDatesTest.R172RdmMixedActionDatesHisHftBlocks`
  - `CoverageTests` → `R172ReaderMixedDatesTest.R172ReaderMixedActionDatesHisHftSlices`
- 现象: 同一 reader、同一 `stdCode-endTDate` 上 queue 先成功后，orders/trans 的装载判断
  命中 `_his_ordque_map` 的同一键并跳过各自文件装载，随后从各自数据 map 取到空块并返回 NULL。
  R185 历史记录称补上交易所目录后出现 `que` 成功、`dtl`/`trans` 为 NULL；本次复核未重跑。
- 测试侧处理: 最终夹具为每种历史逐笔各用一个新 reader（`WtRdmDtReader::init(NULL, ...)`
  不启线程；`WtDataReader` 用同一 cfg 重新 init），未触碰产品代码，原断言全部保留。manifest
  记载的 5/5 PASS 只验证隔离 reader 下的路径，不证明同 reader 的共享缓存问题已修复或通过。
- 交叉引用: `bugs/R74.md` BUG-R74-001、`bugs/R1_wtdatastorage.md` §2（RDM 同一查错 map
  问题）；`manifests/wave25/R175.md` §1.3 对同一缺陷的复核。BUG-R100-001 是 AD
  `onMinuteEnd` 的 `endBarTime` 顺序问题，与本项无关。
- 备注: 修复方向是按 queue/orders/trans 各自的 map 做命中判断（或用 `(kind, key)` 组合键）。

## 附：两条初始 FAIL 的直接原因（测试夹具缺陷，非产品缺陷）

- R172 两个 mixed-dates 用例把历史文件写成 `his/<kind>/20240109/600000.dsb`，
  读端实际拼 `his/<kind>/SSE/20240109/600000.dsb`（RDM 见 `WtRdmDtReader.cpp:705`，
  Reader 见 `WtDataReader.cpp:546`），`StdFile::exists` 不命中 → `que/qs == NULL`。
- 两个用例最初的 `que/qs == NULL` 是缺交易所目录的夹具错误；补上
  `queue/SSE`、`orders/SSE`、`trans/SSE` 路径后，R185 又通过隔离 reader 绕开了观察 3 的
  同 reader 顺序，因此不能把最终 PASS 当作共享 map 缺陷的反证。断言未改。

## 2026-10-29 复核结论与证据边界

- 观察 1 是既有 `BUG-R144-002`（及 `BUG-P05-001`、`R4-BUG-02`）的重复记录：源码证明
  `get_k_db` 会移空 map 中的 shared pointer，R185 保存的崩溃记录与空句柄路径相符；本次未重跑。
  修复应让 kline 缓存命中返回共享所有权副本，并在刷新端防御空句柄。`get_t_db` 查存键不一致
  另属 BUG-P05-003，需独立修复与验证。
- 观察 2 是既有 `BUG-R32-001` 的重复复核：覆盖首元素的源码事实成立，R185 记录了特定窗口
  返回 0 条；其它窗口的结果需按各自输入验证。修复方向见上文，回归应覆盖多笔数据和不同窗口。
- 观察 3 与 `BUG-R74-001` 及 `bugs/R1_wtdatastorage.md` §2 同源，不另计数。文件路径少 `SSE/` 是前两条
  初始 FAIL 的测试夹具错误；在补路径后按每种类型隔离 reader 的最终 5/5 PASS 不会触发共享键
  守卫，也不验证同 reader 的 queue→orders/trans 序列。产品路径根因仍由源码确认，R185 的
  中间运行记录为历史证据，本次未重跑。修复方向为按数据类型使用各自 map 判断命中，或将类型纳入缓存键。
- 本复核只静态检查源码并核对 R185 manifest 与关联主记录，未运行 `CoverageTests`、
  `CoverageTests_adstorage` 或重新生成 profile/lldb 记录；文中所有运行结果均明确作为历史证据引用。
