## BUG-R53-001【中】WTSEntrustAction::createCancelAction 裸 new 池对象，release 读取未初始化池状态

- 状态: 待审核（静态实现缺陷确认；影响限于调用该工厂并按对象契约 release 的路径）
- 严重级别: Major（未定义行为；既有 rc=139 记录是特定构建的动态结果，不代表所有运行均稳定 SIGSEGV）
- 模块/文件: `src/Includes/WTSTradeDef.hpp:237-248`（`createCancelAction`）与 `src/Includes/WTSObject.hpp:92-111`（`WTSPoolObject::release`）
- 相关测试: `src/TestUnits/coverage/r12_headers/r12_trade_def_test.cpp` → `r12_trade_action.cancel_action_fields`（用例调用 `act->release()`；仓内既有 `build-cov/coverage/rc/CoverageTests/r12_trade_action_cancel_action_fields.rc` 记录 `CRASH(rc=139,sig=11)`，本次文档复核未重跑）；`r53_trade_def_more_test.cpp` → `DISABLED_r53_entrust_action.cancel_action_release_uses_allocated_pool`（禁用用例，未作为本次动态证据）
- 输入: `WTSEntrustAction* a = WTSEntrustAction::createCancelAction("1001", "OID01"); a->release();`
- 期望行为: `release()` 引用计数归零后把对象归还对象池，进程正常退出。
- 静态行为: `WTSEntrustAction` 派生自 `WTSPoolObject<WTSEntrustAction>`，池对象路径由 `allocate()` 初始化 `_pool/_mutex`；`createCancelAction` 却用 `new WTSEntrustAction`，基类构造只把 `_pool` 置 NULL，`_mutex` 保持未初始化。`release()` 在计数 1→0 时解引用 `_mutex` 并调用 `_pool->destroy(this)`，因此构成未定义行为。
- 复现步骤:
  1. 覆盖率构建后单跑 `CoverageTests --gtest_filter='r12_trade_action.cancel_action_fields'`；
-  2. 仓内既有 `build-cov/coverage/rc/CoverageTests/r12_trade_action_cancel_action_fields.rc` 记录 `CRASH(rc=139,sig=11)`；本次复核未重跑，记录只能证明该构建/用例进程崩溃，不能推出所有运行均以同一信号退出。
- 影响: 调用方若通过该工厂创建并按 `WTSObject` 生命周期约定调用 `release()`，会进入未初始化的 `_mutex/_pool` 状态。当前仓内 `WtCore`、`WtUftCore` 的 `TraderAdapter::doCancel` 使用的是 `WTSEntrustAction::create()`；源码检索未发现生产代码调用 `createCancelAction()`，因此不能据此声称所有撤单/改单实盘链路都会崩溃。修复方向：改为 `WTSEntrustAction::allocate()`（与 `create()` 一致），并将 release 用例启用；若该工厂有意返回普通堆对象，则需明确定义并实现相匹配的析构/释放接口。

## BUG-R53-002【中】WTSMap::erase 三个重载摘除节点但不释放元素引用

- 状态: 待审核（容器所有权语义不一致已静态确认；当前仓内未发现 `WTSMap::erase` 生产调用点）
- 严重级别: Major（仅在调用方把 retain 后的元素交由容器持有并调用 erase 时形成泄漏）
- 模块/文件: `src/Includes/WTSCollection.hpp:494-510`（`erase(ConstIterator)`、`erase(Iterator)`、`erase(T key)`）；对照 `remove` `:418-428` 与 `clear` `:546-554` 均会 `release()`
- 相关测试: `src/TestUnits/coverage/r12_headers/r53_collection_variant_test.cpp` → `DISABLED_r53_map.erase_by_key_does_not_release_element`（禁用用例；源码推导，未运行）
- 输入: `WTSMap<int>* m = WTSMap<int>::create(); WTSObject* o = new R53TagObj(7); m->add(1, o, true); m->erase(1);`
- 期望行为: `erase(key)` 与 `remove(key)` 语义一致，元素引用计数从 2 降为 1（容器持有的那一份被释放）。
- 静态行为: `_map.erase(key)` 直接丢弃 `WTSObject*`，不调用 `release()`；`add` 默认 retain，因而在该所有权用法下容器引用仍留在对象计数上。`erase(Iterator)`/`erase(ConstIterator)` 同形。
- 复现步骤: 相关 DISABLED 用例断言 erase 后计数回到 1，但本次未运行；结论来自 `add/remove/clear/erase` 源码对照，不称为实测。
- 影响: 对 `add` 默认 retain 的对象调用任一 `erase` 重载会丢失容器持有引用而不执行 `release()`；当前源码检索未找到 `WTSMap::erase` 的生产调用，故不能外推为现有订单、持仓或合约路径正在持续泄漏。修复方向：若 erase 应与 remove/clear 一样释放容器持有引用，则先保存元素、摘除节点再 release；若要转移所有权，应返回元素指针并单独定义语义，避免无返回值地丢失指针。

## BUG-R53-003【待契约确认】WTSTickStruct::operator= 对未终止旧 tick 字段未保证目标终止

- 状态: 证据不足（未证明无 NUL 的满宽字段是该旧结构体允许的有效字符串输入）
- 严重级别: 条件性边界风险；不得按常规行情转换路径上的越界读或信息泄露计入
- 模块/文件: `src/Includes/WTSStruct.h:203-205`（`strncpy(exchg, tick.exchg, MAX_EXCHANGE_LENGTH); strncpy(code, tick.code, MAX_INSTRUMENT_LENGTH);`）
- 相关测试: 本轮 `r53_struct_union_test.cpp` → `DISABLED_r53_struct_tick.assignment_terminates_full_width_code`
- 输入: `WTSTickStructOld ot; memset(ot.exchg, 'E', 10); memset(ot.code, 'C', 32); WTSTickStruct nt; nt = ot;`。该夹具刻意制造无 NUL 的数组，尚无契约证据证明其属于合法 C 字符串输入。
- 静态行为: `WTSTickStructOld::exchg` 是 10 字节，目标 `MAX_EXCHANGE_LENGTH` 为 16；若源数组无 NUL，`strncpy(exchg, tick.exchg, 16)` 最多读取 16 字节，可能越过源数组边界，且目标代码字段满宽时也没有终止符。此条件下的实现风险可由源码确认。
- 动态证据: 仅有 `DISABLED_r53_struct_tick.assignment_terminates_full_width_code` 的断言设计；本次未运行，未观察 ASAN 或越界读。
- 影响与修复方向: 只有当无 NUL 满宽字段是允许输入，或外部反序列化可产生该状态时，才可确认这是产品数据路径缺陷。先明确旧结构体字段是 C 字符串还是固定宽原始字节；若需容忍非终止数据，应按源数组实际容量做有界拷贝并显式写 NUL，尤其不能用 16 字节长度读取 10 字节的旧 `exchg` 数组。测试应分别覆盖合法字符串契约和明示支持的原始字节契约。
