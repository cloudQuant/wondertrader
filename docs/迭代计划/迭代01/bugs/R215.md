## BUG-R215-001 WtDataReaderAD 缓存命中移空 shared_ptr，刷新路径空指针崩溃

- 状态: 已合并（主编号 `BUG-R144-002`；R185 观察 1、P05-001、R4-BUG-02 为同源记录）
- 严重度: Major（沿用主编号 `BUG-R144-002`）
- 位置:
  - `src/WtDataStorageAD/WtDataReaderAD.cpp:576-578`（`get_k_db` 命中时 `return std::move(it->second)`）
  - `src/WtDataStorageAD/WtDataReaderAD.cpp:272-274`（`update_cache_from_lmdb` 直接 `WtLMDBQuery query(*db)`，未判空）
  - 调用点 `:444-456`（RT bar 晚于 etime 的二次回源）、`:287-290`（同时间戳覆盖）
- 根因与证据边界: `cacheBarsFromStorage` 首次打开并缓存句柄；后续命中时
  `std::move(it->second)` 会把 map 槽位移空，而返回的局部 `shared_ptr` 在该次调用内仍有效；
  再次命中可得到空句柄。`update_cache_from_lmdb` 未检查空句柄便构造 `WtLMDBQuery`。
  本条与 R144-002 是同一源码根因，不另计一项。
- 既有动态证据: 崩溃报告触发栈
  `WtLMDB::is_readonly -> WtLMDBQuery::WtLMDBQuery -> WtDataReaderAD::update_cache_from_lmdb
  -> WtDataReaderAD::readKlineSlice -> R203AdResidualTest...TestBody`（rc=139）。
- 影响: 在同一 reader、同一 (交易所, 周期) 的 map 槽位已被移空后再次刷新时，可能解引用空句柄；
  R203 的原用例报告过该路径崩溃。具体发生次数取决于调用路径，不把“第三次取库”推广为所有场景。
- 测试处理: 原输入、原断言完整保留在 `DISABLED_R203ReaderRtCacheAheadOfEtimeDoesNotAppendFutureBar`；
  另增启用用例 `R203ReaderRtCacheBranchesWithIsolatedReaders`，每次刷新换新 reader，
  只驱动 450-456/459-461 分支。
- 修复建议: 缓存命中时返回 `it->second` 的共享所有权副本；在 `update_cache_from_lmdb` 检查句柄，
  记录错误并安全退出。回归应在同一 reader 上重复触发刷新，并验证无崩溃及返回数据；
  单独换 reader 的分支测试不能覆盖被移空的 map 槽位。
- 交叉引用: `bugs/R144.md` BUG-R144-002（主条目）；`bugs/R185.md` 观察 1、
  `bugs/p05_datastorage2.md` BUG-P05-001、`bugs/R4_adstorage.md` R4-BUG-02 为同源佐证。

## BUG-R215-002 WtRdmDtReaderAD 首次载入把末笔覆写回首笔，跨日区间丢首日

- 状态: 已合并（主编号 `BUG-R32-001`；R185 观察 2 为同源复核）
- 严重度: Blocker（静默数据损坏，跨日区间少返回记录）
- 位置: `src/WtDataStorageAD/WtRdmDtReaderAD.cpp:135-144`，重点 `:140`
  （`WTSTickStruct& curTs = tickList._ticks.front(); ... curTs = tickList._ticks.back();`）
- 根因: `curTs` 是指向 `_ticks[0]` 的引用，赋末笔不是重新绑定，而是把末笔整体
  `memcpy` 回首笔。三笔跨 20240109/20240110 的 tick 载入后首元素被替换成末笔，
  起点 20240109 10:00 的第二次 `lower_bound` 结果错位，区间只返回 2 笔。
- R215 补充证据: `R203AdResidualTest.R203RdmCrossDateTickRangeKeepsAllTicks`：
  `tick_count(slice)` 实际 2、期望 3，`at(0)->action_date` 实际 20240110、期望 20240109。
- 影响: 首次载入至少两笔时缓存首元素可能被末元素覆盖，后续区间查找可错位或漏笔；
  具体分支是否可达取决于输入时间与数据排列，不能据此概括为所有调用均漏首日。
- 测试处理: 原输入、原断言保留，改为
  `DISABLED_R203RdmCrossDateTickRangeKeepsAllTicks`。
- 修复建议: 计算首末时间时分别引用 `front()` 与 `back()`，不要通过可写的首元素引用读取末元素；
  回归覆盖首次载入多笔、跨日期窗口及首元素等于窗口起点的查找。
- 交叉引用: `bugs/R32_adstorage.md` BUG-R32-001（主条目）；`bugs/R185.md` 观察 2 为同源证据。

## BUG-R215-003 TraderAdapter::isTradeEnabled 声明 inline、定义只在 .cpp，跨 TU 调用跳空

- 严重度: 低（沿用主编号：跨 TU 的 inline 声明/定义可见性与告警问题）

  `src/WtCore/TraderAdapter.cpp:598-607`（唯一非 inline 定义）
- 现象与边界: 头文件把函数声明为 `inline`，定义仅在 `TraderAdapter.cpp`，其他 TU 看不到定义；
  主条目记录了 `-Wundefined-inline` 编译问题。R215 的特定目标中 `nm` 显示未定义符号 `U`，
  并有一次 rc=139 的调用报告；这些证据支持该构建/调用路径有问题，但不能推出所有外部调用
  都会以 SIGSEGV 结束，也未单独证明崩溃地址的解析机制。
- 影响: 对需跨 TU 调用的公开 inline API，编译器告警/链接可见性受构建方式影响；
  `getCommodify` 同型但位于 private，不作为公开接口缺陷扩大影响面。
- 测试处理: 原两条 `isTradeEnabled` 断言保留在

  `PublicStateAfterInitExt` 只断言 `initExt` 后的 `state()`。
- 修复建议: 若实现留在 `.cpp`，从头文件声明移除 `inline`；若保留 `inline`，将定义放入所有调用方
  可见的头文件。用未抑制 `-Wundefined-inline` 的独立 TU 编译并链接验证公开调用。
- 交叉引用: `bugs/R202.md` BUG-R202-003（主条目）；`bugs/R211.md` 为复核；
  Q04-006、N01-004、N03-006 可作为调用面关联记录，不重复计数。

## BUG-R215-004 readKlineSlice 在追加 RT bar 前夹紧 count，追加结果被截断

- 状态: 独立候选（与 R215-001 源码函数相同，但根因是 count 提前夹紧；尚未合并）
- 严重度: Major（公开读 API 少返回 K 线；RT 缓存追加对返回条数无效）
- 位置: `src/WtDataStorageAD/WtDataReaderAD.cpp:423`（缓存检查前
  `count = min(barsList._bars.size(), count)`）、`:473`（追加后的第二次夹紧）
- 静态路径: 请求 `count=10`、当前 `_bars` 有 1 根时，`:423` 将局部 `count` 改成 1；
  若随后追加一根符合 `etime` 的 RT bar，`:473` 再用已缩小的 `count` 夹紧，返回切片最多仍为 1 根。
  这是与 BUG-R215-001 空句柄崩溃不同的独立逻辑问题；修复句柄不会自动修复条数截断。
- 既有动态记录: R203 09:40 路径记录为期望 2 根、换 reader 后实际 1 根；本轮未重跑该场景，
  此结果按既有记录引用，不称为本轮复现。
- 影响: 在请求条数大于追加前缓存条数、且追加 RT bar 条件成立时，可能少返回该 RT bar；
  影响限于符合此分支条件的请求。`_last_from_cache` 与返回切片条数是否不一致需另加断言确认。
- 测试处理: 启用分支用例改用 `count=1` 只验证追加分支
  （返回 1 根 09:36 是 count=1 的正确结果）；原 `count=10` 的两根断言保留在
  `DISABLED_R203ReaderRtCacheAheadOfEtimeDoesNotAppendFutureBar`。
- 修复建议: 保存 `requestedCount`，只在形成最终可返回序列后按实际条数与请求上限取最小值；
  不要让追加前对局部 `count` 的夹紧永久缩小请求。回归以 count=10、1 根存储 bar、1 根符合条件
  的 RT bar 期望返回 2 根，并另测请求上限小于实际数据量时仍只返回请求数量。
- 交叉引用: 与 `bugs/R144.md` BUG-R144-002 共用 `readKlineSlice` 刷新路径和部分测试背景，
  但根因分别是句柄移空与 count 截断，须分开修复和计数。

## BUG-R215-005 Level2 逐笔切片在 lower_bound 返回 end 或命中后续项时多报记录

- 状态: 已合并（迭代02：主编号 BUG-R91-003）
- 严重度: Major（切片长度可超过有效数据；目前证据未显示回调实际解引用越界）
- 位置: `src/WtBtCore/HisDataReplayer.cpp:2547-2593`（逐笔委托）、`:2595-2640`
  （委托队列）、`:2643-2685`（逐笔成交）；三者均在 lower_bound 后写 `_cursor = idx + 1`，
  随后通过 `_cursor - 1` 得到末下标。
- 静态现象: 查询时间严格晚于末条时 `lower_bound` 为 `end()`、`idx == size`；加一后
  `eIdx == size`，使计算出的 `realCnt` 可比有效数据多一条。若查询时间落在两条记录之间，
  `lower_bound` 给出后一条下标，当前算式也会把这条晚于截止时间的记录计入；需按契约确定边界算法。
- 证据: `R205BtPorterLevel2.HftLevel2GettersServeStoredBlocksAndRejectMissing`
  原配置 `stime=0930` 时 `hft_get_ordque/orddtl/trans` 均返回 2、回调 count=2；
  把回放起始时间调到 09:00（游标正好落在首条）后返回 1。
- 影响: 委托队列切片的长度/回调 count 会超出有效记录数；委托和成交 getter 有同型源码，
  可能存在同根因问题，但本轮新回归只覆盖队列。不得把“可能越界读”写作已经观测到内存越界，
  因新增测试的回调只记 count、不解引用数据指针。
- 测试处理: 该用例 `stime` 改为 `202001020900`，输入与期望（1 条）保持一致；
  不改产品代码。
- 后续回归（2026-10-29）: 新增 `R205BtPorterLevel2.HftOrderQueueQueryAfterLastStoredRecordDoesNotOvercount`，仅写 09:00 一条记录、于 09:30 查询，回调只记录 count，不解引用数据指针。重新构建后单跑 FAIL：返回值和回调 count 均为 2，期望均为 1；原 09:00 边界用例保留。
- 修复建议: 按公开接口“结束时间”语义定义是否包含等于截止时间的记录；若按截止时间含等号，
  用 `upper_bound` 定位最后一条 `<= etime` 的记录，再计算窗口起止下标，并对空结果、`count==0`
  和 `eIdx < items.size()` 做边界处理。对三种切片分别验证：命中记录、两条之间、晚于末条、
  早于首条及 `etime=0`；断言返回数不超过有效条数，并仅在专门的安全测试中解引用切片。
- 交叉引用: `bugs/R103.md` BUG-R103-002 在 `get_last_tick` 有相似的末尾游标边界症状，
  但 API 和读路径不同，作为相关问题单独保留；BUG-P04-010 是另一段 bar 回放起始游标问题，
  `R210` 本轮条目也不涉及该 Level2 getter，故不作为本条重复证据。

- 迭代02复核: DUPLICATE。detail、queue、transaction 三个切片都以同一类 lower_bound/游标边界错误处理 etime；其代码根因和公开 etime 右界契约与 BUG-R91-003 相同。现有队列测试只断言回调次数，未安全解引用返回记录；detail/trans 的相关边界仍缺直接回归。
