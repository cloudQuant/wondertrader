## BUG-R46-001 运行器构造列表漏初始化部分可读成员（分项已有重复记录）

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtPorter/WtRtRunner.cpp:55-100`（构造函数）；`src/WtBtPorter/WtBtRunner.cpp:47-89`（构造函数）
- 现象:
  - `WtRtRunner` 的初始化列表覆盖了全部 `_cb_*`，但没有 `_engine`、`_feed_obj`、
    `_feeder_bars`、`_feeder_fcts`；成员声明见 `.h:853,924-932`。`getEngine()`（`.h:324`）
    直接返回未初始化的 `_engine`；`feedAdjFactors()`（`.cpp:277-280`）在未先成功调用
    `loadAdjFactors/loadAllAdjFactors` 时直接调用未初始化的 `_feeder_fcts` 并传 `_feed_obj`。
    `feedRawBars()`（`.cpp:283-292`）先检查外部最终K线 loader；若已注册 loader 但尚未通过
    `loadFinalHisBars/loadRawHisBars` 设置 `_feeder_bars/_feed_obj`，直接 feed 也会读到未初始化槽位；
    此调用顺序是源码可达，尚无实际复现。
    `_config`（`.h:824`）也未列入构造列表，但 `config()` 第一处使用前先在 `.cpp:491` 赋值，
    本条不把它列为已证实的「config 前读未定义」路径。
  - `WtBtRunner` 的初始化列表覆盖了 `_cta_mocker/_sel_mocker/_inited/_running/_async`，
    但没有 `_hft_mocker`、`_worker`、`_loader_auto_trans`；`initHftMocker()`（`.cpp:285-297`）
    首句就读取/可能删除 `_hft_mocker`，`stop()`（`.cpp:550-559`）的未运行早退路径读 `_worker`，
    `isAutoTrans()`（`.h:122-125`）直接读 `_loader_auto_trans`。`_exec_mocker` 和 `_cfg` 也未初始化，
    但各自使用路径须结合调用顺序分别确认，不在本条声称已证明为 pre-config 读取。
  - 实盘与回测 C 导出都通过函数静态 runner（`WtPorter.cpp:34-37`、`WtBtPorter.cpp:40-44`），
    静态存储零初始化会掩盖这些构造初值问题；这不能使非静态实例的成员访问合法。
- 相关测试:
  - 既有 BUG-R6-009 覆盖 `_config/_feed_obj/_feeder_bars/_feeder_fcts` 的漏初始化；BUG-Q06-003 覆盖
    `WtBtRunner::_hft_mocker`。BUG-R144-003（并由 R35-001 补充证据）则是被 runner 按值持有的
    `WtCtaEngine::_cfg` 未初始化，属于另一个成员/析构问题。
  - `r6_porter_lifecycle_test.cpp` 的栈 runner 用例确有失败，但同栈析构红不能独立证明本条列出的每个字段是崩溃根因。
  - 本 lane 的 `r46_porter_config_test.cpp` / `r46_btporter_runner_test.cpp` 全部改用
    「堆上 `new`、故意不 `delete`」的实例；这些用例避开了对象析构，未直接验证本条列出的危险读取。
- 输入/前置条件: 对非静态对象在成员赋值前调用相应消费入口，例如 `WtRtRunner r; r.getEngine()`、
  未装外部复权因子 feeder 时调用 `feedAdjFactors()`、`WtBtRunner r; r.isAutoTrans()`，或
  `WtBtRunner r; r.initHftMocker("x")`。这些入口读取不确定值，结果为 C++ 未定义行为，不能承诺必现崩溃。
- 期望: 会在构造后被入口读取的标量/指针/句柄全部有确定默认值；未配置时入口返回空/失败或安全早退。
- 实际与证据等级: 源码证实上述具体成员未初始化且对应消费者会读它们；本次没有单独运行 R46-001 的
  非静态字段用例。R35 的栈实例测试本次 exit 139，但它只证明栈 runner 析构崩溃，相关根因已归
  BUG-R144-003，不能算作 `_engine/_worker/_hft_mocker` 等字段的独立运行证据。
- 影响: 非静态实例在相应调用顺序下会触发未定义行为。现有 coverage lane 的堆分配/泄漏方式是测试夹具
  的规避策略，不是生产影响证据；静态 C 导出单例的零初始化也只规避静态对象自身的构造初值问题。
- 备注: 与 BUG-R6-009 / BUG-Q06-003 重复的字段合并到既有记录；本条只保留未被既有条目覆盖的 `_engine`、
  `_worker`、`_loader_auto_trans` 等具体消费路径。建议对实际被读取字段做类内默认初始化，并为上述入口
  增加安全早退；`_exec_mocker/_cfg` 仅在确认存在未赋值读取后再登记。

## BUG-R46-002 WtRtRunner::config 忽略 initEngine() 失败，env 缺失时仍返回 true 且 _engine 未赋值

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtPorter/WtRtRunner.cpp:584`（`initEngine();` 返回值未接）、`:840-842`（`env` 缺失直接 `return false`）
- 现象: `config()` 对 `initEngine()` 的 `bool` 返回值不做判断；`env` 段缺失时
  `initEngine()` 在 `_config->get("env")` 为 NULL 处提前返回 false，既不设置 `_engine`，
  也不回滚后续步骤；`config()` 继续执行 `initDataMgr()`/`initActionPolicy()`，
  在 `bspolicy` 存在时一路走到 `return true`。
- 相关测试: `r46_porter_config_test.cpp:R46PorterConfig.MissingEnvMakesConfigFail`。
  原禁用用例曾读取未初始化 `_engine` 并期望 nullptr，属未定义行为；本次删除该读取，改成启用测试断言配置失败。
  重新构建后单跑为 FAIL：`config()` 实际返回 true，期望 false。
- 输入: `config("{\"basefiles\":{},\"data\":{},\"bspolicy\":\"<存在的actions.json>\"}", false)`
- 期望: 返回 false（或至少把 `_engine` 置空并记录错误），让调用方知道运行环境没建起来。
- 实际与证据等级: 本次实测 `config()` 返回 true；源码也表明 `initEngine()` 返回值被忽略，后续
  `initDataMgr()` 返回值同样被忽略，`initActionPolicy()` 成功后 `.cpp:713` 无条件返回 true。
  `_engine` 未由 `initEngine()` 设置，但读取其值属于未定义行为，原测试的 `getEngine()==nullptr` 断言无效。
  此后 `create_ext_parser`/`run_porter` 会按 BUG-R6-003 的路径崩溃。
- 复现步骤: 在有效 `basefiles:{}`、`data:{}`、存在的空 action policy JSON、缺少 `env` 的配置上调用
  `config()`；本次运行修正后的启用测试得到 FAIL（实际 true）。不要在未先初始化 `_engine` 的状态调用
  `getEngine()/create_ext_parser()/run_porter()` 来证明返回值，因为这些操作触发另一个未定义行为/崩溃路径。
- 影响: 配置漏写 `env` 属常见笔误，实盘侧表现为"配置加载成功"却在启动阶段崩溃，
  排障信息指向 `_engine` 空指针而不是缺段本身。
- 备注: 与 BUG-R69-003 同属 config 忽略内部初始化结果的错误传播问题，但一个是 `initEngine()`、
  一个是 `initDataMgr()`；可以在修复中统一检查子步骤结果，保留不同缺段的回归用例，不应把它们当作同一条源码路径。

## BUG-R46-003 WtBtRunner::config 对 replayer / env 两段没有 NULL 守卫，缺段即空指针解引用

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件: `src/WtBtPorter/WtBtRunner.cpp:467`（`_replayer.init(_cfg->get("replayer"), ...)`，`HisDataReplayer::init` 首行即解引用 cfg）、`:469-470`（`WTSVariant* cfgEnv = _cfg->get("env"); const char* mode = cfgEnv->getCString("mocker");`）
- 现象: `config()` 只校验了 `_cfg` 是否为 NULL（`:458-462`），对两个必需子段都没有判空。
  `env` 缺失 -> `cfgEnv->getCString` 段错误；`replayer` 缺失 -> `HisDataReplayer::init`
  （`src/WtBtCore/HisDataReplayer.cpp:175`）在 `cfg->getCString("mode")` 处段错误。
  同函数对 `notifier` 段（`:465`）反而有判空，三处口径不一致。
- 相关测试:
  - `r46_btporter_runner_test.cpp:R46BtRunner.DISABLED_ConfigWithoutEnvSectionDerefsNull`
  - `r46_btporter_runner_test.cpp:R46BtRunner.DISABLED_ConfigWithoutReplayerSectionDerefsNull`
- 输入:
  - `config("{\"replayer\":{\"mode\":\"none\",\"basefiles\":{},\"path\":\"/tmp\"}}", false)`（缺 env）
  - `config("{\"env\":{\"mocker\":\"none\"}}", false)`（缺 replayer）
- 期望: 返回/记录 "config missing env/replayer" 并安全退出（`config` 返回 void，至少不崩）。
- 实际: SIGSEGV 打死宿主；`catch(...)` 抓不到，gtest 进程直接终止。
- 证据等级与复现: 源码直接证实缺少段检查；本次分别运行现有两条 `DISABLED_` 用例，profile 路径均在 `/tmp`，
  且 `ulimit -c 0`：`LLVM_PROFILE_FILE=/tmp/codex-r46-003-env-%p.profraw build-cov/build_x64/Debug/bin/TestUnits/CoverageTests_btporter --gtest_filter=R46BtRunner.DISABLED_ConfigWithoutEnvSectionDerefsNull --gtest_also_run_disabled_tests`
  缺 `env` 用例 exit 139；`LLVM_PROFILE_FILE=/tmp/codex-r46-003-replayer-%p.profraw build-cov/build_x64/Debug/bin/TestUnits/CoverageTests_btporter --gtest_filter=R46BtRunner.DISABLED_ConfigWithoutReplayerSectionDerefsNull --gtest_also_run_disabled_tests`
  缺 `replayer` 用例 exit 139。前者带有效 `replayer/basefiles`，后者的空指针在 `HisDataReplayer::init`
  首个 `cfg->getCString("mode")` 处被解引用。
- 修复方向: 在 `WtBtRunner::config` 对 `replayer` 和 `env` 子段及预期类型做检查；缺项时记录具体段名并早退。
  `config` 当前返回 `void`，所以不能直接要求返回 false；若需让调用方观察失败，可单独评估接口返回类型变更。
- 影响: 回测配置写错 / 使用旧版配置模板（不含 `replayer` 段）时，回测进程崩溃而非报错；
  覆盖率侧导致 `config()` 的这两条错误路径无法在进程内取样。
