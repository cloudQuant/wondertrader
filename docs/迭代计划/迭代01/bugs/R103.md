## BUG-R103-001 TraderMocker 收到零长度 UDP 数据报后不再重新挂起接收，tick 源永久静默

- 编号: BUG-R103-001
- 状态: 待审核
- 模块/文件/行: `src/TraderMocker/TraderMocker.cpp:935-962`，
  重点是 `950-951`（`if (_terminated || bytes_transferred <= 0) return;`）
  与 `955-960`（仅在正常路径重新 `async_receive_from`）
- 相关测试: `src/TestUnits/coverage/t_TraderMocker/r103_mocker_udp_packet_test.cpp`
  `R103Mocker_UdpUnknownTickAndEmptyDatagram`
- 输入/前置条件:
  1. `init(cfg)`（`udp_port` 为任意本地端口）+ `connect()`；
  2. 向该端口发送一个长度为 0 的 UDP 数据报（`sendto(fd, "", 0, ...)`）；
  3. 之后再发送任意合法 `UDP_MSG_PUSHTICK` 包。
- 期望行为: 0 字节数据报应被忽略并继续 `async_receive_from`；后续 tick 仍应进入
  `extract_buffer()` 更新 `_ticks`（或至少保持接收链存活）。
- 实际行为: `handle_read` 在 `bytes_transferred <= 0` 时直接 `return`，而重新挂起
  `async_receive_from` 的代码在 `return` 之后（`955-960`）。因此一次 0 字节接收会让
  UDP 接收链永久停止；`io_context` 仍在运行，`queryAccount/queryPositions` 等仍能正常回报，
  从外部看“连接还活着”，但撮合器再也收不到行情。
- 复现步骤:
  1. `TraderMocker a; a.init(cfg); a.connect();`；
  2. 用一个本机 UDP socket 向 `cfg.udp_port` 发送 0 字节数据报；
  3. 再发送合法 tick 包；观察 `extract_buffer` 不再被调用（`_ticks` 不更新，
     `match_once` 永远拿不到新价）。
- 影响范围: 任何对端/网络设备发送空 UDP 数据报（心跳、探测、截断包）的场景；
  仿真撮合在无日志、无错误码的情况下静默停摆。
- 严重级别: Major
- 备注: 修复方向是把 `951` 的早退改成 `if (bytes_transferred > 0) extract_buffer(...);
  if (isBroad && _b_socket) async_receive_from(...)`，或在 `bytes_transferred == 0` 时
  仅跳过 `extract_buffer`、仍然重新挂起。本 lane 的用例把空数据报放在最后发送，
  避免影响前面 tick 包的覆盖断言；该缺陷不阻塞覆盖率。

## BUG-R103-002 HisDataReplayer::get_last_tick 在“当前时间晚于最后一笔”时越界读

- 编号: BUG-R103-002
- 状态: 待审核
- 模块/文件/行: `src/WtBtCore/HisDataReplayer.cpp:2881-2912`，
  重点是 `2890-2908`（`_cursor == UINT_MAX` 时用 `lower_bound` 直接写
  `_cursor = idx + 1`）与 `2912`（`_items[_cursor - 1]`）
- 相关测试: 无启用用例（触发即越界读，结果依赖堆布局，无法写确定性断言）。
  由 `r103_replayer_minute_slice_test.cpp` 的只读审阅路径发现；该用例在 tick 回放
  结束后不再调用 `get_last_tick`，避免踩中。
- 输入/前置条件:
  1. 某合约当日 tick 缓存有 2 笔：09:31、09:33；
  2. `prepare()` 后把当前时间推进到 09:35（或 `run()` 回放完成后 `_cur_time` 晚于最后一笔）；
  3. 首次调用 `get_last_tick(code)`（`_cursor` 仍为 `UINT_MAX`）。
- 期望行为: 返回最后一笔（09:33），或明确返回 NULL；不得读取 vector 末尾之外。
- 实际行为: `std::lower_bound` 对 09:35 返回 `end()`，`idx == size`，
  `_cursor = idx + 1 == size + 1`。由于该赋值发生在
  `if (_cursor == UINT_MAX)` 分支内，紧随其后的
  `else if (_cursor > _count) return NULL;` 本次调用不会执行；
  函数直接执行 `_items[_cursor - 1]`，即 `_items[size]`，越界读一个 `WTSTickStruct`
  并 `WTSTickData::create()` 返回垃圾行情。只有第二次调用才会因
  `_cursor > _count` 返回 NULL。
- 复现步骤:
  1. 构造 `mode=bin`/`tick=true` 的 replayer，写入 09:31、09:33 两笔 tick；
  2. `prepare()`；`set_time_range` 或回放推进到 09:35 之后；
  3. 调用 `get_last_tick("SSE.STK.000001")`；在 ASan/libc++ 调试模式下
     报 heap-buffer-overflow / vector 下标断言。
- 影响范围: 策略在收盘后、`run()` 结束后或跨日边界调用 `get_last_tick` 的常见路径；
  可能拿到垃圾价格，也可能直接崩溃。
- 严重级别: Major
- 备注: 修复方向：在 `if (_cursor == UINT_MAX)` 分支内，`lower_bound` 返回 `end()`
  时把 `_cursor` 夹到 `_count`（或直接返回 NULL），并让 `_cursor > _count` 的守卫
  对本次调用同样生效。`get_tick_slice` 已用 `eIdx = _cursor - 2` 与
  `if (tit == end) size` 做了类似保护，可作为参照。本 lane 不修，仅归档。
