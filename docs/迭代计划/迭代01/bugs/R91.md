## BUG-R91-001 checkOrderDetails / checkOrderQueues 缺数据时写错缓存，污染 trans 缓存

- 编号: BUG-R91-001
- 状态: 源码缺陷已确认；与 `bugs/R2_wtbtcore.md` 首条同根重复，R91 保留主记录
- 模块/文件/行:
  - `src/WtBtCore/HisDataReplayer.cpp:2729-2739`（`checkOrderDetails` 的 `!hasData` 分支，
    实际写入 `_trans_cache[stdCode]`）
  - `src/WtBtCore/HisDataReplayer.cpp:2771-2781`（`checkOrderQueues` 同样写入 `_trans_cache`）
  - 受影响读取：`HisDataReplayer.cpp:2786-2825`（`checkTransactions`）、`2643-2688`
    （`get_transaction_slice`）
- 相关测试: `src/TestUnits/coverage/q02_btcore3/r91_replayer_bin_hft_test.cpp`
  `DISABLED_R91BinHft_OrderDetailCacheMissPoisonsTransactionCache`
- 输入/前置条件:
  1. `mode=bin`，`prepare()` 后当前交易日 20200102；
  2. 临时存储中只有 `his/trans/SSE/20200102/000003.dsb`（两条成交 20.1/20.2），
     没有 `his/orders/SSE/20200102/000003.dsb`；
  3. `get_order_detail_slice("SSE.STK.000003", 2, 202001020933)` 先执行（返回 NULL）。
- 期望行为: 缺少委托明细只应把 `_orddtl_cache` 标记为当日空；随后
  `get_transaction_slice("SSE.STK.000003", 2, 202001020932)` 应从磁盘装载并返回两条成交
  （20.1/20.2）。
- 源码证据与影响: `checkOrderDetails` 在无数据分支执行
  `auto& dataList = _trans_cache[stdCode]; dataList._items.resize(0); ... _date = uDate; _count = 0;`
  把**成交缓存**伪造成「当日已装载的空列表」。`checkTransactions` 看到 `_date == uDate`
  后直接返回 true，不再调用 `cacheRawTransFromBin`，所以磁盘上的成交不会加载。
  `get_transaction_slice` 随后会对空缓存走游标/切片计算；其具体返回或越界表现受空 vector 的 `data()` 和调用方式影响，不能据当前禁用用例写成已观察到的固定结果。
  `checkOrderQueues` 有同一错误。
- 测试边界: 旧名称 `R91BinHft_DISABLED_OrderDetailCacheMissPoisonsTransactionCache` 把 `DISABLED_` 放在测试名中间，GoogleTest 实际不会禁用它；现已改名 `DISABLED_R91BinHft_OrderDetailCacheMissPoisonsTransactionCache` 并用 `--gtest_list_tests` 核对。污染后查询可能构造空数组的非空切片，故未执行该路径；修复后应启用并验证两笔成交。新增不查询缺失订单明细的 `R91BinHft_TransactionSliceLoadsWithoutOrderDetailMiss`，独立运行 PASS，验证同类 fixture 的正常成交读取。R2 的 CSV 拒绝用例在 CSV 分支提前返回，也不覆盖这里的 bin 缺数据路径。源码足以确认缓存污染和成交加载被跳过；具体切片后果尚待安全验证。
- 修复方向: 缺失 order detail / queue 应写入各自缓存，不能修改 `_trans_cache`。若对缺失数据做负缓存，检查逻辑必须在同日空缓存命中时仍返回“无数据”，避免空列表进入切片；也可不负缓存而重复安全返回失败。回归应先确认交易缓存可加载，再查询缺 detail/queue，最后确认成交仍可读；并单独验证重复空流查询返回 NULL。
- 严重级别: S3（跨数据类型污染有源码证据；切片层具体后果未动态验证）

## BUG-R91-002 bin K线装载失败留下空 BarsList，可能被自动选为主K线

- 编号: BUG-R91-002
- 状态: 原“未初始化 `_period` 导致 UB”论据不成立；失败项污染自动主K线选择的路径由源码确认，影响场景待动态验证
- 模块/文件/行:
  - `src/WtBtCore/HisDataReplayer.cpp:4497-4504`（进入 `cacheRawBarsFromBin` 即
    `_bars_cache[key].reset(new BarsList)`）
  - `src/WtBtCore/HisDataReplayer.cpp:4560-4567`（loader/HisDtMgr 失败且 buffer 为空时
    直接 `return false`，缓存项留在 `_bars_cache`）
  - `src/WtBtCore/HisDataReplayer.cpp:684-711`（`run()` 无显式主K线时按 `_period` 自动挑选缓存项）
  - `src/WtBtCore/HisDataReplayer.cpp:771-785,912-916`（选中的空 bars 项使 `run_by_bars` 进入无数据分支并退出）
- 相关测试: `R91BinBars_MissingBinBarsYieldNullSlice` 仅验证缺失数据返回 NULL 和时间轴未变化，不调用 `run()`。
  本轮未运行该用例；它不验证自动主K线选择或回放是否被空缓存项截断。
- 输入/前置条件:
  1. `mode=bin`，`prepare()`；
  2. `get_kline_slice("SSE.STK.600000", "m", 3, 1, false)`，但存储中没有
     对应的 minute-1 bin 数据（返回 NULL，同时 `_bars_cache` 多出 `_period=KP_Minute1` 的空 `BarsList`）；
  3. 再装入一条有效的 day K 线，确保没有通过 `isMain=true` 显式设置 `_main_key`，再调用 `run(false)`。
- 期望行为: 自动选主K线应忽略没有 bars 的失败项，选择有效缓存；若无有效缓存，应按无数据路径结束。
- 源码证据: `cacheRawBarsFromBin` 在失败返回前已经给 `barsList->_code` 和 `barsList->_period` 赋值（L4503-L4504），所以该路径的 `_period` **不是未初始化值**，不支持原文的 UB 结论。失败项仍留在 `_bars_cache`。当 `_main_key` 为空时，`run()` 不检查 `_bars` 是否为空，按最小 `_period` 选择缓存项；若空的 m1 项排在有效 day 项之前，`run_by_bars` 的 `locate_barindex` 对空 vector 得到 `UINT32_MAX`，随后因 cursor 仍为 `UINT_MAX` 走“无数据”分支并结束回放。可据源码推出有效 day 数据不会被回放，但本轮没有动态运行该组合场景。
- 修复方向: 加载失败时从目标 cache 擦除失败 key，或让 `run()` 的候选筛选忽略 `_bars.empty()`；显式设置为失败 `_main_key` 时也应返回清晰失败/结束状态。无需为此路径声称需初始化 `_period`。
- 严重级别: S3（可导致自动选择空周期并漏回放其他有效缓存；场景未动态验证）

## BUG-R91-003 get_order_detail/queue/transaction_slice 在 etime 不早于最后一笔时越界读

- 编号: BUG-R91-003
- 状态: 源码确认的越界访问风险；本轮未运行 ASan/测试
- 模块/文件/行:
  - `src/WtBtCore/HisDataReplayer.cpp:2578-2592`（`get_order_detail_slice`）
  - `src/WtBtCore/HisDataReplayer.cpp:2626-2640`（`get_order_queue_slice`）
  - `src/WtBtCore/HisDataReplayer.cpp:2674-2688`（`get_transaction_slice`）
- 相关测试: 无启用用例；本轮未运行 ASan。下述为可操作的测试设计，不是已有复现结果。
- 输入/前置条件:
  1. 当日 orders/queue/trans 缓存各有 3 条（931/932/933）；
  2. `prepare()` 后 `_cur_date/_cur_time` 为 20200102 09:30；
  3. 调用 `get_order_detail_slice(code, 3, 202001021500)`（etime 晚于全部数据），
     queue/trans 同理。
- 期望行为: lower_bound 落在 `end()` 时应把 `eIdx` 夹到 `size()-1`，返回最后 3 条。
- 源码证据与风险: `std::lower_bound` 返回 `end()` 时 `idx == size`，代码写
  `_cursor = idx + 1`（= size+1），随后 `eIdx = _cursor - 1`（= size），
  `sIdx = eIdx + 1 - count`。以 size=3、count=3 为例：sIdx=1、realCnt=3，
  最终 slice 起点是 `items.data()+1`、长度仍为 3；读取 slice 第三个元素会访问 `items[3]`，超出 3 项 vector。
  count=2 时也会产生相同的末端越界。`WTSOrdDtl/OrdQue/TransSlice::create` 只保存指针和长度，越界通常在调用者读取相应元素时发生，不是在 create 内复制数据。
- 测试设计（未运行）:
  1. 写 3 条 orddtl（或 ordque/trans）到临时 bin 存储；
  2. `prepare()` 后调用 `get_order_detail_slice(code, 3, 202001021500)`；
  3. 在 ASan 构建中读取 `slice->at(2)`，检查越界；该结果本轮未取得。
- 修复方向: 对 `count==0` 和空缓存先行处理；把结束索引夹在 `_count-1`，或在 `lower_bound==end()` 时明确返回最后一项的 cursor，保证 `start + realCnt <= _items.size()`。对 order detail、queue、transaction 三个路径一致修复并覆盖 `etime` 早于首项、命中、晚于末项及默认当前时间落在末尾的情况。
- 严重级别: S3（公开切片 API 可返回越界 view；调用者读到末项之外时触发未定义行为）
