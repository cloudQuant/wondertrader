## 审计裁定（2026-10-29）

- **源码路径成立、但本次未动态触发：BUG-R60-001/002/003/004。** 001 的 joinable worker 与未关闭 socket 是两项生命周期清理问题；002 是首次建 `_awaits` 前撤单的空指针路径；003 是 `_b_socket` 裸指针未在 `release`/析构销毁；004 的 `init()` 在 creator 缺失时仍返回 `true`，`connect()` 随后无守卫调用 creator。报告中的信号与 fd 后果需按这些前提描述，不能称为本次实测。
- **生命周期前提未证：BUG-R60-005。** `notifyTrade` 的缓存路径在 `m_mapPosition == NULL` 时确有空指针访问，但没有 YD SDK 时序证据证明正式生命周期会在 `notifyFinishInit` 前送达已登记合约成交。它与 T5-15 共用“持仓表未就绪/键缺失”状态前提，但属于另一个回调点；应作为同一缺陷族的条件候选，不宣称已证实正常柜台时序会触发。
- **接口语义不足以定为缺陷：BUG-R60-006。** `ITraderApi::isConnected()` 没有定义是 transport connect、login 还是 ALLREADY。`WTE_Connect` 只证明 connect 事件已发；多个实盘 adapter 的 `isConnected()` 返回 ALLREADY，故不能从该事件推出应为 true。应先统一模拟器与宿主的状态契约，再改实现或测试。
- **空指针是否属于可接受输入未约定：BUG-R60-007。** `orderAction(NULL)` 会在入口解引用，这是源码事实；但 `ITraderApi` 对 `action` 的说明未承诺 NULL 可用。应登记为防御性候选，先明确调用契约；不要仅凭 `orderInsert(NULL)` 的局部防护认定 API 契约不一致。

## BUG-R60-001

- 状态: 待审核
- 严重级别: Blocker（特定断开/销毁序列导致不可正常析构；信号未在本次复核中实测）
- 模块/文件: `src/TraderMocker/TraderMocker.cpp` L705-716（`disconnect`）、L640-657（`release`）、
  L689-703（`connect` 起 `_thrd_worker`）
- 相关测试: 本轮全部 connect 用例只走「connect → release」；该崩溃序列未启用
- 输入/前置条件: `init(cfg)` → `connect()`（成功 bind 并起 io worker）→ `disconnect()` → 对象析构
- 期望行为: `disconnect()` 关闭 UDP socket、`_io_service.stop()` 并 join `_thrd_worker`；`release()` 同样
- 实际行为: `disconnect()` 只 join `_thrd_match`，并把 `_terminated = true`（L710）；随后 `release()`
  在 L642-643 因 `_terminated` 直接 return，`_io_service.stop()` 与 `_thrd_worker->join()`（L652-656）
  **永不执行**。`_thrd_worker` 是 `std::thread` 的 shared_ptr，析构仍 joinable 的 thread 会调用
  `std::terminate`
- 复现步骤: `TraderMocker a; a.init(cfg); a.connect(); a.disconnect();` 离开作用域
- 影响范围: 在 `connect()` 创建 worker 后走「先 disconnect 再销毁/重载」的宿主。由 joinable `std::thread` 成员析构可推导会触发 `std::terminate`；本次未动态确认信号。socket 未关闭是独立清理问题，见 BUG-R60-003。
- 备注: 修复方向：`disconnect()` 复用 `release()` 的 stop+join 逻辑，或 `release()` 不因
  `_terminated` 跳过 worker 清理；`_thrd_worker.join()` 后置空。

## BUG-R60-005

- 状态: 待审核
- 严重级别: Major（空指针解引用，启动/重连时序相关）
- 模块/文件: `src/TraderYD/TraderYD.cpp` L536-552（`notifyTrade` 的缓存链）、L376-377（`m_mapPosition` 唯一创建点）
- 相关测试: 无启用用例；`trade_for_unregistered_contract...` 用未登记合约在 L1061-1063 提前返回，
  没有触碰该分支。T5-15 对 `notifyOrder` 的关联路径也只作静态候选，未证明 SDK 正常回调顺序会在 `notifyFinishInit` 前触发。
- 输入/前置条件: `init + registerSpi` 后，`notifyFinishInit()` 尚未执行（`m_mapPosition == NULL`），
  厂商推一条**已登记合约**的成交（`m_bCatchup == false` 或 `update_cache == true`）
- 候选期望（待接口/SDK时序确认）: 若允许该回调顺序，成交处理不应在持仓表未建时解引用空指针；是缓存、延迟合并还是安全拒绝，需按 SDK 与仓位同步契约确定。
- 实际行为: L551 `WTSPositionItem* pos = (WTSPositionItem*)m_mapPosition->get(key);` 直接解引用 NULL；
  L552 的 `pos == NULL` 判断在解引用之后，救不了
- 复现步骤: 夹具 init/register 后，直接 `notifyTrade(&trade, &inst, NULL)` 一条 `SHFE.ag2512` 成交
- 影响范围: 若 SDK 在持仓初始化前推送已登记合约成交，该回调会在访问空 map 时产生未定义行为；重连/补推是否具备此顺序尚未验证。
- 备注: T5-15 记录了 `notifyOrder` 对同一持仓 map 的空指针候选。两个 callback 行不同，但共享“持仓表初始化时序”根因族；复核尚无正式 SDK 时序证据，需并列引用而不将本项描述成独立的已动态复现缺陷。
  修复方向：在所有缓存回调前保证持仓表已初始化，或明确缓冲到快照合并完成；补测前先确认 SDK 回调顺序与持仓更新契约。

## BUG-R60-006

- 状态: 待接口契约确认（源码现象成立，缺少可判定期望）
- 严重级别: 未定级（连接态语义不一致的候选）
- 模块/文件: `src/TraderMocker/TraderMocker.cpp` L718-721（`isConnected`）、L689-703（`connect`）、
  L723-743（`login` 才给 `_thrd_match` 赋值）
- 相关测试: `r60_tradermocker_async_test.cpp` 的 connect 用例（只断言 `WTE_Connect`，未把该现状写成期望）
- 输入/前置条件: `init` + `connect()` 成功（UDP 已 bind、io worker 已 run、`WTE_Connect` 已回调）
- 原期望: `isConnected()` 为 true（理由是连接事件已经发出）。该推断未由接口契约支持；`WTE_Connect` 是否等价于 `isConnected()` 的状态尚未定义。
- 实际行为: `isConnected()` 返回 `_thrd_match != NULL`；`connect()` 只创建 `_thrd_worker`，
  `_thrd_match` 直到 `login()` 才创建，因此 connect 之后仍为 false
- 复现步骤: connect 后等 `handleEvent(WTE_Connect)`，再调 `isConnected()`
- 影响范围: 只有当接口契约要求 connect 事件后立即为 true 才构成行为缺陷。CTP/YD 等适配器把 `isConnected()` 定义为 `WS_ALLREADY`，与此处「login 后才创建撮合线程」更接近；应先确认 host 侧调用语义。
- 复核方向: 查明 `isConnected()` 是 transport 状态还是已登录/可交易状态，再据此修改实现或测试。不能仅改为 `_thrd_worker != NULL`，因为该判断也可能把尚未登录状态报告为已连接。
