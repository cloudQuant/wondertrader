## BUG-R164-001 UDPCaster socket 晚于 io_context 析构，存在服务对象生命周期错误

- 状态: 待审核
- 严重级别: Major（静态确认生命周期次序错误；崩溃表现尚无当前可复核动态证据）
- 模块/文件/行: `src/WtDtCore/UDPCaster.h:88-96`（`m_sktBroadcast`/`m_sktSubscribe`/`m_list*Group` 声明在 `m_ioservice` 之前）、`src/WtDtCore/UDPCaster.h:96`（`m_ioservice`）、`src/WtDtCore/UDPCaster.cpp:58-60`（析构体本身为空）
- 相关测试: `r164_udp_caster_active_test.cpp::R164UdpCasterActiveTest.DISABLED_ActiveStartThenDestructorCrashes`；R154 active 用例现有 `.rc` 通过 `LeakyCaster` 绕开了真实 `UDPCaster` 析构
- 输入/前置条件: `UDPCaster caster; WTSVariant* cfg = {"active": true, "sport": <空闲端口>}; caster.init(cfg, nullptr, nullptr); caster.stop();` 然后对象离开作用域
- 期望行为: 析构安全；socket 应在 `io_context` 仍然存活时 close/reset，或在销毁 `io_context` 前清理所有 socket 持有者
- 实际行为: 成员按声明逆序析构，`m_ioservice`（H96）早于 `m_sktBroadcast`（H88）、
  `m_sktSubscribe`（H89）和 `m_list*Group`（H93-95）销毁；socket 对象可能在其所属的
  Asio service/reactor 之后销毁，违反依赖对象生命周期顺序，构成静态确认的生命周期风险。
  具体是否表现为 SIGSEGV、异常或其他后果依赖 socket 状态与 Boost/平台实现，源码不能
  推出“只要创建 socket 就必崩”。`stop()` 当前停 io_context 并 join 线程，但不 reset
  这些成员，不能修正析构次序。`ShmCaster` 不持有该 io_context，不属于本问题。
- 复现步骤: 1) 用 active=true、sport=空闲端口的配置 init 一个栈上 UDPCaster；2) stop()；
  3) 作用域结束触发析构；4) 在 sanitizer 或可取得的系统崩溃报告下检查析构期间是否访问
  失效服务对象。当前用例仍为 `DISABLED_`，这只是建议的受控验证步骤。
- 证据:
  - 头文件的成员声明顺序静态确认了 io_context 先于关联 socket/group 容器析构；`stop()` 未 reset 这些成员。
  - `DISABLED_ActiveStartThenDestructorCrashes` 未运行。文档原先引用的
    `~/Library/Logs/DiagnosticReports/CoverageTests_dtcore-2026-10-28-200143.ips` 当前不存在，
    因而该崩溃栈不能作为本轮可核验证据。
  - 当前 R154 三条 `.rc` 记录为 PASS，但测试使用 `LeakyCaster`，析构时不释放真实
    `UDPCaster`，不能证明析构安全或覆盖真实析构路径。
- 影响范围: 当 active 路径创建并保留关联 socket 时，析构次序留下服务对象早于 socket
  释放的风险，可能影响正常退出、重载和异常释放；本轮未验证实际崩溃概率、影响实例数或
  行情数据丢失。
- 修复方向: 让 `m_ioservice` 在所有依赖它的 socket/group 容器之后析构（按声明顺序调整），
  或在 service 仍存活时显式 close/reset 所有 socket 并清理持有引用的容器，再停止/销毁
  service。增加真实对象析构的受控验收；不要用 `LeakyCaster` 的 PASS 作为析构证明。
