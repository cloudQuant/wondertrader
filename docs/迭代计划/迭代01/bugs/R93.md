## BUG-R93-001 TraderYD::extractEntrustID 未拒绝缺少 `#` 的委托号

- 状态: 源码缺陷确认；本轮未运行测试
- 严重级别: Major（非法格式会进入未定义的指针偏移/读取路径；具体运行表现未测）
- 模块/文件: `src/TraderYD/TraderYD.cpp:1101-1111`
- 相关测试: `r93_traderYD_api_test.cpp:512-569` 的有效委托号和双 `#` 拒绝用例覆盖了两种格式，但没有覆盖无 `#`。测试源码说明双 `#` 令 `idx != idx2` 并拒绝；该用例本轮未运行。
- 输入/前置条件: `m_wrapperState == WS_ALLREADY`，调用 `orderAction()`，委托号不含 `#`，例如 `no_separator_here`。
- 证据与行为: `StrUtil::findFirst/findLast` 在找不到字符时返回 `std::string::npos`（`src/Share/StrUtil.hpp:64-91`）。此时 `idx == idx2`，`TraderYD::extractEntrustID()` 不会走 `idx != idx2` 的拒绝分支，而会计算 `entrustid + idx + 1` 并传入递归读取字符的 `convert::to_uint32()`（`src/Share/Converter.hpp:57-60`）。该指针偏移已越出输入字符串边界，行为未定义；不能据静态代码断言每次都读到特定值、稳定返回或实际发出撤单。`orderAction()` 在解析函数返回 false 时会返回 -1（`:839-846`），因此解析入口应负责拒绝该格式。
- 期望行为: 对不符合 `user#数字` 格式的委托号返回 false；`orderAction()` 返回 -1 且不调用厂商撤单接口。
- 可操作修复: 在计算后缀指针前显式拒绝 `idx == std::string::npos`；再验证分隔符后有非空数字后缀且整个后缀可解析，只有完整校验成功后才写入 `orderRef`。
- 验证方向: 增加无 `#`、空后缀、非数字后缀和双 `#` 的拒绝断言，并确认 stub 的撤单调用数不增加。当前仅有测试源码证据，没有动态结果。

## BUG-R93-002 TraderYD 的 queryOrders/queryTrades 未释放回报数组

- 状态: 源码缺陷确认；泄漏增长量未测
- 严重级别: Major（每次被执行的查询都会留下数组及其持有引用）
- 模块/文件: `src/TraderYD/TraderYD.cpp:915-963`；对照 `queryPositions()` 在 `:905-909` 回调后释放数组
- 相关测试: `r93_traderYD_api_test.cpp` 的 `cache_roundtrip_marks_orders_and_trades_and_queries_arrays` 验证查询回报内容；一次或少量功能断言不能证明无泄漏或 RSS 增长。本轮未运行该用例或内存基准。
- 输入/前置条件: API 非空、状态为 `WS_ALLREADY`，队列中的 `queryOrders` 或 `queryTrades` lambda 被执行。
- 证据与行为: 两个 lambda 分别创建 `WTSArray`，对缓存对象调用 `append(..., true)` 后回调 sink，但回调后没有 `clear()` 或 `release()`（`:924-934`, `:949-959`）。`WTSArray::append` 的 `true` 会增加对象引用计数（`src/Includes/WTSCollection.hpp:153-160`），而数组的 `release()` 会清空并释放元素引用（`:197-229`）。对应接口接收 `const WTSArray*`（`src/Includes/ITraderApi.h:150-160`），且同一适配器的 `queryPositions()` 采用回调后释放的生命周期。因此已执行的订单/成交查询会泄漏其数组及数组持有的元素引用；未测得实际 RSS 变化。
- 期望行为: 和 `queryPositions()` 一样，在同步回调结束后释放本地数组；sink 若需跨回调保存数组或元素，应显式 retain。
- 可操作修复: 两个回调调用结束后分别执行 `ayOrders->release()` / `ayTrades->release()`，确保即使 sink 为空也释放；按接口借用期约定处理异步保存场景。
- 验证方向: 保留回调内容断言，并补充元素引用归还/重复查询的生命周期检查；若只做 RSS 观测，应作为辅助证据，不以单次 RSS 波动定论。

- 证据与行为: `queryAccount()` 入队后调用 `triggerQuery()`（`:431-442`）；其余三个入口只入队并返回（`:453-463`, `:473-484`, `:494-505`）。`triggerQuery()` 才会向 strand 投递处理当前队首的闭包（`:1152-1179`）；worker 运行 `io_context` 并不会自行扫描 `m_queQuery`。因此独立调用这三个入口时请求不会由该入口启动；之后若账户查询或其他查询应答结束触发队列，待处理任务才可能继续，不能写成无条件“永不发送”。

## BUG-R93-004 TraderXTP::disconnect 后 isConnected() 仍返回 true

- 严重级别: Major（断开后连接状态残留）
- 模块/文件: `src/TraderXTP/TraderXTP.cpp:623-640`、`:707-715`

- 输入/前置条件: 登录完成后 `_state == TS_ALLREADY`，调用 `disconnect()`。

- 影响边界: 上层用 `isConnected()` 判断状态会得到过期结果。断开后 query API 空指针风险已在既有 T5-02 登记，本条只登记断开状态未更新，不重复计数该空指针问题。

- 验证方向: 启用对应 stub 测试，设置 ALLREADY 后断开并检查 `isConnected()==false`；再验证重复断开和重新登录状态转换。

## BUG-R93-005 TraderXTP 的 worker 无退出路径，release/析构不停止或 join

- 状态: 源码生命周期缺陷确认；本轮未运行线程/析构测试
- 严重级别: Major（worker 生命周期无法随连接对象结束）
- 模块/文件: `src/TraderXTP/TraderXTP.cpp:184-186`、`:623-640`、`:688-710`；成员声明 `src/TraderXTP/TraderXTP.h:142-145`
- 相关测试: `r93_traderXTP_api_test.cpp:214-218,235-258` 的 `preset_worker()` 放入一个默认构造、不可 join 的 `std::thread`，让 `connect()` 跳过真实 worker 创建；该测试不覆盖真实线程停止或析构。本轮未运行测试。
- 输入/前置条件: 正常调用 `connect()`，创建 `_thrd_worker` 后调用 `disconnect()/release()`，随后销毁对象。
- 证据与行为: `connect()` 设置 work guard，并启动 `while (true)` 循环，循环中 sleep 后调用 `_asyncio.run_one()`（`:688-705`）。循环没有退出条件；`release()` 不 stop `io_context`、不 reset work guard、也不 join worker（`:623-640`），析构函数为空（`:184-186`）。`StdThreadPtr` 是 `std::shared_ptr<std::thread>`（`src/Share/StdUtils.hpp:23-24`），且唯一成员线程仍 joinable 时，其析构会触发 `std::terminate`。持有 work guard 时空闲 `run_one()` 会等待工作，不应据代码称为每 2ms 空转；已能确认的是线程无法按当前路径正常退出。
- 影响边界: 断开不代表 worker 已结束；对象销毁存在 joinable thread 终止风险。`OnDisconnected()` 还会投递延迟 `doLogin()` 的闭包（`:345-354`），停止期间需同时处理闭包访问对象的生命周期。本轮没有观察实际进程退出表现。
- 可操作修复: 增加可同步读取的停止状态；release 时阻止新的重连/登录闭包、停止或唤醒 `io_context`，随后在非 worker 自身线程上 join，再释放 API 和对象状态。若支持 reconnect，重新启动前显式恢复 `io_context` 与 work guard，并避免旧代异步闭包触碰对象。
- 验证方向: 不预置空线程；通过 stub 确认真实 worker 可启动、disconnect 后退出且可 join，再销毁对象并检查无 terminate。另测 pending reconnect 回调在释放后不会访问已销毁对象。

## BUG-R93-006 TraderYD 的 CM_OpenCover 冻结/撤单释放算式错误

- 状态: 本地 stub 撤单回补回归 FAIL；混合仓与真实柜台未验证
- 严重级别: Major（混合今昨仓时冻结不足；撤单可留下未恢复的可用持仓）
- 模块/文件: `src/TraderYD/TraderYD.cpp:444-473`（首次平仓冻结）、`:481-513`（撤单释放）
- 相关测试: `open_cover_order_freezes_yesterday_available` 现验证同一订单 6101 撤单前可用仓 `1/0`、终态为 canceled、撤单后应恢复 `5/0`；本地定向 FAIL，撤单后 `availPre` 实际仍为 1。原重复禁用用例已合并。该用例只验证昨仓回补，混合今昨仓冻结路径仍为源码推演。
- 证据与行为: 首次冻结处计算 `maxQty=min(availPre, volume)` 并从昨仓扣减（`:464-465`），随后条件为 `volume < maxQty`（`:466`）。因为 `maxQty <= volume`，该条件不可达，今仓不会承担剩余冻结。例如 `availPre=2, availNew=3, volume=4` 时，按代码只冻结 2 手昨仓，今仓仍全部可用；此混合仓例仍是源码推演。撤单处计算 `maxQty=min(newQty-availNew, untrade)`，先加回今仓（`:503-504`），后续条件 `untrade < maxQty` 同样不可达（`:505-508`）；昨仓 5、今仓 0、委托 4 的本地替身用例已观测撤单后未回补。
- 可操作修复: 冻结时先扣 `min(availPre, volume)`，再将剩余量扣今仓；同时校验可用持仓不足时的拒单/截断语义。撤单释放应依据该委托最初从今仓和昨仓各冻结多少，按未成交部分分别回补；建议为每笔委托保留冻结来源，避免从更新后的可用余额反推来源。
- 验证方向: 保留已启用的撤单回补回归；另加混合仓测试 `pre=2,new=3,volume=4`，检查冻结后 `pre=0,new=1`、零成交撤单后恢复 `pre=2,new=3`。再覆盖部分成交，只恢复未成交冻结量。现有 `pre=5,new=0` 测试不能作为混合仓冻结缺陷的动态证据。
