## BUG-R93-001 TraderYD::extractEntrustID 对「不含 #」的委托号越界读

- 状态: 待审核
- 严重级别: Blocker（未定义行为，可能崩溃/脏 OrderRef）
- 模块/文件: `src/TraderYD/TraderYD.cpp:1101-1112`
- 相关测试: 未启用；`r93_traderYD_api_test.cpp` 的
  `order_insert_and_cancel_fill_yd_requests` 用双 `#` 串（`yduser#1#2`）覆盖安全拒绝面，
  并注释了本缺陷。
- 输入/前置条件: `m_wrapperState == WS_ALLREADY`，调用
  `orderAction(action)` 且 `action->getEntrustID()` 中没有任何 `'#'`，例如
  `"no_separator_here"`。
- 期望行为: 解析失败返回 false，`orderAction` 返回 -1，不调用厂商 API。
- 实际行为: `StrUtil::findFirst` 与 `StrUtil::findLast` 都返回 `std::string::npos`；
  两者相等，`if (idx != idx2)` 不触发；随后执行
  `convert::to_uint32(entrustid + idx + 1)`，指针为 `entrustid + npos + 1`，
  越界读任意内存并得到不确定的 `orderRef`。函数返回 true，继续走
  `getInstrumentByID`/`cancelOrder`。
- 复现步骤: 构造 `TraderYD`（注册 sink、`notifyCaughtUp()` 置 ALLREADY、任意非空 `m_pUserAPI`），
  `WTSEntrustAction::create()` 后 `setEntrustID("no_separator_here")`，调用 `orderAction`。
  ASan 下报 heap/global-buffer-overflow；非 ASan 下行为不确定。
- 影响范围: 上层传入非本系统格式的委托号（人工撤单、迁移缓存、脏数据）即可能崩溃或发错撤单。
- 备注: 修复方向=先判 `idx == std::string::npos` 再解析；现有 T5 用例只注释了该路径未执行。

## BUG-R93-002 TraderYD 的 queryOrders/queryTrades 泄漏回报数组

- 状态: 待审核
- 严重级别: Major（每次查询稳定泄漏）
- 模块/文件: `src/TraderYD/TraderYD.cpp:915-938`（`queryOrders`）、`:940-963`（`queryTrades`）；
  对照 `queryPositions` 在 `:908` 有 `ayPos->release()`。
- 相关测试: `r93_traderYD_api_test.cpp` 的
  `cache_roundtrip_marks_orders_and_trades_and_queries_arrays`（调用两个查询并读取回调）。
- 输入/前置条件: 已 catchup（ALLREADY），`m_mapOrders`/`m_mapTrades` 非空，执行
  `queryOrders()`/`queryTrades()` 的队列 lambda。
- 期望行为: 与 `queryPositions` 一致，回调返回后 `ayOrders->release()` / `ayTrades->release()`；
  数组内元素以 `append(..., true)` 增过引用，释放数组时归还原引用。
- 实际行为: `queryOrders` 创建 `WTSArray`、逐项 `append(it->second, true)`、回调后既不
  `clear()` 也不 `release()`；`queryTrades` 同样。每查询一次泄漏一个 `WTSArray`，
  并使其中的订单/成交对象引用计数永久 +1（`m_mapOrders`/`m_mapTrades` 释放时也回收不掉）。
- 复现步骤: 先推入 1 条订单/成交，循环 1000 次 `queryOrders()`/`queryTrades()` 并执行队列，
  观察 RSS 与 `WTSObject` 池占用单调上升；`queryPositions()` 同条件不增长。
- 影响范围: TraderAdapter 定时查询订单/成交的通道长期运行内存持续增长。
- 备注: 修复方向=照抄 `queryPositions` 的 `ay->release()`；若担心 sink 持有，可先 `clear()`。

## BUG-R93-003 TraderFemas 只有 queryAccount 触发查询队列，其余三个查询永不发送

- 状态: 待审核
- 严重级别: Blocker（持仓/订单/成交查询功能失效）
- 模块/文件: `src/TraderFemas/TraderFemas.cpp:424-506`；`triggerQuery` 在 `:1152-1180`，
  仅在 `queryAccount`（`:441`）之后调用。
- 相关测试: `r93_traderFemas_api_test.cpp` 的 `query_entries_assemble_requests`。
  该用例对 `queryPositions/Orders/Trades` 只能由测试探针手工 `runNextQuery()` 出队，
  证明三个 lambda 本身能组装正确请求，但产品路径不会主动执行它们。
- 输入/前置条件: 已 `connect()`（`m_strandIO` 非空、worker 跑 `m_asyncIO.run_one()`），
  状态 ALLREADY；只调用 `queryPositions()`（或 queryOrders/queryTrades），不调用 queryAccount。
- 期望行为: 查询请求入队后立即 `triggerQuery()`，worker 取出并调用
  `ReqQryInvestorPosition/ReqQryOrder/ReqQryTrade`。
- 实际行为: 三个函数只 `m_queQuery.push(...)`，没有 `triggerQuery()`。`connect()` 的 worker
  只执行 `m_asyncIO.run_one()`，不会主动扫描队列；唯一投递 `triggerQuery` 的是
  `queryAccount` 以及四个 `OnRspQry*` 的 `bIsLast` 分支。因此单独调用持仓/订单/成交查询时，
  请求永远留在队列里；只有恰好有资金查询或查询应答收尾时才会被顺带带走一条。
- 复现步骤: connect 成功后只调用 `queryPositions()`，等待任意时长，stub/真实 API 的
  `ReqQryInvestorPosition` 调用数保持 0；再调用 `queryAccount()` 后才可能看到队列推进。
- 影响范围: TraderAdapter 的持仓/订单/成交同步在 Femas 通道上整体失效或严重滞后。
- 备注: 修复方向=三个入口与 `queryAccount` 一样在 push 后调用 `triggerQuery()`；
  与 BUG-T4-003（strand 未初始化）相邻但不同。

## BUG-R93-004 TraderXTP::disconnect 后 isConnected() 仍为 true

- 状态: 待审核
- 严重级别: Major（连接状态失真）
- 模块/文件: `src/TraderXTP/TraderXTP.cpp:707-710`（`disconnect()` 只调 `release()`）、
  `:623-640`（`release` 未重置 `_state`）、`:712-715`（`isConnected` 只读 `_state`）。
- 相关测试: `r93_traderXTP_api_test.cpp` 的
  `DISABLED_disconnect_should_reset_connected_state`（现状会失败，故禁用）。
- 输入/前置条件: `_state == TS_ALLREADY`（登录成功后），调用 `disconnect()`。
- 期望行为: `disconnect()` 后 `isConnected() == false`，后续业务入口按未连接处理。
- 实际行为: `release()` 只清 `_api` 与 `_orders/_positions/_trades`，`_state` 保持
  `TS_ALLREADY`；`isConnected()` 返回 true。上层若以 `isConnected()` 做健康检查会认为
  通道仍可用，但 `_api` 已是 NULL，`orderInsert/orderAction` 返回 -1，
  四个 `query*` 则直接空指针解引用（见 T5-02）。
- 复现步骤: 用 stub 完成登录→ALLREADY，调用 `disconnect()`，断言
  `api.isConnected()`；实际为 true。
- 影响范围: 断线/主动下线后的状态机与重连决策；与 T5-02 组合会把「查询」变成崩溃。
- 备注: 修复方向=`release()` 末尾置 `_state = TS_NOTLOGIN`（并考虑 `_inited=false`）。

## BUG-R93-005 TraderXTP::connect 的 worker 线程没有停止条件，release 也不 join

- 状态: 待审核
- 严重级别: Major（线程泄漏/退出挂起）
- 模块/文件: `src/TraderXTP/TraderXTP.cpp:688-705`（`while (true)` + `sleep_for(2ms)` +
  `_asyncio.run_one()`）、`:623-640`（release 未 `stop()`/`join()`）、`:707-710`（disconnect 只 release）。
- 相关测试: 本 lane 未启用；`r93_traderXTP_api_test.cpp` 在 connect 用例中预置已 detach 的
  空线程，绕开该线程体（manifest 留白第 2 条）。
- 输入/前置条件: 正常调用 `connect()` 后再 `disconnect()`/`release()`。
- 期望行为: 有停止标志或 `_asyncio.stop()`，release 时 worker 退出并可 join；
  进程退出/重连不遗留线程。
- 实际行为: 线程函数是 `while (true)`，无停止条件；`_asyncio` 也从未 `stop()`。
  `release()` 只释放 `_api` 并清容器，`_thrd_worker` 仍 joinable 且持续每 2ms 空转。
  对象析构时 `StdThreadPtr`（`std::thread`）若仍 joinable 会 `std::terminate`。
- 复现步骤: 真实调用 `connect()`（stub creator 亦可）→ `disconnect()` → 观察线程仍存活；
  让 `TraderXTP` 析构可触发 terminate。
- 影响范围: 进程无法干净退出、反复重连累积线程；与 `OnDisconnected` 的 2s 重投（L350-354）
  组合更明显。
- 备注: 修复方向=增加 `_stopped` 原子标志，release 中 `_asyncio.stop()` 后 join；
  与 Femas 的同类 worker 留白（T4 manifest）相邻但独立。

## BUG-R93-006 TraderYD 的 CM_OpenCover 平仓冻结/撤单释放算式错误

- 状态: 待审核
- 严重级别: Major（可用持仓错误，可能超卖/超平）
- 模块/文件: `src/TraderYD/TraderYD.cpp:461-470`（首推冻结）、`:500-509`（撤单释放）。
- 相关测试: `r93_traderYD_api_test.cpp` 的
  `open_cover_order_freezes_yesterday_available`（只验证冻结面）；
  `DISABLED_open_cover_cancel_should_release_yesterday_freeze` 是修复后期望的哨兵
  （撤单后 availPre 应为 5，现状为 1）。
- 输入/前置条件: 品种 `getCoverMode() == CM_OpenCover`；昨仓 `availPre=5, availNew=0`；
  推一条 `WOT_CLOSE, volume=4` 的平仓委托，再推同一 OrderSysID 的 `Canceled, TradeVolume=0`。
- 期望行为:
  - 冻结：昨仓不足时先冻昨仓、剩余从今仓冻结（`availPre: 5→1`，`availNew` 相应减少）；
  - 撤单：按原冻结来源回补 4 手，`availPre` 回到 5。
- 实际行为:
  - 冻结：`maxQty = min(availPre, volume)` 后 `availPre -= maxQty`，随后判断
    `decimal::lt(volume, maxQty)`——由于 `maxQty <= volume`，该条件恒假，今仓永远不参与冻结，
    昨仓不足时可用量被多扣/少扣；
  - 撤单：`maxQty = min(newQty - availNew, untrade)` 以「今仓可用」为基数，且
    `decimal::lt(untrade, maxQty)` 同样恒假；昨仓被冻结的 4 手不会回补，
    `availPre` 停在 1。
- 复现步骤: 按上面输入推两次 `notifyOrder`，每步 `queryPositions()` 读 `availPre/availNew`
  （本 lane 实测冻结后 `1/0`，撤单后仍 `1/0`）。
- 影响范围: 不区分平今平昨的品种（CM_OpenCover）撤单后可用持仓永久减少，
  后续平仓可能被风控拒绝或被上层误判为可平数量。
- 备注: 修复方向=冻结按 `availPre/availNew` 顺序扣减，释放按原冻结来源回补；
  两个 `decimal::lt` 的参数顺序也应重新核对（当前内层分支逻辑上不可达）。

## BUG-R93-007 TraderXTP 构造函数漏初始化 _state（及 _sessionid）

- 状态: 待审核
- 严重级别: Major（未定义行为/连接状态误判）
- 模块/文件: `src/TraderXTP/TraderXTP.cpp:169-181`（初始化列表），成员声明
  `src/TraderXTP/TraderXTP.h:135-137`。
- 相关测试: 未启用；本 lane 的 XTP 用例都在登录或 `make_ready()` 里显式写 `_state`，
  不读取构造后的初值。
- 输入/前置条件: `new TraderXTP()`（或 `init()` 之后、`login()` 之前）调用 `isConnected()`。
- 期望行为: `_state` 初值为 `TS_NOTLOGIN`，`_sessionid` 初值为 0；`isConnected()` 稳定返回 false。
- 实际行为: 初始化列表覆盖了 `_api/_sink/_positions/_trades/_orders/_bd_mgr/_inited/_tradingday/_reqid/_ordref`，
  漏掉 `_state`、`_sessionid`（以及由 `init()` 赋值的 `_quick/_hbInterval/_port/_client` 在
  init 之前也不确定）。`isConnected()` 只读 `_state`，构造后即读未初始化值；
  `orderInsert/orderAction` 的 `_state != TS_ALLREADY` 守卫同样可能被随机值绕过。
- 复现步骤: `TraderXTP api; api.isConnected();` 在 ASan/MSan 或不同栈布局下结果不稳定；
  同一进程多次构造也可能出现 true/false 漂移。
- 影响范围: 启动早期健康检查、连接守卫的判定不确定；与 BUG-R93-004 的状态残留叠加。
- 备注: 修复方向=构造函数补 `_state(TS_NOTLOGIN), _sessionid(0), _port(0), _client(0),
  _quick(false), _hbInterval(0)`（后四项 init 会覆盖）。
