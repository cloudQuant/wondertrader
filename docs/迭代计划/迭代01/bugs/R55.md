## BUG-R55-001

- 状态: 源码确认；本次未运行 MemorySanitizer/Valgrind
- 严重级别: Minor
- 模块/文件: `src/Share/charconv.hpp` `UTF8toChar::init`（L85-98）/`~UTF8toChar`（L167-171）；`ChartoUTF8::init`（L257-270）/`~ChartoUTF8`（L341-345）
- 相关测试: `r55_codehelper_charconv_test.cpp: R55_charconv.utf8_helpers_handle_empty_and_null_inputs`
- 输入/前置条件: `UTF8toChar u(static_cast<const char*>(nullptr));`、`ChartoUTF8 c(static_cast<const char*>(nullptr));`
- 期望行为: 空指针分支显式设置 `needFree = false`，析构时的分支判断有确定值。
- 实际行为: 两个类的成员声明均为裸 `bool needFree`；空指针分支只把字符串指针置空，析构函数仍读取未初始化 bool，属于未定义行为。`delete[] nullptr` 是 no-op 不能消除之前对 bool 的未初始化读取。
- 复现步骤: 空指针构造后离开作用域会执行该读取；MemorySanitizer/Valgrind 可能报告未初始化条件分支。本次未运行消毒器，不能把报告写成已观察到的运行结果。
- 影响范围: 传入 nullptr 的调用点。现有 R55 启用用例自身就构造了两个空指针对象并在作用域结束时析构，因此该测试执行时也进入 UB；普通断言值不能证明析构路径安全。
- 修复方向: 在两个类的构造/成员初始化处将 `needFree` 初始化为 false，转换分配成功后再置 true。
- 备注: 不阻塞覆盖率目标；删除“后续指针改成非空默认值会非法释放”的推测性影响描述。

## BUG-R55-002

- 状态: 源码确认；本次未运行测试
- 严重级别: Major
- 模块/文件: `src/Share/charconv.hpp` `EncodingHelper::isUtf8`（L635-669，判定条件在 L645）
- 相关测试: `r55_codehelper_charconv_test.cpp: R55_charconv.encoding_helper_two_byte_and_gbk_boundaries`（锁定实际 false）、`R55_charconv.DISABLED_two_byte_utf8_should_be_accepted`（期望行为）；已有 `r12_charconv_safe_test.cpp: r12_charconv_encoding_helper.isutf8_valid_sequences` 对 `{0xC3,0xA9}` 断言 true，与当前实现冲突
- 输入/前置条件: `unsigned char data[] = {0xC2, 0xA2}`（U+00A2，合法 2 字节 UTF-8）；同理 `{0xC3, 0xA9}`（é）
- 期望行为: 返回 `true`（或至少继续扫描后续字节）
- 实际行为: `(num = preNUm(data[i])) > 2` 把 `num == 2` 排除在多字节分支之外，直接落到 `else { return false; }`，任何以 2 字节 UTF-8 开头的非 ASCII 文本都被判成非 UTF-8
- 复现步骤: `EncodingHelper::isUtf8(data, 2)`，输入 `C2 A2`，实际返回 `false`
- 影响范围: 调用点包括 `WTSCfgLoader.cpp:266,309`、`CTPLoader.cpp:236` 和 CTP 回报转换路径；它们把 false 作为需要 `ChartoUTF8` 转码的信号。仅含合法 2 字节 UTF-8 的配置/名称可能因此按本地编码转换。原文关于 `isGBK` 强化误判不属于这些调用路径，撤下。
- 修复方向: 按合法 UTF-8 首字节范围接受 2 至 4 字节序列，并检查续字节、截断边界及 Unicode 标量限制。
- 本轮证据: 已把 R55 将合法两字节编码断言为 false 的错误测试改为 true；`R55_charconv.two_byte_utf8_is_accepted` 单独运行 FAIL（实际 false），非法边界对照 PASS。

## BUG-R55-003

- 状态: 源码确认；逻辑长度测试本机复现，未运行 sanitizer
- 严重级别: Major
- 模块/文件: `src/Share/charconv.hpp` `EncodingHelper::isUtf8`（L635-669，续字节循环在 L653-660）
- 相关测试: `r12_charconv_encoding_helper.isutf8_rejects_sequence_truncated_by_logical_length` 使用物理四字节、逻辑长度三字节的有效输入，边界外放置合法续字节；单独运行 FAIL（实际 true）。此前精确三字节数组作为调用方输入本身有效，但产品实现读取 `data[3]` 导致物理越界，旧测试结果不能作为确定性安全证据。
- 输入/前置条件: `unsigned char data[] = {0xE4, 0xB8}`（截断的 3 字节“中”）、`{0xF0, 0x9F, 0x98}`（截断的 4 字节 emoji）
- 期望行为: 读取续字节前验证余下输入长度足够，截断序列返回 `false`。若当前 `i` 已在消费 lead byte 后递增，应检查 `num - 1 <= len - i`。
- 实际行为: `i++` 后直接进入 `for (j = 0; j < num - 1; j++)`，循环体只判断 `(data[i] & 0xc0) != 0x80`，没有 `i < len` 边界；`{E4,B8}` 会读取 `data[2]`（越界 1 字节），`{F0,9F,98}` 会读取 `data[3]`（越界 1 字节）
- 复现步骤: 对长度恰好等于数组容量的 2-byte buffer `{0xE4,0xB8}`，当前代码会访问 `data[2]`；ASan 在精确边界缓冲区上可检测越界。本次未运行 ASan。若调用者传的是 `std::string::data()`，其末尾 NUL 可能掩盖物理越界，但访问仍超出传入的 `len`。
- 影响范围: 所有以恰好 `len` 字节存储的截断输入均有越界读风险。与 `isGBK` 越界读是不同函数，不与 `BUG-L01-005` 合并；现有 R12 测试包含该触发条件，但其断言含 UB。
- 修复方向: 对 lead byte 支持的字节数做合法范围校验，再用剩余长度差检查续字节数量；循环条件同时保持 `i < len`。
- 备注: 修正后的测试仅安全地复现忽略逻辑长度，未证明精确物理边界上的运行时越界；本次未运行 sanitizer。
