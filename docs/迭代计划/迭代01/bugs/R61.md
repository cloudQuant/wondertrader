# lane R61 缺陷登记 — TraderCTPOpt / TraderCTPMini

本 lane 只登记生产缺陷。后续复核已把固化错误行为的部分测试改成正确契约断言；未修改生产代码。

本 lane 与既有登记的交叉：T1-CTPOpt-01/02/03/05、T3-MINI-006/007/008 已覆盖的缺陷不重复登记；
下列 5 条是候选记录。审计后，003 的字段转发错误可由源码和 stub 回调序列确认；001/002 是源码可推导的 join 阻塞，测试为避开挂起而使用空线程，并未动态触发；004/005 的直接调用现象可复现，但是否违反公开调用契约尚未确认。

## 审计裁定（2026-10-29）

- **BUG-R61-001/002：源码推导，不是本轮动态挂起证据。** 两个 `release()` 都不置 `m_bStopped`，实际 `connect()` 起的 worker 在处理释放 lambda 后仍循环；`disconnect()` 的 `join()` 因而无退出条件。manifest 说明测试预置了空线程并手工 drain 队列，所以这两个用例只证明请求组装/释放调用，不证明真实 worker 已运行时的 hang。修复方向需同时停止循环、清理 API 并 join；补测应在隔离子进程或带可靠超时的外层中验证真实 worker。
- **BUG-R61-003：确认的实现错误。** `OnRspQryExecOrder` 收集在 `m_ayExecOrds`，末帧却把普通订单容器 `m_ayOrders` 交给期权 sink，并立即清空行权数组。测试先证明行权数组已有数据，再观察到错容器，根因和回调参数均明确；尚未连接真实柜台，但不影响该本地转发错误的确定性。
- **BUG-R61-004/005：同一引用分配模式的条件候选，尚不能定为正常生产流程缺陷。** 无 tag 分支确实用 `fetch_add(0)`，如果低层调用方连续直接调用 `orderInsert*` 且从未先调用 `makeEntrustID`，会重复使用当前值。测试正是通过 probe 直接调用并把计数器设为 0。常规 `TraderAdapter::doEntrust`（`src/WtCore/TraderAdapter.cpp:487-508`）会先调用 `makeEntrustID`，再写入非空 userTag；当前测试没有经过这一接口路径。`ITraderApi` 文档未说明直接调用必须先分配 entrust ID，也未说明无 tag 是否合法，故应先确认调用契约并覆盖 adapter 路径，不能直接把柜台拒单/错撤作为已证影响。
- 004 与 005 是 Opt/Mini 两处同型 `fetch_add(0)` 的模块表现，可同组跟踪为一个分配契约问题，不应当作两个独立机制；两个实现仍需分别验证和修复。

## BUG-R61-001 `TraderCTPOpt::disconnect()` 无法结束查询线程，停服路径永久挂起

- 状态: 待审核
- 严重级别: 高（真实 worker 条件下 join 无退出条件；源码推导，测试未实际运行该线程）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:365-376`（disconnect）；`331-362`（线程体，`while (!m_bStopped)` 在 L334）；`TraderCTPOpt.cpp:234` 是 `m_bStopped(false)` 的唯一写入
- 相关测试: `R61_TraderCTPOpt.connect_subscribes_topics_and_disconnect_releases_api`
- 输入/前置条件: 正常 `connect()`（会创建 worker 线程），随后调用 `disconnect()`
- 期望行为: `disconnect()` 置停止标志或从队列取出 release 后让线程退出，`join()` 在有限时间内返回
- 实际行为: `m_bStopped` 在整个文件里只有构造时置 `false`，没有任何置 `true` 的路径；
  worker 处理完 `release` lambda 后继续 `while (!m_bStopped)` 空转，`m_thrdWorker->join()`（L373）永久阻塞
- 源码推导步骤（非本轮动态复现）:
  1. 用真实/测试 creator 让 `connect()` 成功；
  2. 调 `disconnect()`；
  3. 观察进程卡在 `join()`（本 lane 为绕开该缺陷，在 connect 前把 `m_thrdWorker` 换成空线程）
- 影响范围: 任何调用 `disconnect()` 的停服/重连流程（`TraderAdapter::release` 等）会挂死；
  实盘进程无法优雅退出，只能被强杀
- 备注: T1-CTPOpt-05 已指出线程「以 m_bStopped 为唯一出口」，但未登记 disconnect 挂死；
  该缺陷也是本 lane 不能直接覆盖 worker 线程体的原因

## BUG-R61-003 期权行权委托查询把普通订单数组回传给 `onRspOrdersOpt`

- 状态: 待审核
- 严重级别: 高（行权委托查询结果全部丢失，且回调类型错位）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:1068-1096`，L1091 `m_optSink->onRspOrdersOpt(m_ayOrders);`，L1093-1094 紧接着 `m_ayExecOrds->clear()`
- 相关测试: `R61_TraderCTPOpt.query_entries_enqueue_requests_drained_locally`
- 输入/前置条件: 先收到一帧 `OnRspQryExecOrder`（有效 `CThostFtdcExecOrderField`，非末帧，`m_ayExecOrds` 已 append 1 条），再收到末帧
- 期望行为: 末帧应把 `m_ayExecOrds`（行权委托列表）传给 `onRspOrdersOpt`，再清空
- 实际行为: 传的是 `m_ayOrders`（普通订单查询的容器，本场景为已清空的 0 长度数组）；
  `m_ayExecOrds` 里的行权委托从未交付即被 `clear()`
- 复现步骤:
  1. `OnRspQryExecOrder(&eo, NULL, 1, false)` → `m_ayExecOrds->size()==1`；
  2. `OnRspQryExecOrder(&eo, NULL, 1, true)`；

- 后续定向复测: 旧测试将收到 0 条写成通过条件；现改为要求两帧有效行权单返回 2 条。重建 `CoverageTests_t_TraderCTPOpt` 并独立运行 `R61_TraderCTPOpt.query_entries_enqueue_requests_drained_locally`，FAIL：option sink 实际收到 0 条。前面的普通订单、成交、错误帧及 API release 断言未失败；这是本地 stub，不证明真实柜台行为。
- 影响范围: 上层期权行权模块查询不到任何行权委托（UI/对账/风控全部失真）；查询结果被静默丢弃
- 备注: T1 的旧用例只断言了「转发的是 m_ayOrders、size 0」，未登记为缺陷；本 lane 用
  `ayExecOrds()` 探针证明 append 确实发生过（size 1），再证明交付为 0

## BUG-R61-004 无 userTag 且未预留 entrust ID 的直接调用复用当前 `OrderRef/ExecOrderRef`

- 状态: 已合并（迭代02：主编号 T2-CTP-08）
- 严重级别: 未定级（条件性引用重复候选）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:629`（`orderInsert`，`m_orderRef.fetch_add(0)`）；
  `TraderCTPOpt.cpp:499`（`orderInsertOpt`，同写法）
- 相关测试: `R61_TraderCTPOpt.order_insert_and_cancel_fill_ctp_requests`、
  `R61_TraderCTPOpt.option_exec_order_paths_fill_ctp_requests`
- 输入/前置条件: 调用方绕过 `TraderAdapter::doEntrust`，未调用 `makeEntrustID` 预留引用，且直接送入多个 `userTag` 为空的委托
- 期望行为: 取决于公开契约：若低层 API 允许此调用，应保证引用唯一；若调用方必须先预留 `entrustID`，应在 `ITraderApi` 文档及入口校验中明确。
- 实际行为: 无 tag 分支 `fetch_add(0)` 返回当前值但不递增；stub 直调、计数器初值为 0 时观察到相同的 `"0"`。标准 `TraderAdapter::doEntrust` 会先调用 `makeEntrustID` 并设置非空 tag，因此本测试未覆盖标准路径。
- 复现步骤:
  1. `setIds(5, 6, 0)`、state=ALLREADY、注入 API stub；
  2. 构造两个 userTag 为空的 `WTSEntrust`，连续 `orderInsert`；
  3. stub 捕获的 `OrderRef` 两次都为 `"0"`（`orderInsertOpt` 同理）
- 影响范围: 仅在允许上述未预留引用的直接调用时，可能造成同一 session 引用冲突；柜台拒单或错撤属于协议后果推断，当前无真实柜台证据。
- 备注: 带 userTag 路径由 entrust ID 第三段提供引用。修复前先明确调用者的引用分配责任；若要支持不预留的直接调用，入口需分配唯一值或消费 entrustID，而非仅以 `fetch_add(1)` 盲增。


- 迭代02复核: DUPLICATE。空 userTag 分支 fetch_add(0) 不推进 OrderRef/ExecOrderRef；公开 ITraderApi::orderInsert 没有要求必须先 makeEntrustID 的前置契约，空 tag 也是显式支持分支。标准 adapter 先填 ID 的路径不能消除直接接口调用的重复引用风险。与 T2-CTP-08 同根。
- 迭代02依据: [逐条裁定与主代理修订](../../迭代02/缺陷裁定总表.md)。原记录保留作为历史，未声称产品已修复。
- 迭代02前状态（历史）: - 状态: 待接口调用契约确认（直接调用现象成立，正常 adapter 路径不适用）
