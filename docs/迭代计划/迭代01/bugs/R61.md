## BUG-R61-001 `TraderCTPOpt::disconnect()` 无法结束查询线程，停服路径永久挂起

- 状态: 待审核
- 严重级别: 高（进程无法退出）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:365-376`（disconnect）；`331-362`（线程体，`while (!m_bStopped)` 在 L334）；`TraderCTPOpt.cpp:234` 是 `m_bStopped(false)` 的唯一写入
- 相关测试: `R61_TraderCTPOpt.connect_subscribes_topics_and_disconnect_releases_api`
- 输入/前置条件: 正常 `connect()`（会创建 worker 线程），随后调用 `disconnect()`
- 期望行为: `disconnect()` 置停止标志或从队列取出 release 后让线程退出，`join()` 在有限时间内返回
- 实际行为: `m_bStopped` 在整个文件里只有构造时置 `false`，没有任何置 `true` 的路径；
  worker 处理完 `release` lambda 后继续 `while (!m_bStopped)` 空转，`m_thrdWorker->join()`（L373）永久阻塞
- 复现步骤:
  1. 用真实/测试 creator 让 `connect()` 成功；
  2. 调 `disconnect()`；
  3. 观察进程卡在 `join()`（本 lane 为绕开该缺陷，在 connect 前把 `m_thrdWorker` 换成空线程）
- 影响范围: 任何调用 `disconnect()` 的停服/重连流程（`TraderAdapter::release` 等）会挂死；
  实盘进程无法优雅退出，只能被强杀
- 备注: T1-CTPOpt-05 已指出线程「以 m_bStopped 为唯一出口」，但未登记 disconnect 挂死；
  该缺陷也是本 lane 不能直接覆盖 worker 线程体的原因

## BUG-R61-003 期权行权委托查询把普通订单数组回传给 `onRspOrdersOpt`

- 状态: 待审核
- 严重级别: 高（行权委托查询结果全部丢失，且回调类型错位）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:1068-1096`，L1091 `m_optSink->onRspOrdersOpt(m_ayOrders);`，L1093-1094 紧接着 `m_ayExecOrds->clear()`
- 相关测试: `R61_TraderCTPOpt.query_entries_enqueue_requests_drained_locally`
- 输入/前置条件: 先收到一帧 `OnRspQryExecOrder`（有效 `CThostFtdcExecOrderField`，非末帧，`m_ayExecOrds` 已 append 1 条），再收到末帧
- 期望行为: 末帧应把 `m_ayExecOrds`（行权委托列表）传给 `onRspOrdersOpt`，再清空
- 实际行为: 传的是 `m_ayOrders`（普通订单查询的容器，本场景为已清空的 0 长度数组）；
  `m_ayExecOrds` 里的行权委托从未交付即被 `clear()`
- 复现步骤:
  1. `OnRspQryExecOrder(&eo, NULL, 1, false)` → `m_ayExecOrds->size()==1`；
  2. `OnRspQryExecOrder(&eo, NULL, 1, true)`；
  3. `IOptTraderSpi::onRspOrdersOpt` 收到的数组 size 为 0
- 影响范围: 上层期权行权模块查询不到任何行权委托（UI/对账/风控全部失真）；查询结果被静默丢弃
- 备注: T1 的旧用例只断言了「转发的是 m_ayOrders、size 0」，未登记为缺陷；本 lane 用
  `ayExecOrds()` 探针证明 append 确实发生过（size 1），再证明交付为 0

## BUG-R61-004 无 userTag 的委托复用同一 `OrderRef/ExecOrderRef`

- 状态: 待审核
- 严重级别: 高（报单引用重复，柜台拒单或撤单错单）
- 产品文件: `src/TraderCTPOpt/TraderCTPOpt.cpp:629`（`orderInsert`，`m_orderRef.fetch_add(0)`）；
  `TraderCTPOpt.cpp:499`（`orderInsertOpt`，同写法）
- 相关测试: `R61_TraderCTPOpt.order_insert_and_cancel_fill_ctp_requests`、
  `R61_TraderCTPOpt.option_exec_order_paths_fill_ctp_requests`
- 输入/前置条件: `m_orderRef` 初值 0（登录后为 `MaxOrderRef`），连续下两笔 `userTag` 为空的委托
- 期望行为: 每笔委托的 `OrderRef/ExecOrderRef` 唯一（至少自增 1），与 `makeEntrustID` 的
  `m_orderRef.fetch_add(1) + 1` 语义一致
- 实际行为: `fetch_add(0)` 返回当前值但不递增 → 两笔委托都写同一个引用（用例实测均为 `"0"`）；
  只有带 userTag 的委托才从 entrustID 第三段取到不同引用
- 复现步骤:
  1. `setIds(5, 6, 0)`、state=ALLREADY、注入 API stub；
  2. 构造两个 userTag 为空的 `WTSEntrust`，连续 `orderInsert`；
  3. stub 捕获的 `OrderRef` 两次都为 `"0"`（`orderInsertOpt` 同理）
- 影响范围: 同一 session 内多笔无标签委托共用报单引用，CTP 侧会以「报单引用重复」拒单；
  即便成交，撤单按 `OrderRef` 定位也会撤错单
- 备注: 带 userTag 的路径正常；修复方向应为 `fetch_add(1) + 1`，但本迭代只登记不修
