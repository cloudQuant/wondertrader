  `:113`（`initDataMgr();` 返回值丢弃）、`:195`（`initUftStrategies();` 返回值丢弃）；

  `_tm_ticker/_cfg/_notifier`，`_base_data_mgr/_data_mgr`（`WtUftEngine.h:133-134`）没有初值；
  只有 `initEngine()` 成功调用 engine.init 才赋这两个字段。若仅缺 `data` 而 `env` 存在，engine 的
  `_data_mgr` 指向 runner 成员对象，但 `WtUftDtMgr::init` 被跳过，其 `_engine` 保持 NULL。
- 相关测试: R14 已修正的用例
  `src/TestUnits/coverage/m_WtUftRunner/r14_wtuftrunner_main_test.cpp:r14_uft_config.authored_config_without_basefiles_children_walks_the_early_exits`

- 输入/前置条件: 一份 basefiles/bspolicy 齐全、但**没有 `env` 段**（或没有 `data` 段）的 yaml。
- 期望行为: `config()` 在 `initEngine()`/`initDataMgr()` 失败时返回 false 或至少记 error，
  让调用方知道引擎/数据管理器没有初始化。
- 实际行为: `initEngine()` 在 `:253-264` 因缺 `env` 返回 false，`initDataMgr()` 在 `:268-278`

  `_base_data_mgr/_data_mgr` 只有 `init()` 才赋值（`WtUftEngine.cpp:308-319`），构造函数未初始化
  这两个字段（`:35-39`）。`run()` 仍调用 engine.run，ticker 路径会通过 `get_basedata_mgr()` 使用
  基础数据管理器（`WtUftTicker.cpp:182`）。因此“config 对缺失必需项报告成功”源码可证；run 的具体崩溃
  行为因未初始化指针属于未定义行为，本轮未复现，不能写成确定 SIGSEGV。
- 复现步骤: R14 `r14_uft_min_config.yaml` 仅含 basefiles/bspolicy（测试源 `r14_wtuftrunner_main_test.cpp:59-67`）。

- 影响范围: 配置缺失时 `config()` 仍报告成功；后续未初始化 manager 的运行风险静态可见，动态影响待证。
- 备注: 与 BUG-R28-007（`WtRunner` 同形）同族，但这是 UFT 侧独立实现。最小修复应对必需的
  `initEngine/initDataMgr` 失败返回 false，并将 engine 指针成员置空；`initUftStrategies()` 对缺少/空策略
  配置是否为致命错误尚无契约，不能不加区分地把其 false 都提升为 config 失败。

## BUG-R95-003

- 状态: 待审核
- 严重级别: Minor
- 模块/文件: `src/WtLatencyHFT/HftLatencyTool.cpp:192`（`double t2t = total * 1.0 / times;`）
  与 `:407`（`_times = _config->getUInt32("times");`）；
  `src/WtLatencyUFT/UftLatencyTool.cpp:116` 与 `:248` 同形
- 相关测试: `r95_hft_run.zero_ticks_after_successful_init_exercises_engine_and_parser_tail`、
  `r95_ufttool_run.zero_ticks_after_successful_init_exercises_engine_and_parser_tail`
  （两条用例都用 `times: 0` 进入该除法）
- 输入/前置条件: `config.yaml` 写 `times: 0`。完全不写 `times` 时的默认值需以 WTSVariant 契约另行核实。
- 期望行为: 延迟基准至少有一笔样本；`times==0` 应拒绝，或跳过均值并输出可识别的“无样本”状态。
- 实际行为: `TestParser::run` 在循环结束后无条件算 `total * 1.0 / times`（HFT `:192`，UFT `:116`）；
  `times` 由配置读入（HFT `:407`，UFT `:248`）。当 times 为 0 且 `total>0` 时结果为 `+inf`，若计时值
  恰为 0 则为 NaN；两者都不是有效平均延迟。当前测试只断言 `EXPECT_NO_THROW`，不检查输出值，因而
  不能作为日志为 `inf` 的动态证据。进程崩溃不是本项主张。
- 复现步骤: 现有零 tick 用例分别进入上述尾部除法，本轮运行均 PASS；没有捕获/断言 latency 日志，
  所以只证明执行到调用且不抛异常，不证明日志具体是 inf/NaN。
- 影响范围: 允许零样本时会输出无意义的非有限均值；是否默认漏写 times 得 0 需配置解析契约确认。
- 备注: 若接口允许 `times: 0` 作为 smoke/no-op 模式，应跳过均值输出；若不允许，则在两工具 init 校验
  `_times > 0` 并清楚返回失败。需补测试断言配置拒绝或无样本标记。`init()` 失败后入口继续 run 的问题
  属 R14-005，不作为本编号的重复主张。

## BUG-R95-004

- 状态: 待审核
- 严重级别: Minor
- 模块/文件: `src/WtUftRunner/WtUftRunner.cpp:302-306`（`initParsers` 的
  `adapter->init(...)` 返回值丢弃后 `addAdapter` + `count++`）与
  `:327-332`（`initTraders` 同形），日志在 `:309`/`:335`
- 相关测试: `r95_uft_config.string_basefiles_and_array_modules_return_true`、
  `r95_uft_config.array_basefiles_and_string_module_files_return_true`
  （两条都写 `module: no_such_parser/no_such_trader`）
- 输入/前置条件: 配置里的 parser/trader 条目 `active: true`，但 `module` 指向不存在的插件。
- 期望行为: 只统计 `adapter->init()` 成功的适配器，或在失败时记 error 且不加入管理器；
  日志里的「N parsers/traders loaded」应与实际装载数一致。
- 实际行为: `UftParserAdapter::init` 在 dlopen 失败时返回 false（`ParserAdapter.cpp:70-75`），
  `UftTraderAdapter::init` 同理（`TraderAdapter.cpp:172-177`）；调用方不检查返回值，仍 addAdapter/count++
  并打印 `N parsers/traders loaded`（`WtUftRunner.cpp:280-335`）。因此成功数/失败状态被错误报告；是否会
  导致后续下单失败或崩溃取决于 manager/adapter 对空 API 的处理，本轮未验证，不应写成确定的订单后果。
- 复现步骤: 用本 lane 的 cfg_a.yaml/cfg_b.yaml 跑 `WtUftRunner::config()`，
  对比日志里的 `Parser module ... loading failed` 与随后的 `1 parsers loaded`。
- 影响范围: 配置错误时 `config()` 仍可返回 true，且 active 条目会计入 loaded 数；是否影响后续
  运行/委托不在本轮证据范围内。
- 备注: 与 BUG-R14-003（缺 basefiles 段直接空指针）不同，这里段存在、条目也合法，
  只是插件装载失败被计数掩盖。
