## BUG-R95-001

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtUftRunner/WtUftRunner.cpp:340-349`（`initEvtNotifier()`）与
  `:195-197`（`config()` 在 `initUftStrategies()` 之后直接 `return true`）；
  声明见 `src/WtUftRunner/WtUftRunner.h:116`
- 相关测试: `src/TestUnits/coverage/m_WtUftRunner/r95_wtuftrunner_config_run_test.cpp`
  的 6 条 config 用例（均未写 `notifier` 键，因为这个键不会被读取）
- 输入/前置条件: 配置里写 `notifier:` 对象（任意内容）。
- 期望行为: `config()` 在加载策略之后调用 `initEvtNotifier()`，
  把 `notifier` 段交给 `EventNotifier::init`，与 `WtRunner`/`WtBtRunner` 的同名流程一致。
- 实际行为: `initEvtNotifier()` 在整个仓库里只有声明与定义，**没有调用点**
  （`grep -rn initEvtNotifier src/WtUftRunner` 只命中 `.cpp:340` 与 `.h:116`）。
  `config()` 返回 true，`_notifier` 保持默认构造状态，配置中的事件通知设置被静默忽略。
- 复现步骤: `grep -rn "initEvtNotifier" src/WtUftRunner`；或在配置中写
  `notifier:\n    module: xxx` 后调用 `WtUftRunner::config()`，观察没有任何 notifier 初始化日志。
- 影响范围: UFT 实盘进程无法按配置启用事件通知；覆盖率侧 `WtUftRunner.cpp:340-349`
  （约 10 行）成为不可达死代码。
- 备注: 修复方向是把 `:195` 的 `initUftStrategies();` 后面补
  `if (!initEvtNotifier()) WTSLogger::error(...)`，或明确删除这段死代码。

## BUG-R95-002

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtUftRunner/WtUftRunner.cpp:110`（`initEngine();` 返回值丢弃）、
  `:113`（`initDataMgr();` 返回值丢弃）、`:195`（`initUftStrategies();` 返回值丢弃）；
  对照 `:124` 的 `if(!_act_policy.init(...))` 是同一函数里唯一被检查的 init。
  未初始化成员的来源：`src/WtUftCore/WtUftEngine.cpp:35-51` 的构造函数只初始化
  `_tm_ticker/_cfg/_notifier`，`_base_data_mgr` 与 `_data_mgr`（`WtUftEngine.h:133-134`）没有初值。
- 相关测试: R14 既有用例
  `src/TestUnits/coverage/m_WtUftRunner/r14_wtuftrunner_main_test.cpp:r14_uft_config.authored_config_without_basefiles_children_walks_the_early_exits`
  （配置无 `env`/`data` 时 `config()` 仍返回 true）；本 lane 的
  `r95_uft_config.*` 都显式写了 `env`/`data`，没有触发该路径
- 输入/前置条件: 一份 basefiles/bspolicy 齐全、但**没有 `env` 段**（或没有 `data` 段）的 yaml。
- 期望行为: `config()` 在 `initEngine()`/`initDataMgr()` 失败时返回 false 或至少记 error，
  让调用方知道引擎/数据管理器没有初始化。
- 实际行为: `initEngine()` 在 `:256-257` 因 `env == NULL` 返回 false，`initDataMgr()` 在
  `:271-272` 因 `data == NULL` 返回 false，但两个返回值都被丢弃，`config()` 继续走到
  `:197 return true`。随后 `run()` 在 `:355` 调 `_uft_engine.run()`；`WtUftRtTicker::run()`
  在 `src/WtUftCore/WtUftTicker.cpp:182` 用 `_engine->get_basedata_mgr()`，
  取到的是从未赋值的 `_base_data_mgr`（静态推演：空指针或野指针）。
- 复现步骤: 用 R14 那份 `r14_uft_min_config.yaml`（有 basefiles、无 env/data）调用
  `WtUftRunner::config()`，确认返回 true；再调用 `run(false)`，观察在 ticker 初始化处崩溃/挂死
  （R14 已把该调用标为 `DISABLED_run_false_loops_until_signal`）。
- 影响范围: 配置缺一整段时从「可控失败」变成「config 报成功、run 稍后崩」；
  `catch(...)` 救不了 SIGSEGV。
- 备注: 与 BUG-R28-007（`WtRunner` 同形）同族，但这是 UFT 侧的独立实现；
  修复方向是三处补 `if (!initXxx()) return false;`，并给 `WtUftEngine` 的指针成员补默认初值。

## BUG-R95-003

- 状态: 待审核
- 严重级别: Minor
- 模块/文件: `src/WtLatencyHFT/HftLatencyTool.cpp:192`（`double t2t = total * 1.0 / times;`）
  与 `:407`（`_times = _config->getUInt32("times");`）；
  `src/WtLatencyUFT/UftLatencyTool.cpp:116` 与 `:248` 同形
- 相关测试: `r95_hft_run.zero_ticks_after_successful_init_exercises_engine_and_parser_tail`、
  `r95_ufttool_run.zero_ticks_after_successful_init_exercises_engine_and_parser_tail`
  （两条用例都用 `times: 0` 进入该除法）
- 输入/前置条件: `config.yaml` 写 `times: 0`，或完全不写 `times`（`getUInt32` 默认 0）。
- 期望行为: `times <= 0` 时报错退出，或跳过延迟统计，避免输出无意义的延迟值。
- 实际行为: 循环 0 次后执行 `total * 1.0 / 0`，按 IEEE 浮点得到 `inf`，再以 `{:.3f}`
  打印成 `inf ns`；进程不崩，但结果没有任何测量意义，且入口 `test_hft()/test_uft()`
  在 init 失败时也会无条件 `run()`（R14-005 已登记异常吞噬）。
- 复现步骤: 在临时目录写 `times: 0` 的 config，运行 `WtLatencyHFT`/`WtLatencyUFT`，
  观察日志末尾 `HftEngine/UftEngine Innner Latency: inf ns`。
- 影响范围: 延迟工具在默认/漏写配置时给出 `inf` 而不是可诊断的错误；覆盖率侧这条
  除法路径只能靠 0 值触发，本身是缺陷证据。
- 备注: 建议在 `init()` 里校验 `_times > 0`，或在 `TestParser::run` 入口直接返回并记 error。

## BUG-R95-004

- 状态: 待审核
- 严重级别: Minor
- 模块/文件: `src/WtUftRunner/WtUftRunner.cpp:302-306`（`initParsers` 的
  `adapter->init(...)` 返回值丢弃后 `addAdapter` + `count++`）与
  `:327-332`（`initTraders` 同形），日志在 `:309`/`:335`
- 相关测试: `r95_uft_config.string_basefiles_and_array_modules_return_true`、
  `r95_uft_config.array_basefiles_and_string_module_files_return_true`
  （两条都写 `module: no_such_parser/no_such_trader`）
- 输入/前置条件: 配置里的 parser/trader 条目 `active: true`，但 `module` 指向不存在的插件。
- 期望行为: 只统计 `adapter->init()` 成功的适配器，或在失败时记 error 且不加入管理器；
  日志里的「N parsers/traders loaded」应与实际装载数一致。
- 实际行为: `UftParserAdapter::init` 在 module 为空或 dlopen 失败时返回 false
  （`WtUftCore/ParserAdapter.cpp:60-75`），`UftTraderAdapter::init` 同样返回 false
  （`WtUftCore/TraderAdapter.cpp:162-177`），但 `initParsers/initTraders` 不看返回值，
  仍 `addAdapter` 并 `count++`；于是日志打印「1 parsers loaded」「1 traders loaded」，
  而实际上没有任何插件被装载。
- 复现步骤: 用本 lane 的 cfg_a.yaml/cfg_b.yaml 跑 `WtUftRunner::config()`，
  对比日志里的 `Parser module ... loading failed` 与随后的 `1 parsers loaded`。
- 影响范围: 配置错误时运维会看到「loaded」而误判插件已生效；后续策略绑定到
  一个没有 API 的 TraderAdapter，错误被推迟到下单时才暴露。
- 备注: 与 BUG-R14-003（缺 basefiles 段直接空指针）不同，这里段存在、条目也合法，
  只是插件装载失败被计数掩盖。
