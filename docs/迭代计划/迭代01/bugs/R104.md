## BUG-R104-001 QuoteFactory 配置缺 `writer` 段时对 NULL 调 `WTSVariant::getCString`

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件:
  - `src/QuoteFactory/main.cpp:199`（`initDataMgr(config->get("writer"), bAlldayMode);`）
  - `src/QuoteFactory/main.cpp:64~68`（`initDataMgr` 把指针原样交给 `g_dataMgr.init`）
  - `src/WtDtCore/DataManager.cpp:71`（`std::string module = params->getCString("module");`）
  - `src/Includes/WTSVariant.hpp:346~353, 364~373`（`getCString` 非 static，`get()` 先读 `_type`）
- 相关测试: `r104_quotefactory_init_test.cpp` 的
  `r104_quote_initialize.full_allday_config_reaches_end_of_function`（配置里**必须**写
  `writer: { module: R104NoSuchWriterModule }` 才不崩）、
  `r104_quote_initialize.minimal_config_skips_absent_basefiles_children`（同样必须写 writer）
- 输入/前置条件: 一份 `basefiles` 齐全、`allday: true`、但**没有 `writer` 段**的 `dtcfg.yaml`。
- 期望行为: `writer` 是可选段（`dist/QuoteFactory/dtcfg.yaml` 之外的最小配置完全合理），
  缺段时应打一条 error 并跳过 `initDataMgr`，或按 `parsers`/`index` 的写法先判空。
- 实际行为: `config->get("writer")` 返回 NULL，`DataManager::init` 第一句
  `params->getCString("module")` 在 `this == NULL` 上访问 `_type` → **SIGSEGV**，
  进程在 `initialize()` 里当场死；`WtLogger` 连一行 error 都来不及写。
  同一函数里 `:221` 的 `parsers`、`:201` 的 `index`、`:175/:181` 的 caster 都判了 `has()/get()`
  的真假，只有 `:199` 直接传指针，属于漏项而不是有意。
- 复现步骤:
  1. 写 `r104_bug1.yaml`: `basefiles: {}\nallday: true\n`（有 basefiles、无 writer）；
  2. 在空目录里 `initialize("./r104_bug1.yaml")`；
  3. 进程收到 SIGSEGV（实测前置：同一份配置补上 `writer: {module: R104NoSuchWriterModule}`
     后正常返回，说明崩点就在 `DataManager::init` 的第一句）。
- 影响范围: 任何精简掉 `writer` 段的部署配置都会让报价服务「启动即段错误」；
  覆盖率侧 `initialize()` 的成功支必须靠用例自己补 `writer` 才能取样，缺陷被夹具掩盖。
- 备注: 与 BUG-R14-003（缺 `basefiles` 整段空指针）同族，建议一次 PR 把
  `basefiles`/`writer` 两处判空一起收口，并补「缺段 → error + 明确失败返回」的语义。

## BUG-R104-002 行情解析器 `init()` 失败仍被登记进适配器表，`g_parsers.size()` 谎报「已加载」

- 状态: 待审核
- 严重级别: Major
- 模块/文件:
  - `src/QuoteFactory/main.cpp:88~90`
    （`ParserAdapterPtr adapter(new ParserAdapter(...)); adapter->init(...); g_parsers.addAdapter(...);`）
  - `src/WtRunner/WtRunner.cpp:450~452`（同一形状，`adapter->init(realid, cfgItem, _engine, ...)` 的返回值被丢弃）
  - 失败点: `src/WtDtCore/ParserAdapter.cpp:110~121`、`src/WtCore/ParserAdapter.cpp:105~121`
    （模块 dlopen 失败 → `return false`）
- 相关测试: `r104_quote_initparsers.active_entries_with_and_without_id_land_in_manager`
  （断言 `g_parsers.size()` 恰增 2，其中两条 entry 的模块名都是 `R104NoSuchParserModule`）、
  `r104_wtrunner_config.traders_parsers_and_all_three_executer_kinds`
- 输入/前置条件: `parsers` 里一条 `active: true`、`module` 指向不存在的插件（拼写错误或漏装插件）。
- 期望行为: `ParserAdapter::init` 返回 false 时跳过 `addAdapter`，并在汇总日志里把
  「配置了 N 条 / 真正加载 M 条」分开；至少不要把失败项算进 `size()`。
- 实际行为: `init` 的返回值被完全忽略，适配器照样进 `_adapters`；
  `main.cpp:93` 打印的 `"{} market data parsers loaded in total"` 用的是 `g_parsers.size()`，
  于是日志写「1 条已加载」，实际 0 条可用。随后 `g_parsers.run()`（`ParserAdapterMgr::run`）
  对这条空适配器调 `run()` → `_parser_api == NULL` → 静默 `return false`，
  进程看起来启动成功但永远收不到行情。`WtRunner.cpp:457` 的 `"{} parsers loaded"` 用 count
  变量统计的是 `active: true` 的条数，同样把失败项算进去。
- 复现步骤:
  1. 配置 `parsers: [{id: p1, active: true, module: NoSuchParser}]`；
  2. 调 `initParsers(...)`（或 `WtRunner::config`）；
  3. 断言 `g_parsers.size()`，得到 1；把 `module` 换成真实插件才可能收到数据。
- 影响范围: 行情插件漏装/改名时进程不报错、日志还宣称加载成功，属于「静默降级」；
  运维只能靠行情不来反推。覆盖率侧 `:89` 的返回值分支永远取不到假侧。
- 备注: 建议 `ParserAdapter::init` 失败时 `continue`，并让总计日志区分 loaded/failed。

## BUG-R104-003 交易通道 `init()` 失败仍被登记，执行器可以绑到一条永远不会就绪的通道上

- 状态: 待审核
- 严重级别: Major
- 模块/文件:
  - `src/WtRunner/WtRunner.cpp:565~568`
    （`TraderAdapterPtr adapter(new TraderAdapter(&_notifier)); adapter->init(...); _traders.addAdapter(id, adapter);`）
  - 绑定侧: `src/WtRunner/WtRunner.cpp:494~500`（`getAdapter(tid)` 非空即 `setTrader` + `addSink`）
  - 失败点: `src/WtCore/TraderAdapter.cpp:163~178`（`module` 为空或 dlopen 失败 → `return false`）
- 相关测试: `r104_wtrunner_config.traders_parsers_and_all_three_executer_kinds`
  （`traders: [{id: r104wt_t1, active: true, module: R104NoSuchTraderModule}]`，
  `executers: [{..., trader: r104wt_t1}]`；用例断言 `config()` 仍为 true）
- 输入/前置条件: 交易通道 `module` 拼错/未安装，同时执行器 `trader` 指向该通道 id。
- 期望行为: `TraderAdapter::init` 失败时不入表（或入表但标记为不可用），
  `initExecuters` 的 `getAdapter` 应拿不到死通道，走 `:502` 的
  「Trader {} not exists, cannot configured for executer」错误支。
- 实际行为: 失败的 adapter 照样进 `_traders`，`getAdapter("r104wt_t1")` 返回非空，
  执行器 `setTrader` + `addSink` 成功，`_channel_ready` 取 `isReady()`（`_state == AS_NOTLOGIN`）
  为 false；从这一刻起执行器把所有下单请求投给一条没有 `ITraderApi` 的通道，
  既不报错也不成交。日志里只有 init 阶段那条 `"Loading trading module ... failed"`，
  之后的绑定过程完全「成功」。
- 复现步骤:
  1. `traders` 一条 active + `module: R104NoSuchTraderModule`；
  2. `executers` 一条 local + `trader: <上一步的 id>`；
  3. `WtRunner::config()` 返回 true；观察不到 `:502` 的错误日志（该支只有在 id 完全不存在时才走）。
- 影响范围: 交易通道故障时策略侧看到的是「已绑定、通道 not ready」而不是「配置错误」，
  排查成本高；覆盖率侧 `:495~500` 的「trader 存在」路径被测到的其实是一条死通道。
- 备注: 与 BUG-R104-002 同一类「子对象 init 返回值被丢弃」。建议 `initTraders` 判返回值，
  失败时不入表并把错误上抛给 `config()`。

## BUG-R104-004 `initCtaStrategies` 少 `createStrategy` 判空，工厂缺失时 `stra->self()` 空指针

- 状态: 待审核
- 严重级别: Major（配置错误直接打崩进程）
- 模块/文件:
  - `src/WtRunner/WtRunner.cpp:305~307`
    （`CtaStrategyPtr stra = _cta_stra_mgr.createStrategy(name, id); stra->self()->init(...);`）
  - 对照实现: `src/WtRunner/WtRunner.cpp:338~340`（HFT 分支有 `if (stra == NULL) continue;`）
  - 触发点: `src/WtCore/CtaStrategyMgr.cpp` 的 `createStrategy` 在工厂/策略名不存在时返回空
- 相关测试: `r104_runner_executers_test.cpp` 的
  `DISABLED_run_starts_parsers_traders_engine_and_polls_forever` 之外的
  `strategies` 相关路径未启用；本轮只登记（既有 `r28_runner_main_test.cpp` 的
  `DISABLED_active_cta_entry_needs_real_factory_dir` 也指向同一处）
- 输入/前置条件: `env.name: cta`、`strategies.cta` 里一条 `active: true`、
  `name: WtCtaStraFact.DualThrust`，但运行目录 `cta/` 下没有可 dlopen 的策略工厂
  （或 `name` 拼错）。
- 期望行为: 与 HFT 分支一致——`stra == NULL` 时记 error 并 `continue`，其余策略继续加载。
- 实际行为: `createStrategy` 返回空 `CtaStrategyPtr`，下一行 `stra->self()` 对空 shared_ptr
  解引用 → **SIGSEGV**。`config()` 里也没有 try/catch，异常/信号直接终止进程。
  同一文件里 HFT 分支（`:338~340`）明确判了空，说明这是 CTA 分支的漏项。
- 复现步骤:
  1. 在空运行目录写一份含 `strategies.cta[0].active: true` 的 CTA 配置；
  2. `WtRunner::config()`；
  3. 进程在 `:307` 段错误（用 `DISABLED_active_cta_entry_needs_real_factory_dir` 可复现，
     该用例保留在 `m_WtRunner/r28_runner_main_test.cpp`）。
- 影响范围: 策略名拼错 = 实盘进程启动即崩，且崩点在 `WTSLogger` 之外（无 error 日志）；
  覆盖率侧 `:302~:310` 的 20 余行因此只能整段留白。
- 备注: 修复只需 3 行（判空 + error + continue），之后配合「工厂目录注入」接缝可一次拿下
  `:302~:310` 与 `:321~:362` 约 44 行。
