# R104 缺陷清单 —— 第十八波 lane R104

- 本轮仅复核台账；未修改生产代码/测试。状态按条目标注，测试结果只说明被执行的用例。
- 范围: `src/QuoteFactory/main.cpp`、`src/WtRunner/WtRunner.cpp`（只读）。
- 复核环境: `build-cov`（`WT_ENABLE_COVERAGE=ON`）；本轮定向运行 QuoteFactory 3 条用例和
  WtRunner 1 条用例，均 PASS。QuoteFactory 的 `initialize()` 用例通过 fork 子进程；直接调用
  `initParsers()` 与 WtRunner `config()` 的测试不都在独立进程内，不能概括为“每条用例独立进程”。

## BUG-R104-001 QuoteFactory 缺 `writer` 段将 NULL 传入 DataManager

- 状态: 已合并（主编号 BUG-R18-001；相同 DataManager::init(NULL, ...) 根因；QuoteFactory 调用路径为补充证据，writer 必需性/可选性仍未证）
- 严重级别: 不另计（按 BUG-R18-001 处理）
- 模块/文件:
  - `src/QuoteFactory/main.cpp:199`（`initDataMgr(config->get("writer"), bAlldayMode);`）
  - `src/QuoteFactory/main.cpp:64~68`（`initDataMgr` 把指针原样交给 `g_dataMgr.init`）
  - `src/WtDtCore/DataManager.cpp:71`（`std::string module = params->getCString("module");`）
  - `src/Includes/WTSVariant.hpp:346~353, 364~373`（`getCString` 非 static，`get()` 先读 `_type`）
- 相关测试: `r104_quotefactory_init_test.cpp` 的
  `full_allday_config_reaches_end_of_function`、`minimal_config_skips_absent_basefiles_children` 都配置了
  `writer: { module: R104NoSuchWriterModule }`；本轮二者均 PASS。测试没有执行“缺 writer”输入，不能称其已复现
  本条。配置假模块时 `DataManager::init` 因 dlopen 失败返回 false，QuoteFactory 的 `initDataMgr` 丢弃返回值并继续。
- 输入/前置条件: 一份 `basefiles` 齐全、`allday: true`、但**没有 `writer` 段**的 `dtcfg.yaml`。
- 测试前提/契约边界: `writer` 是否为可选配置没有在本轮找到公开契约；当前 `dist/QuoteFactory/dtcfg.yaml`
  提供 writer 配置。故不声称“缺 writer 是合理的最小配置”。
- 源码证据: 当 YAML 有 `basefiles: {}` 但没有 `writer`，`config->get("writer")` 会返回空指针并被传入
  `DataManager::init`；该函数首个读取为 `params->getCString("module")`，无 NULL 守卫。输入若到达该调用，源码存在
  空指针成员调用/未定义行为路径；本轮没有运行此配置，不断言实际信号一定为 SIGSEGV。它与 BUG-R18-001
  的 API 根因相同，不应在缺陷数中再算一个独立 DataManager 问题；QuoteFactory 仍应按必需/可选契约校验配置并检查
  `initDataMgr` 返回值，给出明确失败状态。
- 修复方向: 统一在 `DataManager::init` 对空 `params` 返回 false 并记录可读原因；QuoteFactory 明确 writer 是必需还是可选，
  若必需则在调用前拒绝缺段配置，若可选则判空并跳过初始化。不要将“假 writer 模块使 initialize 返回”作为缺段测试。

## BUG-R104-002 行情解析器 `init()` 返回 false 仍被登记并计入 loaded 数

- 状态: 源码确认 active 失败项仍落表并被计数；失败有日志，是否必须令整体配置失败取决于插件可选性契约
- 严重级别: Major
- 模块/文件:
  - `src/QuoteFactory/main.cpp:88~90`
    （`ParserAdapterPtr adapter(new ParserAdapter(...)); adapter->init(...); g_parsers.addAdapter(...);`）
  - `src/WtRunner/WtRunner.cpp:450~452`（同一形状，`adapter->init(realid, cfgItem, _engine, ...)` 的返回值被丢弃）
  - 失败点: `src/WtDtCore/ParserAdapter.cpp:110~121`、`src/WtCore/ParserAdapter.cpp:105~121`
    （模块 dlopen 失败 → `return false`）
- 相关测试: `r104_quote_initparsers.active_entries_with_and_without_id_land_in_manager`
  （断言 `g_parsers.size()` 增 2，即使两条 active entry 都是不存在模块；本轮 PASS）；
  `r104_wtrunner_config.traders_parsers_and_all_three_executer_kinds`（本轮 PASS，config 返回 true）。
- 输入/前置条件: `parsers` 里一条 `active: true`、`module` 指向不存在的插件（拼写错误或漏装插件）。
- 期望行为: active parser 初始化失败应在结果中标为 failed，不应计为 loaded；整体配置是否拒绝缺插件需由配置契约决定。
- 源码/测试证据: `init` 的返回值被忽略，适配器照样进 `_adapters`；
  `main.cpp:93` 打印的 `"{} market data parsers loaded in total"` 用的是 `g_parsers.size()`，
  因此它把表内 adapter 数称为已加载数。模块加载失败时 `ParserAdapter::init` 会先发 LL_ERROR 并返回 false
  (`WtDtCore/ParserAdapter.cpp:116-121`、`WtCore/ParserAdapter.cpp:116-121`)；这不是完全静默。
  `ParserAdapterMgr::run()` 忽略 adapter `run()` 返回值，并按表大小打印 started (`WtCore/ParserAdapter.cpp:417-425`)；
  对缺模块的空 parser API，该 adapter 自身不可提供行情。`WtRunner::initParsers` 的 `count` 也只数 active 项
  (`:433-457`)。因此可确认计数/状态表达不实和部分失败仍配置成功；不能据此声称整个服务永远无行情或没有错误日志。
- 测试前提/重复边界: QuoteFactory 用例主动选择不存在模块来覆盖“落表”路径，其 PASS 证明现状而非期望成功加载；
  WtRunner 用例同样只验证 config 完成。两个 runner 的发生点不同，但与 BUG-R104-003 同属“子对象 init 失败后仍登记/计数”
  的处理模式，不是同一 adapter 的重复编号。
- 修复方向: 检查 `init()` 返回值，区分 configured/loaded/failed；失败项不应进入可用 adapter 表，或必须保留显式 failed 状态，
  并让 manager 汇总结果反映实际启动数。补测试核对错误日志、loaded/failed 数和整体配置策略。

## BUG-R104-003 交易通道 `init()` 失败仍被登记，执行器把它当作存在的 adapter

- 状态: 源码确认失败 adapter 落表且配置成功；下单路径会 fail-closed，配置是否应失败待契约确认
- 严重级别: Major
- 模块/文件:
  - `src/WtRunner/WtRunner.cpp:565~568`
    （`TraderAdapterPtr adapter(new TraderAdapter(&_notifier)); adapter->init(...); _traders.addAdapter(id, adapter);`）
  - 绑定侧: `src/WtRunner/WtRunner.cpp:494~500`（`getAdapter(tid)` 非空即 `setTrader` + `addSink`）
  - 失败点: `src/WtCore/TraderAdapter.cpp:163~178`（`module` 为空或 dlopen 失败 → `return false`）
- 相关测试: `r104_wtrunner_config.traders_parsers_and_all_three_executer_kinds`
  （`traders: [{id: r104wt_t1, active: true, module: R104NoSuchTraderModule}]`，
  `executers: [{..., trader: r104wt_t1}]`；用例断言 `config()` 仍为 true）
- 输入/前置条件: 交易通道 `module` 拼错/未安装，同时执行器 `trader` 指向该通道 id。
- 期望行为: `TraderAdapter::init` 失败时不入表（或入表但标记为不可用），
  `initExecuters` 的 `getAdapter` 应拿不到死通道，走 `:502` 的
  「Trader {} not exists, cannot configured for executer」错误支。
- 源码/测试证据: 失败的 adapter 照样进 `_traders`，`getAdapter("r104wt_t1")` 返回非空，
  执行器 `setTrader` + `addSink` 成功，`_channel_ready` 取 `isReady()`（`_state == AS_NOTLOGIN`）
  为 false；此时订单入口在 `WtLocalExecuter`/`WtDiffExecuter` 检查 `_channel_ready` 后返回空订单 ID/false，
  不会把下单转发给空 `_trader_api`。`TraderAdapter::init` 的模块加载失败会写 LL_ERROR，不能说无错误日志。
  本轮 `r104_wtrunner_config.traders_parsers_and_all_three_executer_kinds` PASS，证明 `config()` 可在失败 adapter
  被登记并被执行器找到的情况下返回 true；它没有实际运行策略/下单。
- 复现步骤:
  1. `traders` 一条 active + `module: R104NoSuchTraderModule`；
  2. `executers` 一条 local + `trader: <上一步的 id>`；
  3. 源码可推 `getAdapter` 得到 failed adapter 并避开 `:502` 的“不存在”分支；本轮启用配置用例 PASS，
     但没有捕获该错误分支日志，也没有执行订单。
- 影响范围: 交易通道故障时策略侧看到的是「已绑定、通道 not ready」而不是「配置错误」，
  排查成本高；覆盖率侧 `:495~500` 的「trader 存在」路径被测到的其实是一条死通道。
- 重复边界: 与 BUG-R104-002 的控制流模式相同，但交易 adapter 有独立初始化和订单 readiness 保护，保留为独立发生点；
  两处可由统一的“初始化结果必须参与注册/计数”原则修复。
- 修复方向: `initTraders` 检查 `init()` 返回值；若 active channel 属必需配置则让 `config()` 失败，否则记录 loaded/failed 并阻止
  executer 将 failed adapter 当成可用关联。回归应断言 failed channel 不被计为 loaded、绑定状态明确、订单仍 fail-closed。

## BUG-R104-004 `initCtaStrategies` 未校验策略 wrapper/inner，工厂缺失时解引用空指针

- 状态: 源码确认存在空指针解引用路径；本轮未运行相关崩溃用例，运行时信号与进程影响未复现
- 严重级别: Major（无效策略配置可能中止启动）
- 模块/文件:
  - `src/WtRunner/WtRunner.cpp:305~307`
    （`CtaStrategyPtr stra = _cta_stra_mgr.createStrategy(name, id); stra->self()->init(...);`）
  - 对照实现: `src/WtRunner/WtRunner.cpp:338~340`（HFT 分支有 `if (stra == NULL) continue;`）
  - 触发点: `src/WtCore/CtaStrategyMgr.cpp` 的 `createStrategy` 在工厂/策略名不存在时返回空
- 相关测试: `r104_runner_executers_test.cpp` 的
  `DISABLED_run_starts_parsers_traders_engine_and_polls_forever` 之外的
  `strategies` 相关路径未启用；本轮只登记（既有 `r28_runner_main_test.cpp` 的
  `DISABLED_active_cta_entry_needs_real_factory_dir` 也指向同一处）
- 输入/前置条件: `env.name: cta`、`strategies.cta` 里一条 `active: true`、
  `name: WtCtaStraFact.DualThrust`，但运行目录 `cta/` 下没有可 dlopen 的策略工厂
  （或 `name` 拼错）。另一条空路径是工厂可加载但返回空策略对象。
- 期望行为: 在调用策略对象前检查 `createStrategy` 返回的 wrapper 及 `stra->self()`；无效项应有明确错误并按策略配置契约拒绝配置或跳过。
  HFT 分支对 wrapper 做了空检查（`:338~:340`），但这不能单独证明 CTA 的正确恢复策略。
- 源码行为: `createStrategy` 在工厂/策略名不存在时返回空 wrapper；此外，工厂返回空 unit strategy 时
  `CtaStrategyMgr` 仍可能创建非空 wrapper，而 `CtaStraWrapper::self()` 返回空内层指针。
  CTA 路径没有检查 wrapper 或 inner strategy，直接调用 `stra->self()->init(...)`，因此两类输入都存在空指针解引用/未定义行为路径。
  本轮没有运行崩溃用例，不能称为已观测 SIGSEGV 或确认启动进程实际退出方式。
- 动态证据边界: `r28_runner_main_test.cpp::DISABLED_active_cta_entry_needs_real_factory_dir` 是禁用用例；本轮未启用运行，且它在 GTest 进程中直接调用 runner，并非隔离子进程的崩溃验证。它只能作为待运行测试线索，不能据此报告 SIGSEGV 已复现。
- 修复方向: 在 `:305~:307` 前验证 wrapper 与 inner strategy；配置失败还是跳过策略由产品配置契约决定，需记录错误。之后可通过工厂目录/工厂结果注入接缝分别覆盖“工厂缺失”和“工厂返回空 unit strategy”，并将崩溃验证放入隔离子进程。
- 重复边界: `bugs/R82.md` BUG-R82-002 记录相同的 CTA 策略 manager 空结果被 runner 解引用问题，但发生于另一条 `WtPorter/WtRtRunner` 调用路径；两项属于同一缺陷族、不同调用点，不应把它们写成完全相同的代码位置。
- 覆盖影响: 尚未通过本轮运行验证 `:302~:310` 与 `:321~:362` 的覆盖情况。
