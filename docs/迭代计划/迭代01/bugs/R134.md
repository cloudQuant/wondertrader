## BUG-R134-001 `config_backtest` 的一次性门永不生效

- 状态: 已合并（迭代02：主编号 BUG-R9-001）

- 编号: BUG-R134-001
- 模块/文件/行: `src/WtBtPorter/WtBtPorter.cpp` L174-185（`static bool inited` L176、判断 L178、早退 L179）
- 测试用例: `R124BtPorterConfig.SecondConfigBacktestCallIsNoOp`。旧用例连续传无效 JSON 且只断言不抛异常；现已改为有效配置和可观察的 Tick 状态。
- 输入: 隔离子进程中先设置 Tick 开启，第一次有效配置设为关闭并核对生效，第二次有效配置设为开启。
- 期望: 若接口意图是“成功配置一次后忽略重复调用”，成功后门应生效；失败配置是否允许
  重试需由契约明确，不能用坏 JSON 的 no-throw 结果代替验证。
- 实际: 函数体内没有任何 `inited = true` 赋值，故静态上该早退条件永远为假，后续每次调用
  都会转发 `getRunner().config()`。有效配置下会重新进入 runner 的配置流程；覆盖层的
  R124 用例传非法 JSON，runner 在解析失败时返回，不能证明重复配置的副作用或 no-op。
  `WtBtRunner::config` 自身的守卫也未被赋值（见 BUG-R134-002）。
- 证据边界: 源码确认门变量没有写入；旧 R124 用例是测试错误/不足（坏 JSON + `EXPECT_NO_THROW`）。修正后通过 GoogleTest threadsafe 子进程重执行，隔离进程级静态状态；本机重建后单例 FAIL，子进程退出 14 并报告第二次配置改变 Tick 状态，前置 Tick 开启及首次配置关闭均已通过。此结果证明包装层调用序列没有按一次性约定忽略第二次有效配置；两层门均未赋值，不能仅由这一测试分离各层贡献，也未执行真实回测或交易。
- 修复方向: 统一一次性配置门的状态来源。由于 `WtBtRunner::config` 当前返回 `void`，需先
  明确失败后的重试契约，并通过返回状态或可查询状态表达配置是否成功；再由唯一权威门在
  成功后置位。增加有效配置两次调用用例，断言第二次调用确实被忽略/被拒绝及其可观察状态，
  而不是只断言不抛异常。
- 严重级别: 中（一次性调用契约被源码违反；重复有效配置的下游副作用尚未动态测量）


- 迭代02复核: DUPLICATE。config_backtest 的 once 守卫确实没有成功后置位，但相同根因和完整配置语义已由 BUG-R9-001 作为主记录覆盖。当前 negative-config 测试没有证明重复成功配置行为。
- 迭代02依据: [逐条裁定与主代理修订](../../迭代02/缺陷裁定总表.md)。原记录保留作为历史，未声称产品已修复。
## BUG-R134-002 `WtBtRunner::_inited` 永远为 false，重复 config 守卫不可达

- 状态: 已合并（迭代02：主编号 BUG-R9-001）

- 编号: BUG-R134-002
- 模块/文件/行: `src/WtBtPorter/WtBtRunner.cpp` L85（构造 `_inited(false)`）、L451-455（守卫）、`WtBtRunner.h` L642
- 测试用例: `src/TestUnits/coverage/q06_btporter/r205_btporter_residual_test.cpp` 中有
  `DISABLED_R205BtRunnerConfig.SecondConfigIsNotIgnoredBecauseInitedIsNeverSet`，用两份有效
  配置观察 sel/hft mocker 状态；该用例禁用，尚不能作为动态证据。
- 输入: `WtBtRunner r; r.config(cfg, false); r.config(cfg, false);`
- 期望: 第二次 `config` 在 L451 命中守卫，打印 “WtBtEngine has already been inited” 并返回
- 实际: `_inited` 在该实现中只初始化为 false、只读于守卫，没有赋值为 true 的语句；因此
  源码上第二次有效调用不会由此守卫拦截。后续会重新进入 notifier/replayer 初始化，并按新
  `env.mocker` 分支执行；是否泄漏或其他破坏取决于各初始化函数的重置/所有权行为，原记录
  尚未动态确认。
- 证据边界: R205 用例构造了有效 sel→hft 配置并标注预期失败，但仍为 `DISABLED_`；基线
  覆盖行数为 0 不是运行证明。本条目前为源码确认、动态未验证。
- 与 BUG-R134-001 的关系: 两个未赋值的门分别位于导出包装层和 runner 层，是两个源码缺口，
  但外部表现都属于重复 config 未被忽略；R124 包装层有效配置两次测试现已 FAIL，不能单独证明内层门的贡献。评估影响时不重复累计同一调用序列造成的后果。
- 修复方向: 让 runner 的有效配置结果维护 `_inited`，或删除冗余内层门并由一个权威状态
  管理生命周期；增加启用的有效双配置测试，验证第二次调用不覆盖首个 mocker/配置。
- 严重级别: 中（守卫无效由源码确认；资源泄漏/重置损害未运行测试确认）


- 迭代02复核: DUPLICATE。_inited 初始化为 false，成功路径未将其置为 true；这是 BUG-R9-001 中 WtBtRunner config 守卫失效的同一根因，重复记录不独立计数。相关现存测试处于禁用状态。

## BUG-R134-003 SEL 策略初始化是死代码，且键名写错

- 编号: BUG-R134-003
- 模块/文件/行: `src/WtPorter/WtRtRunner.cpp` L709-711（config 末尾只调用 `initCtaStrategies`/`initHftStrategies`）、L745-789（`initSelStrategies`）、L751（读取 `"cta"`）
- 测试用例: `R134PorterBars.SelGetBarsReturnsLoadedBlocks` 使用 `create_sel_context` 显式建
  上下文并测试取 K 线，不配置 `strategies.sel`，不能验证自动策略装载；基线覆盖 L746-789
  全 0 也只说明当时未执行这些行。
- 输入: `{"env":{"name":"sel"},"strategies":{"sel":[{"active":true,"id":"s1","name":"X"}]}}`
- 期望: env=sel 时调用 `initSelStrategies`，读取 `strategies.sel` 并创建 `SelStraContext`
- 实际: 静态调用图中 `initSelStrategies` 没有调用点；config 收尾处只按 `_is_hft` 选择
  `initCtaStrategies` 或 `initHftStrategies`，而 `initEngine` 对 SEL 环境设置 `_is_sel` 并初始化
  `_sel_engine`。若走 `strategies.sel` 自动装载路径，该路径不会创建 `SelStraContext`；即使
  手动调用 `initSelStrategies`，它也读取 cta 键。非 HFT 的 SEL 环境还会走 CTA 初始化
  分支，但其后果（是否创建/运行无效 CTA context）没有动态验证。
- 复核结论: 源码结构支持配置文件驱动的 SEL 策略未自动装载这一窄结论；不代表 SEL
  引擎整体不可用，显式 `create_sel_context` 的公开路径仍独立存在。没有运行
  `strategies.sel` 的动态测试。
- 修复方向: 在配置收尾按 `_is_sel` 路由到 `initSelStrategies`，并将其配置键改为 sel；
  添加真实 `strategies.sel` 条目的测试，断言 SEL context 创建及其策略初始化回调。
- 严重级别: 中（仅限配置文件驱动策略装载；实盘资金影响未由动态证据证明）

## BUG-R134-004 实盘 `registerExtDataLoader` 静默丢弃 tickLoader

- 编号: BUG-R134-004
- 模块/文件/行: `src/WtPorter/WtRtRunner.h` L242-247；导出入口 `src/WtPorter/WtPorter.cpp` L96-104
- 测试用例: `R134PorterBars.*` 只注册 fnl/raw loader，tick 参数传入 NULL；测试没有验证
  非空 tickLoader，因此不提供该问题的动态证据。
- 输入: `register_ext_data_loader(fnl, raw, fct, tickLoader)`，其中 `tickLoader` 非空
- 期望: tickLoader 被保存，`WtDtMgr`/`WtDataReader` 需要 tick 数据时可回调
- 实际: 导出 `register_ext_data_loader` 有四个参数且注释声明支持 tick loader，但
  `WtRtRunner::registerExtDataLoader` 将该参数注释掉、不存储，也没有对应成员；参数在该
  路径上被丢弃。另 `WtPorter.cpp::feed_raw_ticks` 当前只是记录 API not implemented，
  所以修复不能止于保存回调，还需接通回调与 tick 数据写入/读取链路。
- 证据边界: 参数被忽略可由签名和函数体静态确认；本波用例传 NULL，没有计数器运行验证。
  不据此断言实盘 tick 只能来自 `.dmb`，只确认公开外部 loader 参数目前无效。
- 修复方向: 明确实盘 loader 的回调时机与数据馈入契约，在 runner/data manager 保存并调用
  tickLoader，且实现可用的 tick feed 路径；若产品暂不支持，则需同步修正公开 API/注释，避免
  声称接受并支持该参数。
- 严重级别: 中（公开注释契约与实现不符；影响范围需通过非空回调集成测试确定）
