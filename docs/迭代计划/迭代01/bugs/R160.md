## BUG-R160-001 WtCore EventNotifier 的订单通知 retain 后不 release

- 状态: 已合并（迭代02：主编号 BUG-R41-003）
- 位置: `src/WtCore/EventNotifier.cpp:214-230`（`notify(const char*, uint32_t, const char*, WTSOrderInfo*)`）
- 证据: 第 221 行 `ordInfo->retain();`，post 的 lambda 在第 222-227 行只做
  `orderToJson` + `_publisher`，没有对应的 `ordInfo->release();`；同一文件第
  197-212 行的成交通知 lambda 末尾有 `trdInfo->release();`。
- 结论: 源码所有权不平衡，静态确认。每次非空订单通知先 retain；lambda 无 release。
  若 worker 未执行 lambda，排队 handler 被销毁时也不会自动释放这个裸指针引用；若
  handler 被执行，订单回报路径仍少一次 release。Work-guard 停机问题（BUG-R120-001）
  会影响 handler 是否执行，但不消除本条引用泄漏。
- 影响: 每次接受的非空订单通知多保留一个引用。内存增长是由引用计数语义推导出的
  风险，本轮没有做长时间/高频内存测量。
- 建议: 用 RAII 持有订单引用，确保成功投递后在 handler 完成或被销毁时都释放；同时
  分别修复 worker 的 work-guard 生命周期。
- 用例关系: R160 的 `WorkGuardKeepsWorkerAliveForEveryPublishLambda` 通过测试侧
  guard 强制执行发布体，现有 rc 记录为 PASS，但只断言主题到达，没有断言订单引用数；
  因此它不是本条泄漏的动态证据。`BUG-R143-001` 位于 `WtUftCore/EventNotifier.cpp`
  的另一份实现，属于同类缺陷，不是同一代码路径的重复记录。


- 迭代02复核: DUPLICATE。订单通知 retain 后异步 lambda 未 release，与 BUG-R41-003 是同调用、同引用失衡和修复点；消息测试未观察对象生命周期。
- 迭代02依据: [逐条裁定与主代理修订](../../迭代02/缺陷裁定总表.md)。原记录保留作为历史，未声称产品已修复。
- 迭代02前状态（历史）: - 状态: 待审核

## BUG-R160-002 EventNotifier 通过不匹配的函数指针调用 create_server

- 状态: 待审核
- 位置: `src/WtCore/EventNotifier.h:18`、`src/WtCore/EventNotifier.cpp:94`
- 证据: `EventNotifier.h` 声明返回 `unsigned long`、参数仅有 `const char*`；
  `WtMsgQue.h` 导出的真实签名是 `WtUInt32 create_server(const char*, bool)`，而
  `WtUInt32` 定义为 `unsigned int`。因此返回类型和参数列表都不匹配，调用点还漏传
  `confirm`。通过不兼容函数指针调用不符合接口契约，属于源码可证的未定义行为。
- 影响: 具体 ABI 后果不能仅凭源码断言为某个随机 bool、确认等待或发布失败；本轮没有
  控制 `confirm` 值的 ABI 运行验证。`MQServer::init` 的 `confirm` 默认语义为 false，
  但导出的 `create_server` 不提供默认实参，调用端必须显式选定语义。
- 建议: 两个 `EventNotifier` 头文件（WtCore 与 WtUftCore）都使用准确的
  `WtUInt32 (*)(const char*, bool)` 类型，并在调用时显式传入产品所需的 `confirm`
  值；同一错误签名在 UFT 实现中也存在，应一起修正。
- 用例关系: R160 的 inproc 通知用例现有 rc 记录为 PASS，证明该次本机运行收到了
  消息；它没有检查 `confirm`，也不能证明不匹配的函数指针调用符合 ABI。

## BUG-R160-003 WtHftRtTicker 自动闭合后把 _time 写成 HHMM，下一轮时间检查按 0 点解释

- 状态: 待审核
- 位置: `src/WtCore/WtHftTicker.cpp:175、:189、:202-216`
- 证据: `_time` 的 tick 输入在 `on_tick` 中按 HHMMSSmmm 保存，线程检查使用
  `_time / 100000`；自动闭合却在 L189 写入仅有 HHMM 的 `thisMin`。例如 1459
  被除以 100000 后为 0。这是稳定的单位不一致。R160 HFT 用例把会话设成
  00:00-03:59，现有 rc 为 PASS，并断言闭合后 `_time == 359`；它直接观察到了
  HHMM 写入，但该人工会话使 0 仍属于交易时段，未验证常见会话中的休市分支。
- 影响边界: 对不包含 00:00 的会话，下一轮线程检查可能把当前时间误判成休市，并走
  10 秒 sleep；若进入该 sleep，`stop()` 的 join 也可能等待到 sleep 结束。实际发生与
  启动时刻、会话定义和行情线程时序有关，本轮未验证实盘调度或收盘延迟。另 `_cur_pos`
  只在 `on_tick` 中更新，不能把“无新 tick 时没有更高分钟位置”单独归因于本条。
- 建议: 保持 `_time` 的 HHMMSSmmm 表示；自动闭合只更新所需的日期/分钟状态，或写回
  与 tick 路径一致的时间格式。为普通日盘及跨午夜会话分别增加受控线程验收。
- 用例关系: R170/R181 对本条的“只自动闭合一次、后续分钟依赖 tick”表述需要按
  `_cur_pos` 的更新条件重新核对；本文件不把该因果作为已证结论。

## BUG-R160-004 WtDtMgr 后复权 tick 缓存未检查 readTickSlice 返回 NULL

- 状态: 待审核
- 位置: `src/WtCore/WtDtMgr.cpp:301-314`
- 证据: 调用后无 NULL 检查便访问 `size()`。`IDataReader::readTickSlice` 的返回类型是
  可空指针；当前 AD reader 在 `get_t_db` 失败时明确返回 NULL，其他 reader 也存在
  空数据/读取失败返回 NULL 的路径。R160 替身 reader 在 HFQ 路径固定返回 3 根 tick，
  现有测试未触发 NULL，也没有动态崩溃证据。
- 影响: 仅在 HFQ 缓存首次构建且底层 reader 返回 NULL 时触发空指针解引用；不是每个
  缺历史数据请求都会崩溃，实际是否返回 NULL 取决于所用 reader 的空数据语义。
- 建议: 读取后判空并按 `IDataReader` 可空结果约定返回 NULL；若 reader 约定空结果为
  零长度 slice，则明确统一该契约并由实现遵守。
- 用例关系: 需要新增/修正替身测试覆盖 NULL reader 返回；本轮未修改测试。
