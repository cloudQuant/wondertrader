## BUG-R114-001 TraderMocker::registerSpi 不判空，TraderAdapter::release 传 NULL 即崩

- 状态: 待审核
- 严重级别: Blocker（进程退出/热重载时崩溃）
- 模块/文件: `src/TraderMocker/TraderMocker.cpp:659-664`；
  触发点 `src/TraderDumper/TraderAdapter.cpp:127-134`（`_trader_api->registerSpi(NULL)`）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  （用例刻意**不**调用 `ad.release()`，并在注释中说明原因）；
  `R114DumperFixture.adapter_release_with_real_ctp_module_is_safe`（换用有判空的 TraderCTP
  才启用 release 正向分支）
- 输入/前置条件: 交易模块为 `TraderMocker`，`TraderAdapter::init` 成功后调用 `release()`
  （`Dumper::release()` 会对每个适配器执行）。
- 期望行为: `registerSpi(NULL)` 应允许用于注销，至少先判 `listener != NULL` 再取
  `getBaseDataMgr()`；`TraderAdapter::release()` 的注销语义应被所有插件支持。
- 实际行为: `TraderMocker::registerSpi` 先写 `_listener = listener`，随后
  `_bd_mgr = listener->getBaseDataMgr()` 无任何判空；传 NULL 立即空指针解引用。
  TraderAdapter 的 release 恰好固定传 NULL，因此 Mocker 通道在 Dumper 退出时必崩。
- 复现步骤:
  1. 在构建目录用 `libTraderMocker.dylib` 作 module，构造
     `TraderAdapter ad(&mgr); ad.init("m", params, &bd);`；
  2. 调用 `ad.release()`；
  3. `_trader_api->registerSpi(NULL)` 进入 TraderMocker.cpp:659，
     在 `listener->getBaseDataMgr()` 处 SIGSEGV。
- 影响范围: 以 Mocker 通道接入的 TraderDumper 在 `Dumper::release()`/进程退出时崩溃；
  也堵住本 lane 对 Mocker 的 `release` 正向覆盖。
- 备注: 同族 `TraderCTP::registerSpi`、`TraderFemas::registerSpi` 都有
  `if (m_sink)` 守卫，只有 Mocker 缺；建议按同形修复。

## BUG-R114-002 `TraderSpi.cpp:331-333` 的第二次 UTF8 判断是死代码

- 状态: 待审核
- 严重级别: Minor（死代码/不可达，浪费一次检查）
- 模块/文件: `src/CTPOptLoader/TraderSpi.cpp:289-295`、`:330-333`
- 相关测试: `R114OptFixture.query_instrument_covers_stock_option_precision_and_encoding`
  （GBK 品种名的用例只命中 `:292` 与 `:295`，`:333` 恒不执行）
- 输入/前置条件: 任意 `pname`：
  - 若 `pname` 非 UTF8，`:294-295` 已把它赋成 `ChartoUTF8(pname)`；
  - 若 `pname` 本就是 UTF8，`:294` 为真，`:333` 的同一判断仍为真。
- 期望行为: 删除多余的 `:331-333`，或在此处对另一个变量做转换。
- 实际行为: `:331` 先 `pname = StrUtil::trim(pname)`，`:332` 再判
  `!EncodingHelper::isUtf8(pname)`，但 `pname` 在 `:295` 已经可能被转成 UTF8；
  两种输入下 `:333` 均不可达。
- 复现步骤: 用 GBK 品种名跑一次 `OnRspQryInstrument`，在 `:333` 下断点/插桩，
  永不命中；llvm-cov 中该行恒为 0。
- 影响范围: 无运行时错误，只让 TraderSpi.cpp 无法达到 100% 行覆盖。
- 备注: 若 `ChartoUTF8` 转换失败返回空串，`:333` 仍不会执行（`isUtf8("")` 为真），
  所以不是“失败重试”逻辑。

## BUG-R114-003 TraderAdapter 保存了 deleteTrader 却从不调用，交易对象与模块句柄泄漏

- 状态: 待审核
- 严重级别: Major（长期运行/反复 init-release 时资源单调增长）
- 模块/文件: `src/TraderDumper/TraderAdapter.cpp:102`（`_remover = get_symbol(..., "deleteTrader")`）、
  `:127-134`（`release()` 只调 `ITraderApi::release()`）、`:48-50`（析构为空）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  与 `adapter_release_with_real_ctp_module_is_safe`（两条用例都能成功 init，
  但用例结束时 `_trader_api` 仍由插件分配、无人 delete）
- 输入/前置条件: 任意能成功 `createTrader` 的模块；适配器析构或 `release()`。
- 期望行为: `release()`/析构应执行 `_remover ? _remover(_trader_api) : delete _trader_api`，
  并置空 `_trader_api/_remover/_cfg`，与 Init 的 `createTrader` 配对。
- 实际行为: `_remover` 读取后从未使用；`release()` 只调插件自己的 `release()`，
  `TraderAdapter` 析构也为空。每次 Dumper 初始化/重载都泄漏一个 `ITraderApi`
  实例（Mocker 还包括 `mocker_<id>/` 内的资源），DllHandle 也没有释放。
- 复现步骤:
  1. `TraderAdapter ad(&mgr); ad.init("x", paramsWithMocker, &bd);`
  2. `ad.release();` 后让 `ad` 析构；
  3. 在 `createTrader`/`deleteTrader` 上打计数：`create` +1，`delete` 永远 0。
- 影响范围: 长期运行的落地进程反复初始化交易通道时内存与模块引用单调增长；
  插件侧若有全局线程/连接，`release()` 之外的实例生命周期不受控。
- 备注: `TraderAdapter.h:84` 的 `_remover` 字段因此成为只写死字段；
  与 T3-011（忽略 init 返回值后仍登记适配器）叠加时泄漏更隐蔽。

## BUG-R114-004 `TraderAdapterMgr::decAlive` 在 0 上 `fetch_sub` 会回绕，`isAnyAlive` 永久为真

- 状态: 待审核
- 严重级别: Major（`Dumper::run(true)` 死循环，进程无法正常退出）
- 模块/文件: `src/TraderDumper/TraderAdapter.cpp:393-411`
  （`:396 auto left = _live_cnt.fetch_sub(1);`）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  与 `adapter_mgr_dec_alive_reports_undone_and_refresh_queries_done`：
  - 前者的局部 mgr 先 `run()` 成空表（`_live_cnt=0`），随后 `onRspOrders` 的
    `decAlive()` 实际触发 `0 → UINT32_MAX` 回绕；用例只断言 `_done`，**不**再读
    `isAnyAlive()`，因此不会把挂死带进测试。
  - 后者用 3 条失败适配器严格 3→0，证明正常递减序列；同一个用例没有第 4 次调用。
- 输入/前置条件: `_live_cnt` 已为 0（例如所有通道都已完成 `onRspOrders` 的
  `decAlive`，或 `run()` 时表为空），又收到一次失败/完成回调。
- 期望行为: `fetch_sub` 前判 `_live_cnt > 0`，或使用饱和递减；`decAlive` 应幂等。
- 实际行为: `std::atomic<uint32_t>::fetch_sub(1)` 在 0 上回绕成 `UINT32_MAX`；
  `left > 0` 成立后只减到 `UINT32_MAX-1`，随后 `isAnyAlive()` 永远为真。
  `Dumper::run(true)` 的 `for(;;) { if(isAnyAlive()) sleep(1s); else break; }`
  因此永不退出；`decAlive` 的 `left <= 2 && left > 0` 日志分支也不会命中。
- 复现步骤:
  1. 构造 `TraderAdapterMgr mgr; mgr.run();`（空表，`_live_cnt=0`）；
  2. 再调用一次 `mgr.decAlive()`；
  3. `mgr.isAnyAlive()` 返回 true；随后 `Dumper::run(true)` 挂死。
- 影响范围: 交易通道重复回报/失败路径下，落地进程无法按预期结束；
  与 T3-009（`_live_cnt` 构造未初始化）叠加时静态上就无法预测初始值。
- 备注: 同一函数里 `left` 先 `fetch_sub` 返回旧值、再 `if(left>0) left--`，
  日志打印的 `left` 与原子量实际值也不一致，建议一并改为 `compare_exchange` 循环。
