## BUG-R114-001 TraderMocker::registerSpi 不判空，TraderAdapter::release 传 NULL 即崩

- 状态: 已合并（主编号 BUG-R175-001；BUG-R144-001 为同根因记录，TraderDumper 调用点是补充证据）
- 审查结论: 已确认的 NULL 解引用，但与 BUG-R175-001 / BUG-R144-001 重复；此条只补充 TraderDumper 调用点，不新增缺陷计数。
- 严重级别: 按 Mocker release 崩溃评估（本轮静态确认；不重复定级）
- 模块/文件: `src/TraderMocker/TraderMocker.cpp:659-664`；
  触发点 `src/TraderDumper/TraderAdapter.cpp:127-134`（`_trader_api->registerSpi(NULL)`）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  刻意**不**调用 `ad->release()`，所以没有动态触发本路径；
  `adapter_release_with_real_ctp_module_is_safe` 只验证 TraderCTP 的 release 分支。
  既有 `R175.md` 报告了其他 adapter 调用点的崩溃栈，本轮未重跑。
- 输入/前置条件: 交易模块为 `TraderMocker`，`TraderAdapter::init` 成功后调用 `release()`
  （`Dumper::release()` 会对每个适配器执行）。
- 期望行为: TraderDumper 的 `release()` 明确先解绑 listener 再释放插件；实现应在 NULL 时
  安全清空 listener 和其关联 manager。ITraderApi 头文件未单独写明 NULL 契约；但 Dumper
  调用点固定传 NULL，且 TraderCTP/TraderFemas 的同接口实现均判空，因此跨插件兼容需要统一。
- 实际行为: `TraderMocker::registerSpi` 先写 `_listener = listener`，随后
  `_bd_mgr = listener->getBaseDataMgr()` 无判空；传 NULL 会空指针解引用。`TraderAdapter::release`
  固定传 NULL，所以 Mocker 通道执行该 release 路径会崩。这里的产品根因与 R175/R144 相同，
  本条只证明 TraderDumper 也是受影响调用方。
- 复现步骤: 静态路径为 `TraderAdapter::release()` → `registerSpi(NULL)` →
  `listener->getBaseDataMgr()`。本轮没有运行该崩溃路径；R114 的 Mocker 用例特意避开 release。
- 影响范围: TraderDumper 通过 Mocker 模块且执行 adapter release 时受影响；其它影响调用点见
  已登记的 R175/R144，不在此重复统计。
- 备注: 修复方向：在 `TraderMocker::registerSpi` 中对 NULL 安全清理 `_listener`、`_bd_mgr`；
  或在 TraderAdapter 维护注册状态并只在已注册时解绑。应保持接口所有实现一致，且测试 teardown
  真实调用 Mocker release。`TraderCTP::registerSpi`、`TraderFemas::registerSpi` 已有空值守卫。

## BUG-R114-002 `TraderSpi.cpp:331-333` 的第二次 UTF8 转换仅在转换器异常输出时有作用，死代码结论待证

- 状态: 已撤回（当前仅为冗余/防御代码观察，无已证产品故障；转换失败合同另待验证）
- 审查结论: 证据不足以判为产品缺陷；常规成功转换时属于冗余检查候选
- 严重级别: 不适用（当前没有用户可见错误证据）
- 模块/文件: `src/CTPOptLoader/TraderSpi.cpp:289-295`、`:330-333`
- 相关测试: `R114OptFixture.query_instrument_covers_stock_option_precision_and_encoding`
-  （GBK 用例经过首轮 `ChartoUTF8`；`:332` 条件可执行，但正常转换输出使 `:333` 分支不执行。）
- 输入/前置条件: `pname` 先在 `:294-295` 做一次 UTF-8 检查/转换，只有 `_commodities.find(key)` 未命中
  才会在 `:331-333` trim 后再次检查。普通 UTF-8 输入与成功的 GBK→UTF-8 转换会使第二次转换体不执行。
- 期望行为: 保留正确的输入编码并避免无效重复工作；若删除第二轮检查，应先证明 `ChartoUTF8` 对
  所有受支持输入必然给出有效 UTF-8，或明确把转换失败作为错误处理，而不是仅为覆盖率删除保护。
- 实际行为: 两次检查之间除 `StrUtil::trim` 外，`pname` 没有其他赋值，故常规成功转换下第二轮
  转换是冗余的。但 `ChartoUTF8` 的错误输入/转换失败输出契约没有由本轮测试证明；`charconv.hpp`
  的转换代码也没有向此调用点返回成功标志。因此不能断言所有执行情形下 `:333` 分支不可达。
- 测试边界: 现有 GBK case 在 `_commodities` 初次 miss 时执行第二轮 `isUtf8` 判断，结果为 true，
  只说明该正常样本不需要再次转换；未覆盖 iconv 失败、残缺字节或 converter 输出无效的情形。本轮未运行测试。
- 影响范围: 当前没有由此造成错误编码的证据；“行覆盖未达 100%”不是产品故障。
- 备注: 归类为冗余/防御代码审查项，暂不立案为功能缺陷。若希望移除，应先为 converter 建立明确
  的成功/失败契约并验证其输出；若维持容错，则可把二次转换保留为防御分支。

## BUG-R114-003 TraderAdapter 保存了 deleteTrader 却从不调用，交易对象与模块句柄泄漏

- 状态: 待审核
- 审查结论: 产品资源生命周期缺陷（静态源码确认；无动态泄漏量测）
- 严重级别: Major（长期运行/反复 init-release 时资源单调增长）
- 模块/文件: `src/TraderDumper/TraderAdapter.cpp:102`（`_remover = get_symbol(..., "deleteTrader")`）、
  `:127-134`（`release()` 只调 `ITraderApi::release()`）、`:48-50`（析构为空）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  为避开 BUG-R114-001 不调用 release；`adapter_release_with_real_ctp_module_is_safe` 调用 CTP
  `release()` 但不检测 `deleteTrader`。本轮未运行测试，也没有计数器、sanitizer 或堆快照证据。
- 输入/前置条件: 任意能成功 `createTrader` 的模块；适配器析构或 `release()`。
- 期望行为: `release()`/析构应先停止并释放插件 API，再通过对应模块导出的 `deleteTrader`
  销毁对象；模块句柄必须在插件对象销毁之后才可卸载。`FuncDeleteTrader` 是 `ITraderApi.h:286-287`
  定义的插件销毁函数类型；不应未经 ABI/分配器契约证明就用主程序 `delete` 作为 fallback。
- 实际行为: `init()` 的局部 `hInst` 在 `:81` 打开模块，`:102` 只保存 `deleteTrader` 地址，
  没有把 handle 写入成员；`release()` 在 `:127-134` 只调用 `registerSpi(NULL)` 和插件 `release()`；
  析构函数 `:48-50` 为空。`_remover` 不会被调用，`DLLHelper::free_library` 也没有调用点，
  因而通过该生命周期成功创建的 API 对象未被销毁且模块引用未释放。该代码路径重复执行时，
  资源会随次数累积；实际每次累积的字节数/模块卸载行为未做动态测量。
- 复现步骤: 由源码可静态追踪 `createTrader` → 保存 `_remover` → `release()` 未调用 remover →
  空析构；本轮未做运行时 create/delete 计数。
- 影响范围: `TraderAdapterMgr::release()` 遍历适配器调用 `release()` 后清空 map；因此每次
  manager 生命周期结束都会销毁 adapter 外壳，但目前不会销毁 API 对象或释放模块句柄。T3-011
  忽略 init 失败返回值是相关但不同的配置问题；它会扩大半初始化生命周期面，不是本条根因。
- 备注: 修复方向：把 `DllHandle` 与 `_remover` 一起保存，校验 `deleteTrader` 存在后再接受插件；
  release 顺序应为解绑（若已注册）→ 插件 `release()` → `_remover(_trader_api)` → unload handle，
  并清空成员/释放 `_cfg` 以保证幂等。`WtUftCore` 的同形适配器是另一实现；R85-001 记录的是
  其 init 失败回滚问题，不是本条 TraderDumper 正常 release 泄漏的重复项。

## BUG-R114-004 `TraderAdapterMgr::decAlive` 过量调用会使计数器回绕并影响 manager 等待状态

- 迭代02第二轮前状态（历史）: - 状态: 待审核
- 状态: 已撤回（迭代02：TEST，原产品主张不成立）
- 审查结论: 过量调用时原子回绕属静态确认；生产回调能否违反一次/adapter 计数前置条件待验证
- 严重级别: 条件性 Major（只有重复/多余终态回调发生在 `run(true)` 轮询期间才可能延长等待）
- 模块/文件: `src/TraderDumper/TraderAdapter.cpp:393-411`
  （`:396 auto left = _live_cnt.fetch_sub(1);`）
- 相关测试: `R114DumperFixture.mocker_adapter_forwards_account_trade_order_position_records`
  与 `adapter_mgr_dec_alive_reports_undone_and_refresh_queries_done`：
  - 前者的局部 mgr 先 `run()` 成空表（`_live_cnt=0`）；随后直接构造、但没有 `addAdapter`
    登记到 mgr 的 adapter，并对其调用 `onRspOrders`，使 `_mgr->decAlive()` 从 0 下溢。
    这是测试夹具违反 manager 计数前置条件，不是生产 callback 合法性的证据；用例也不检查计数。
  - 后者的三条登记适配器按 3→2→1→0 调用三次，验证正常递减，没有第 4 次调用。
- 输入/前置条件: `_live_cnt` 已为 0 且又发生一次 `decAlive()`（例如同一 adapter 重复终态回调、
  manager 外 adapter 回调到该 manager，或其他 over-decrement）；计数仍大于 0 时的过量调用也会提前
  耗尽其他通道的计数。manager 是否要求 exactly-once
  由调用约定隐含，`TraderDumper`/`ITraderApi` 没有在这些接口处明确记录重复回调语义。
- 期望行为: 若 manager 对多余通知需要防御，应饱和递减；更重要的是每个 adapter 只能发布一次
  终态完成信号，重复 `onRspOrders` 不应重复减计数。
- 实际行为: `fetch_sub(1)` 的返回值是旧值。旧计数为 0 时，局部 `left==0`，但原子值回绕为
  `UINT32_MAX`。现有 `if (left > 0) left--` 不会改变局部值，日志仍打印 0；因此原文所述
  “局部 left 减到 UINT32_MAX-1”不成立。此时 `isAnyAlive()` 因原子非零返回 true；原子需经历
  `2^32-1` 次额外递减才回到 0，所以现实中可视为长期非零，但不是数学上的永久。
  `Dumper::run(true)` 只会在它已开始等待、且 extra decrement 发生在它观察到 0 并返回之前时
  被延长；`Dumper::run()` 本身会先用 adapter 数量重设计数，不能用一个独立局部 mgr 的下溢
  直接推导随后调用全局 `Dumper::run(true)` 会挂死。`run(false)` 不走该等待循环。
- 复现步骤: 静态地对 `mgr.run()` 空表后再调 `mgr.decAlive()` 可推导 `isAnyAlive()` 为 true；
  本轮未运行该路径。R114 正向回调测试中的 manager 外 adapter 恰好会触发 underflow，但该输入
  不满足生产 manager 的 adapter 数量约束，不能作为产品级 hang 的动态复现。
- 影响范围: 只有实际 over-decrement 才会破坏计数；计数尚未归零时的重复通知可能令
  `run(true)` 提前返回，归零之后但等待循环尚未观察到零时的重复通知会使其继续等待。
  重复终态回调在生产插件中是否可能、以及具体时序均待验证。T3-009 的构造未初始化是独立初始化问题；
  正常 `run()` 会先按 adapter 数量设值，不把它作为本条下溢证据。
- 备注: 修复方向：在 manager 侧用 compare-exchange 实现饱和递减，并在 adapter 侧用原子状态
  保证终态只减一次；调整 R114 测试将 adapter 加入 manager 并设置 `_live_cnt` 一致，再单独测
  重复完成回调的期望行为。现有文档中的“随后 Dumper.run(true) 必挂死”应撤回。
