## 观察 2：`WtBtRunner::_inited` 与 `config_backtest` 的 `static inited` 都不置 true

- 位置: `WtBtRunner.cpp:451-455`；`WtBtPorter.cpp:156-185`
- 复核证据: 最新基线 452/179 仍为 0；全文件没有 `_inited = true`，`config_backtest` 内也没有
  `inited = true`。第二次 config 会重复 `initEvtNotifier`、`_replayer.init` 并重建 mocker。
- 证据性质: 这是源码静态结论，未由 R183 动态运行验证。`config_backtest` 的头文件注释承诺
  “只会执行一次、重复调用忽略”；`WtBtRunner::config` 的 `_inited` 在构造时为 false 且配置路径
  未设置为 true。若再次通过此公开配置入口，会再次初始化并覆盖 mocker 指针；资源泄漏风险来自
  源码覆盖分配点的推断，不是本 lane 观察到的运行时泄漏。
- 判定: 守卫不可达，重复初始化有资源泄漏/旧 mocker 悬空风险。
- 本 lane 处理: 不写「第二次不重建」的 active 用例（必红），也不写「会重建」固化缺陷；
  留白并在清单第 5 节标注。
- 交叉引用: `BUG-R173-004` / `BUG-R134-001` / `BUG-R134-002`。

## 观察 3：UFT 切片接口首行返回 NULL，订阅分支死代码

- 位置: `WtUftEngine.cpp:179-243`；`UftStraContext.cpp:944/954/963/972/982`
- 复核证据: `get_tick_slice/get_kline_slice` 第一行无条件 `return NULL`，后续
  `_bar_sub_map` 写入、周期换算、`_data_mgr->get_kline_slice` 全部不可达；上层
  `if (ret) _engine->sub_tick(...)` 永不进入。
- 判定: 当前实现明确是 TODO stub，并无条件返回 NULL；因此当前版本无法通过这两个入口取到
  K 线/Tick 切片，后续订阅代码不可达。是否按产品缺陷计数取决于 UFT API/版本是否承诺支持这项
  能力；在本记录中归类为“能力未实现/契约待确认”，不把返回 NULL 的安全路径误写成 PASS。
- 本 lane 处理: `R183UftEngine` 源码断言只说明当前 NULL 行为；manifest 记载未运行二进制，
  因此该行为不是本 lane 动态验证。修复方向是先确认接口能力契约，再实现数据管理器调用及订阅
  登记的一致生命周期并补非空切片回归；若契约本就规定 TODO/未支持，则明确文档而不立缺陷。
- 交叉引用: `BUG-R173-001` / `BUG-P06-005` / `BUG-R123-001`。

## 观察 4：`TraderAdapter` 频率风控窗口写入点被注释

- 位置: `src/WtUftCore/TraderAdapter.cpp:1864-1965`；插入语句 `:340`（下单）、`:392/:420`
  （撤单）均为注释；正常 buy/sell/open/close 调用风控的若干位置也被注释
  （`:444/:724/:996/:1025/:1054/:1083`）。
- 复核证据: `checkCancelLimits/checkOrderLimits` 的时间窗 `lower_bound/erase/封禁` 分支
  在基线为 0；这三个唯一的缓存插入语句均被注释，故经正常适配器路径不会形成时间窗样本，
  `cnt >= boundary` 分支没有公开写入路径。显式调用检查函数仍可运行总量/排除队列检查。
- 判定: 源码支持“UFT 适配器正常下单/撤单未接入频率窗口”这一实现缺口；不据此声称已发生
  生产违规或量化具体风险，仍需产品契约确认该开关在此版本是否应启用。
- 本 lane 处理: 没有公开缓存写入 API；不伪造私有成员状态。修复方向是恢复成功下单/撤单后的
  对应时间戳写入和调用前的检查门控，并按标准化代码核对写入/查询键的一致性；需要同键多次操作
  的定向测试，当前 R183 未运行该测试。
- 交叉引用: `BUG-Q04-004` / `BUG-R173-002`。

## 观察 5：`DataManager` 缺 writer 符号后解引用 NULL；`ParserAdapter` 无 writer 时索引分支不可达

- 位置: `DataManager.cpp:83-98`；`WtDtCore/ParserAdapter.cpp:307-309`
- 复核证据: `DataManager::init` 对已加载但缺 `createWriter` 或 `deleteWriter` 的模块只记录错误，
  然后仍可能到达 `_writer->init(...)`；若 writer 缺失，该路径存在空指针解引用风险。它以定制
  插件缺符号为前提，R183 未构造插件，属于静态确认的条件性缺陷候选而非动态复现。
  `ParserAdapter::handleQuote` 的 `_idx_fact->handle_quote` 另有正常前置条件：必须先有合约、再由
  `_dt_mgr->writeTick` 成功；当 writer 缺失时 `writeTick` 返回 false，所以该索引调用不会发生。
  这证明的是该故障配置下分支被守卫挡住，不是 `ParserAdapter` 自身缺陷。
- 本 lane 处理: 不构造缺符号 writer。`R183DtIndexWorkerMgr` 测的是缺少 index factory 入口的跳过
  路径，与 DataManager writer 错误处理不是同一测试。修复方向是 DataManager 检查两符号及
  `createWriter()` 返回值，失败时返回 false 并保持可析构；另为 ParserAdapter 保留正常写入门控。
- 交叉引用: `BUG-R18-002`、`BUG-R18-003`、`BUG-R44-005`。

- 本 lane 处理: `R183DtIndexWorkerMgr` 先 `init(poolsize=0)` 注入 `bdMgr` 再取 accessors，
  避免读取未初始化指针；不把该缺陷固化成「必须为 NULL」的断言。
- 交叉引用: `BUG-R44-007`。
