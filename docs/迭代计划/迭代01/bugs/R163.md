## BUG-R163-001 EventNotifier 的 worker 首轮 run_one 会把 io_context 永久 stop，所有通知永不投递

- 编号: BUG-R163-001
- 模块/文件: `src/WtUftCore/EventNotifier.cpp:98-109`（worker 创建）、`:114-227`（五个 notify 入口）
- 相关测试: `R163UftNotifier.DISABLED_WorkerDeliversPostedTradeNotification`
  （`src/TestUnits/coverage/q04_uftcore3/r163_uftcore_guards_test.cpp`）；
  既有 `R143UftNotifier.postsTradeJsonAndReleasesRetainedPayload` 已在该环境下失败
- 输入/前置条件: `WtMsgQue` 可加载，`active=true`、`url=inproc://...`，`EventNotifier::init` 返回 true；
  随后调用 `notify(trader, localid, stdCode, WTSTradeInfo*)`
- 期望行为: worker 在 2ms 轮询周期内执行 post 的 lambda：组装 JSON、调用 publisher、`release()`；
  测试侧 `retainCount` 从 2 回到 1
- 实际行为: `init()` 里的 `auto work = boost::asio::make_work_guard(_asyncio)` 是 **代码块内局部变量**
  （L100），代码块结束即析构，io_context 的 outstanding work 归零。worker 线程随后
  `sleep_for(2ms)`，第一次 `_asyncio.run_one()`（L105）进入
  `boost::asio::detail::scheduler::run_one`；其实现先判 `outstanding_work_ == 0`，
  成立时直接 `stop()` 并返回 0（本机 boost 1.88 `detail/impl/scheduler.ipp:214-229`）。
  io_context 从此处于 stopped 状态，后续 `boost::asio::post` 只入队、不再被任何
  `run_one()/run()` 执行。`notify_log/notify_event/notify(trader,message)` 与两个回报通知
  全部静默丢失；成交通知的 `release()` 也永不执行，引用计数永久 +1。
- 复现步骤:
  1. 准备可加载的 `libWtMsgQue.dylib`，`EventNotifier::init` 使用 `inproc://r163_...` 返回 true；
  2. `WTSOrderInfo`/`WTSTradeInfo` 创建后 `retainCount()==1`；
  3. `notifier.notify("r163", 5, "SHFE.ag2406", trd)`，等待 500ms；
  4. 观察 `trd->retainCount()` 恒为 2（lambda 未执行），析构 join 后仍为 2；
  5. 既有 R143 用例日志
     `build-cov/coverage/CoverageTests_uftcore.R143UftNotifier_postsTradeJsonAndReleasesRetainedPayload.log`
     同样记录 `Expected equality ... 1u ... trd->retainCount() Which is: 2`。
- 证据（覆盖率）: `llvm-cov show` 下 `EventNotifier.cpp` 的 L121 有 7 次命中，而
  L122-140/150-166/177-194 全为 0——post 语句执行了，任务体一次都没执行。
- 严重级别: 高（事件通知通道整体静默失效；同时把成交通知变成引用泄漏）
- 修复方向: 把 work guard 提升为成员（init 到析构期间保持 outstanding work），
  或在 worker 里先 `poll()`/检查 `stopped()` 后 `restart()` 再 `run_one()`；
  修复后 `R163UftNotifier.DISABLED_*` 可直接启用。
- 状态: 待审核

## BUG-R163-002 WtRtRunner::initSelStrategies 从未被调用，且读取的是 strategies.cta

- 编号: BUG-R163-002
- 模块/文件: `src/WtPorter/WtRtRunner.cpp:745-789`（函数定义）、`:708-711`（唯一分派点）
- 相关测试: 静态核对；`R69PorterRunnerConfig` 已有 env=sel 的配置用例，但只验证引擎类型
- 输入/前置条件: 配置 `env.name="sel"`，并在 `strategies` 下提供 SEL 策略数组
- 期望行为: SEL 运行环境加载配置中的选股策略并 `addContext`，与 CTA/HFT 的
  `initCtaStrategies/initHftStrategies` 对称
- 实际行为: `config()` 在 L708-711 只调用 `initCtaStrategies()`（非 HFT）或
  `initHftStrategies()`（HFT）；全文件对 `initSelStrategies` 只有定义、没有任何调用点
  （`grep -n initSelStrategies` 仅 L745）。即使被调用，函数内 L751 读取的也是
  `_config->get("strategies")->get("cta")`，与 SEL 的配置键不符，属复制粘贴遗留。
  结果是 SEL 引擎的 `_ctx_map` 永远为空，配置里写的选股策略被静默忽略。
- 复现步骤:
  1. `env.name="sel"`，`strategies.cta` 放一个 active 策略项；
  2. `WtRtRunner::config` 返回 true，`getEngine()` 为 `WtSelEngine`；
  3. `initSelStrategies` 无调用，`_sel_engine` 中没有对应 context；
  4. 通过 `create_sel_context` 之外的配置方式无法让策略运行。
- 严重级别: 中（SEL 生产配置静默失效；不影响 CTA/HFT）
- 状态: 待审核
