## BUG-R163-001 EventNotifier 局部 work guard 释放后，空闲 run_one 可停止 io_context

- 编号: BUG-R163-001
- 模块/文件: `src/WtUftCore/EventNotifier.cpp:98-109`（worker 创建）、`:114-227`（五个 notify 入口）
- 相关测试: `R163UftNotifier.DISABLED_WorkerDeliversPostedTradeNotification`
  （`src/TestUnits/coverage/q04_uftcore3/r163_uftcore_guards_test.cpp`）；
  既有 `R143UftNotifier.postsTradeJsonAndReleasesRetainedPayload` 已在该环境下失败
- 输入/前置条件: `WtMsgQue` 可加载，`active=true`、`url=inproc://...`，`EventNotifier::init` 返回 true；
  随后调用 `notify(trader, localid, stdCode, WTSTradeInfo*)`
- 分类: 源码可证的 work-guard 生命周期错误；与 WtCore `BUG-R120-001` 属同类机制，
  但这里是独立的 WtUftCore 实现点。
- 期望行为: `EventNotifier` 在其生命周期内持续处理已投递任务，或在设计的停机/重启
  协议中明确恢复 `io_context`；成功处理的成交 handler 应执行对应 `release()`。
- 实际行为: `init()` 的 `make_work_guard(_asyncio)` 是代码块内局部变量（L100），退出
  代码块后 guard 释放。worker 每 2ms 调一次 `run_one()`；Boost 1.88 的 scheduler 在
  outstanding work 为零时会停止 context。该源码路径成立，但“所有通知永不投递”过强：
  若通知先于 worker 的首次空闲 `run_one()` 入队，该 handler 仍可能先被执行；一旦首次
  空闲调用把 context 停止，后续 post 不会自动令 stopped context 恢复运行。
- 复现步骤:
  1. 准备可加载的 `libWtMsgQue.dylib`，`EventNotifier::init` 使用 `inproc://r163_...` 返回 true；
  2. `WTSOrderInfo`/`WTSTradeInfo` 创建后 `retainCount()==1`；
  3. 为确定性验证，应先通过 worker barrier/状态观测确认一次空闲 `run_one()` 已发生，
     再投递交易通知；现有 `DISABLED_WorkerDeliversPostedTradeNotification` 在 notify 后
     立即轮询，没有等待首次空闲调用或检查 stopped 状态，若启用会受时序影响。
  4. 现存 `R143UftNotifier.postsTradeJsonAndReleasesRetainedPayload` 日志记录
     `trd->retainCount() == 2` 而期望 1，是一次本地动态失败，与 handler 未执行相符；
     单次失败不能证明所有时序、所有通知类型均丢失。
- 证据边界: 本轮未运行 R163 禁用测试。现存覆盖率显示 post 调用点有命中、部分 handler
  体无命中；这与上述时序问题一致，但不能据此断言任何 post 都未处理。上述 R143 日志是
  单次运行记录，不是跨时序验证。
- 严重级别: 高（在 worker 首次空闲 poll 后，后续通知可能积压且不再处理；影响面依赖
  初始化与投递时序）。成交 retain 是否泄漏还要区分 lambda 未执行与订单 handler 自身缺
  release 的独立问题。
- 修复方向: 保留成员级 work guard，直到停止并 join worker；或实现受控的 worker 生命周期，
  确保 context 停止后的恢复由同一线程安全协调。测试应确定 worker 已完成首次空闲 poll
  后再投递并检查通知处理，同时另测初始化后立即投递路径。不要与 R143 的订单引用缺陷合并。
- 状态: 待审核

## 重复复核（原 BUG-R163-002）：WtRtRunner::initSelStrategies 未接入 SEL 配置分派

- 编号: BUG-R163-002
- 分类: 与 BUG-R69-002 为相同配置分派缺陷，不另计缺陷。
- 模块/文件: `src/WtPorter/WtRtRunner.cpp:745-789`（函数定义）、`:708-711`（唯一分派点）
- 相关测试: 静态核对；`R69PorterRunnerConfig` 已有 env=sel 的配置用例，但只验证引擎类型
- 输入/前置条件: 配置 `env.name="sel"`，并在 `strategies` 下提供 SEL 策略数组
- 期望行为: SEL 运行环境加载配置中的选股策略并 `addContext`，与 CTA/HFT 的
  `initCtaStrategies/initHftStrategies` 对称
- 实际行为: `config()` 在 L708-711 只调用 `initCtaStrategies()`（非 HFT）或
  `initHftStrategies()`（HFT）；全文件对 `initSelStrategies` 只有定义、没有任何调用点
  （`grep -n initSelStrategies` 仅 L745）。即使被调用，函数内 L751 读取的也是
  `_config->get("strategies")->get("cta")`，与 SEL 的配置键不符。该静态调用图和键名
  错配已由 BUG-R69-002 记录；不在本轮重复论证运行时所有 SEL 部署均为空。
- 复现步骤:
  1. `env.name="sel"`，`strategies.cta` 放一个 active 策略项；
  2. `WtRtRunner::config` 返回 true，`getEngine()` 为 `WtSelEngine`；
  3. `initSelStrategies` 无调用，`_sel_engine` 中没有对应 context；
  4. 通过 `create_sel_context` 之外的配置方式无法让策略运行。
- 严重级别: 中（SEL 策略配置接入缺口；影响应由 R69 主记录统一计算）
- 状态: 已合并（主编号 BUG-R69-002）
