## BUG-R83-001 `init_sel_mocker` 传入超长模板/时段名会越过 `register_task` 的定长字段

- 状态: 静态内存边界已确认；NULL 可空性待接口契约确认（未动态复现）
- 严重级别: Major
- 模块/文件:
  - `src/WtBtPorter/WtBtPorter.cpp:338-341`（C 导出直接转发 `trdtpl`/`session`）
  - `src/WtBtPorter/WtBtRunner.cpp:299-313`（`initSelMocker` 原样转给 `register_task`）
  - `src/WtBtCore/HisDataReplayer.cpp:407-434`（`strcpy(_task->_trdtpl, trdtpl)` 在 L425，`strcpy(_task->_session, session)` 在 L426）
  - `src/WtBtCore/HisDataReplayer.h:355-368`（`TaskInfo::_trdtpl/_session` 均为 `char[16]`）
- 源码证据: 导出层和 `WtBtRunner::initSelMocker` 原样转发两个 `const char*`；`register_task` 用无界 `strcpy` 写入堆上 `TaskInfo::_trdtpl[16]` / `_session[16]`。任一有效 C 字符串长度达到 16 字节，连同末尾 NUL 至少写入 17 字节，越出对应数组并覆盖后续字段。公开头文件只说明默认值，没有给出长度上限。
- NULL 边界: 当前实现无 NULL 守卫，传 NULL 会把无效指针交给 `strcpy`；但 C API 头文件没有声明 NULL 可空，也没有承诺 NULL 回落默认值。应将 NULL 视作需拒绝的无效输入，不能声称绑定语言“通常会传 NULL”或默认为可选值。
- 相关测试: `src/TestUnits/coverage/q06_btporter/r83_btporter_mocker_surface_test.cpp`
  -> `R83BtPorterParamGuards.DISABLED_InitSelMockerNullTemplatesCrashes`
  （崩溃类，保留 DISABLED 占位）
- 候选边界输入（未执行）:
  ```
  init_sel_mocker("r83_sel_null", 20240102, 93000, "d", NULL, NULL, 0, false);
  ```
  以及 `trdtpl = "ABCDEFGHIJKLMNOPQRSTUVWXYZ"`（26 字符）。
- 期望/修复方向: 在 `register_task` 或最近的参数入口拒绝 NULL 和长度 `>= sizeof(_trdtpl/_session)` 的值，返回可观察的失败状态；如 API 需要默认值，应由 API 明确将“未提供”与 NULL 区分。避免无界复制；必要时改字段为拥有型字符串。
- 实际影响: 超长有效字符串可静态证明导致堆对象字段越界；NULL 路径源代码缺少守卫，但具体进程表现未执行。不得据此推断 Python/Go/Rust 正常绑定会传 NULL。
- 测试证据边界: `DISABLED_InitSelMockerNullTemplatesCrashes` 只包含 NULL 入参；本次未运行。它没有对超长输入做断言，也没有记录动态崩溃证据。建议后续分别测试 NULL 拒绝和长度 15/16 的边界行为。
- 备注: 与 Q06-006（`write_log` 的 `catName` 不判空）、R13-007（实盘导出层
  字符串参数不判空）同属「导出层缺 SAFESTR/长度校验」，但本条落在
  `init_sel_mocker` 的模板参数与 `TaskInfo` 定长数组，前两处均未覆盖；
  建议修复时统一在 `register_task` 用 `strncpy` + 强制 `'\0'`。

## BUG-R83-002 `hft_buy`/`hft_sell` 返回函数级共享可变字符串（调用生命周期/并发契约待确认）

- 状态: 条件性风险（静态共享缓冲已确认；无非空/并发动态证据）
- 严重级别: Minor
- 模块/文件:
  - `src/WtBtPorter/WtBtPorter.cpp:1906-1917`（`hft_buy` 的 `static std::string ret`）
  - `src/WtBtPorter/WtBtPorter.cpp:1937-1948`（`hft_sell` 同形）
  - 对照 `src/WtBtPorter/WtBtPorter.cpp:1874`（`hft_cancel_all` 用的是
    `static thread_local std::string ret`）
- 源码证据: `hft_cancel_all` 已经把返回缓冲声明为 `thread_local`，但 `hft_buy`/
  `hft_sell` 仍是非线程局部的函数级 `static std::string ret`。返回给调用方的
  `const char*` 指向这块共享缓冲：
  - 同一线程内，第二次 `hft_buy/hft_sell`（哪怕属于另一个 HFT 上下文）会覆盖
    第一次返回的内容，先前保存的指针立刻失效；
  - 多线程宿主（不同策略线程各自下单）并发写同一个 `std::string`，属数据竞争，
    可能读到撕裂的委托 ID 串。
- 相关测试: `R83BtPorterHft.HftGettersOrdersAndSlicesInChildProcess`
  （空基础数据下 `stra_buy/stra_sell` 返回空 `OrderIDs`，两次结果都是空串，
  只能证明单线程空簿路径不崩；非空返回需要真实商品/合约数据，未启用）
- 输入: 两个 HFT 上下文 `h1`、`h2`（或同一上下文连续两次），有可成交合约数据时：
  ```
  const char* p1 = hft_buy(h1, "SHFE.rb2510", 450.0, 1, "a", 0);
  const char* p2 = hft_buy(h2, "SHFE.rb2510", 450.0, 1, "b", 0);
  // p1 与 p2 指向同一块 static 缓冲
  ```
- 条件期望: 若 API 承诺返回值可跨同函数后续调用保留或支持并发调用，应提供明确所有权/同步的返回方式；`thread_local` 只能隔离线程，不能延长同线程缓冲的有效期。
- 源码推演（非运行结果）: `hft_buy` 与 `hft_sell` **各自**共享一块静态缓冲，且与同文件
  `hft_cancel_all` 的 `thread_local` 实现不同。本次没有观察到返回串覆盖或数据竞争。
- 候选验证步骤（未执行）:
  1. 用真实合约/行情数据初始化 HFT mocker，使 `stra_buy` 返回非空 `OrderIDs`；
  2. 保存第一次 `hft_buy` 的返回指针 `p1`；
  3. 再用另一个上下文调用 `hft_buy`；
  4. 观察 `p1` 指向的字符串被第二次结果覆盖；
  5. 并发场景下用 TSan 可看到对同一 `std::string` 的竞争写。
- 接口契约与影响边界: 头文件把结果描述为返回订单 ID 字符串，返回类型为 `WtString`（`const char*`），但没有说明其所有权、有效期或并发安全。只有调用方保留同一函数的返回指针到下一次同函数调用之后，或不同线程并发调用同一函数时，才会遇到内容覆盖/数据竞争；若调用方立即复制，生命周期风险不成立。`hft_buy` 与 `hft_sell` 各有自己的静态字符串，调用另一函数不会覆盖本函数缓冲。
- 测试证据边界: `HftGettersOrdersAndSlicesInChildProcess` 因缺商品只断言 `hft_buy/hft_sell` 返回空串；没有非空 ID、指针保留或并发场景，本次未运行。
- 修复方向: 明确结果生命周期和线程安全承诺；如需跨调用保留/并发安全，使用调用方提供的输出缓冲或具有明确所有权的返回接口。仅改 `thread_local` 能隔离线程，不能解决同线程下一次调用覆盖旧结果。
- 备注: 本条不涉及 `hft_cancel_all`（其返回缓冲已用 `thread_local`）。
