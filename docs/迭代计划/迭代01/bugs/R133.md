## BUG-R133-001

- 编号: BUG-R133-001
- 模块/文件: `src/WtUftCore/ParserAdapter.cpp:38-40`（空析构）、`:228-240`（`release`）
- 相关测试: `R133ParserAdapterGuards.filter_and_level2_early_returns`
  （`src/TestUnits/coverage/q04_uftcore3/r133_uftcore_remaining_test.cpp`）
- 输入/前置条件: `ParserAdapter` 先 `init()` 装载真实插件并 `release()`，随后在同一实例上
  调用公开的 `initExt()`；或对同一实例连续调用两次 `release()`
- 期望行为: `release()` 是幂等的：释放后把 `_parser_api`、`_remover` 置空（并释放 `_cfg`），
  再调用 `release()` 不重复删除；`initExt()` 不应继承上一个模块的 `_remover`
- 实际行为: `release()` 只 `_stopped=true` 并调用 `_parser_api->release()` /
  `_remover(_parser_api)`，**不置空** `_parser_api` 与 `_remover`，也不释放 `_cfg`。
  因此：二次 `release()` 会对同一指针再次调用 `deleteParser`（double free）；
  `release()` 后 `initExt()` 会把新 api 留给旧模块的 `_remover`，生命周期错配；
  析构函数为空，未显式 `release()` 的实例直接泄漏插件对象与配置引用
- 复现步骤:
  1. 用临时模块根软链 `libParserUDP.dylib`，`ParserAdapter a; a.init(...)`；
  2. `a.release()` 后再 `a.initExt("x", &fake, &stub, &bd)`；
  3. 若再调用一次 `a.release()`，`_remover`（UDP 的 `deleteParser`）会作用于 fake；
     或在 ASan/LSan 下观察 `init` 后未 release 的实例泄漏 `_parser_api`/`_cfg`。
- 严重级别: Minor（生命周期/资源泄漏；正常单次 init-release 流程不触发）
- 状态: 待审核
