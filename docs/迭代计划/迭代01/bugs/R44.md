## BUG-R44-001 StateMonitor::initialize 重入时不清空 _map，已删除的会话继续被状态机管理

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtDtCore/StateMonitor.cpp:107`（`_map[stateInfo->_session] = stateInfo`，函数内无 `_map.clear()`）
- 相关测试: `r44_state_monitor_lifecycle_test.cpp::ReinitializeKeepsRemovedSessionInStateTable`
- 输入/前置条件: 第一次 initialize 配置 `{"SSE": {...}}`；第二次 initialize 只配置 `{"SHFE": {...}}`（同一 StateMonitor 实例，会话模板表同时含 SSE/SHFE）
- 期望行为: 第二次装配后状态表只包含本次配置里的 SHFE；SSE 不再被 `run()` 的状态机处理（否则会对已从配置移除的会话执行 `transHisData`/状态切换）
- 实际行为: `isInState("SSE", SS_ORIGINAL)` 仍为 true，SSE 残留在 `_map` 中，`isAnyInState/isAllInState` 也会把它计入
- 复现步骤: 1) 加载含 SSE/SHFE 的 sessions.json；2) 用只含 SSE 的 state.json 调 initialize；3) 用只含 SHFE 的 state.json 再调 initialize；4) 查询 `isInState("SSE", SS_ORIGINAL)` -> true
- 影响范围: 配置热重载/多次 initialize 时旧会话继续落盘与收盘作业，可能把已下线的会话数据转入历史；单次启动场景不受影响
- 备注: 建议在 initialize 开头清空 `_map`（或提供显式 reload 语义）。当前用例锁定现状，修复后需同步改为断言 SSE 不存在。

## BUG-R44-002 StateMonitor::initialize 不校验 bdMgr，合法配置 + NULL 直接空指针解引用

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件: `src/WtDtCore/StateMonitor.cpp:38-66`（L40 存 `_bd_mgr`，L61 调 `_bd_mgr->getSession` 无判空）
- 相关测试: `r44_state_monitor_lifecycle_test.cpp::DISABLED_InitializeCrashesWithNullBdMgr`
- 输入/前置条件: state.json 存在且 JSON 合法（如 `{"SSE":{"inittime":900,...}}`），`bdMgr == nullptr`
- 期望行为: 返回 false 并记录错误（与「文件不存在/配置解析失败」一致的安全降级）
- 实际行为: 在 L61 解引用空 `_bd_mgr`，SIGSEGV
- 复现步骤: 构造 StateMonitor；写一份合法 state.json；调用 `initialize(cfg, nullptr, nullptr)`
- 影响范围: 上层装配顺序错误/基础数据加载失败但继续启动时，dt_srv 进程直接崩溃而非报错退出
- 备注: 建议在函数入口对 filename/bdMgr 判空。阻塞对应错误路径的覆盖率。

## BUG-R44-003 ParserAdapter::initExt 重复调用覆盖 _parser_api，旧实例既不 release 也不 delete

- 状态: 待审核
- 严重级别: Minor
- 模块/文件: `src/WtDtCore/ParserAdapter.cpp:46-52`（`_parser_api = api;` 直接覆盖，无前置释放/拒绝）
- 相关测试: `r44_parser_adapter_edges_test.cpp::SecondInitExtReplacesApiAndLeaksFirst`
- 输入/前置条件: 同一 ParserAdapter 先 `initExt("id", api1)`，再 `initExt("id", api2)`
- 期望行为: 拒绝第二次调用（与 `init` 的 `_cfg != NULL` 守卫一致），或先 `api1->release()+delete` 再替换
- 实际行为: `api1` 的 `release()` 调用次数为 0，指针被覆盖后永久泄漏；析构/release 只处理 api2
- 复现步骤: 用计数替身 API 连续 initExt 两次；断言 api1->_releaseCnt==0
- 影响范围: 解析模块重复装配（配置重载、异常重连路径）时泄漏 parser 实例及其内部线程/socket；不直接崩溃
- 备注: 建议与 `init` 一样加「已初始化」守卫，或替换前释放旧实例。

## BUG-R44-004 ParserAdapter::run 在 release 之后对已释放的 _parser_api 做虚调用（UAF）

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件: `src/WtDtCore/ParserAdapter.cpp:207-228`（release L210-218 delete 后不置空；run L223 只判 NULL）
- 相关测试: `r44_parser_adapter_edges_test.cpp::DISABLED_RunAfterReleaseUsesFreedApi`
- 输入/前置条件: `initExt` 成功（_parser_api 非空）-> `release()`（_parser_api 被 delete 但保留悬垂值）-> `run()`
- 期望行为: `run()` 识别 `_stopped` 或释放后的空状态，返回 false，不触碰已释放对象
- 实际行为: `_parser_api->connect()` 在已释放内存上做虚表分派 -> use-after-free（崩溃或执行任意旧虚函数）
- 复现步骤: 用替身 API 走 initExt；release；再 run
- 影响范围: 上层在 stop/release 后误调 run（或重复 stop/start）即 UAF；与 R18 已登记的「重复 release 双 delete」同源但路径不同
- 备注: 建议 release 末尾 `_parser_api=nullptr; _remover=nullptr;`，run 增加 `_stopped` 守卫。

## BUG-R44-005 IndexWorkerMgr::loadFactories 对「存在但不是目录」的路径抛出未捕获 filesystem_error

- 状态: 待审核
- 严重级别: Major
- 模块/文件: `src/WtDtCore/IndexWorkerMgr.cpp:35-46`（L37 只判 `StdFile::exists`，L46 用 `fs::directory_iterator`）
- 相关测试: `r44_idxworker_fresh_test.cpp::DISABLED_LoadFactoriesOnRegularFileThrows`
- 输入/前置条件: `path` 指向一个普通文件（配置里把工厂目录写成文件、或路径被同名文件占用）
- 期望行为: 与「目录不存在」一致，记录 error 并返回 false
- 实际行为: `fs::directory_iterator(file)` 构造抛 `std::filesystem::filesystem_error`，loadFactories 未捕获，异常穿透到调用方；若调用方未 catch 则进程 terminate
- 复现步骤: 建一个普通文件；`mgr.loadFactories(file.c_str())`
- 影响范围: 启动期配置路径错误由「返回 false」退化为异常/终止；工厂扫描无任何降级
- 备注: 建议用 `fs::is_directory` 判定或 `std::error_code` 重载。异常类输入只放在 DISABLED 用例。

## BUG-R44-007 IndexWorkerMgr 构造函数不初始化 _hot_mgr/_bd_mgr/_data_mgr，init 前调用即野指针

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件: `src/WtDtCore/IndexWorkerMgr.cpp:26-28`（空构造）；使用点 `:205-221`（`push_tick`/`sub_ticks`/`get_tick` 直接解引用 `_data_mgr`）
- 相关测试: `r44_idxworker_fresh_test.cpp::DISABLED_FreshPushTickCrashesOnUninitializedDataManager`
- 输入/前置条件: 构造 IndexWorkerMgr 后、未调用 `init` 就调用 `push_tick/sub_ticks/get_tick`
- 期望行为: 成员初始化为 nullptr 并做守卫（返回 false/NULL），或显式断言必须先 init
- 实际行为: 三个成员是未初始化的裸指针，`_data_mgr->writeTick/getCurTick` 对野指针解引用 -> UB/SIGSEGV；`get_hot_mgr/get_bd_mgr` 也会回传垃圾值
- 复现步骤: 构造 mgr；`mgr.push_tick(tick)`（或 `sub_ticks("SSE.600000")`）
- 影响范围: 装配顺序错误、工厂加载失败后仍调用上下文接口时崩溃；错误不可预测（取决于栈内容）
- 备注: 建议使用类内初始化 `= nullptr`。blocker 仅针对未初始化调用路径。

## BUG-R44-008 DataManager 接受 bdMgr==NULL，但 getSessionComms/getTradingDate 不做判空

- 状态: 待审核
- 严重级别: Blocker
- 模块/文件: `src/WtDtCore/DataManager.cpp:67-70`（init 无条件存 `_bd_mgr`）与 `:297-311`（两个委托直接解引用）
- 相关测试: `r44_datamgr_caster_edges_test.cpp::DISABLED_SessionCommsCrashesAfterInitWithoutBdMgr`
- 输入/前置条件: `init(params, nullptr, nullptr)`（q05 已把该组合当作「全天候模式」的正常输入），随后调用 `getSessionComms(sid)` 或 `getTradingDate(pid)`
- 期望行为: 返回 NULL / 0，与 `_writer==NULL` 的守卫风格一致
- 实际行为: L299 `_bd_mgr->getSessionComms` / L310 `_bd_mgr->getTradingDate` 空指针解引用，SIGSEGV
- 复现步骤: 用不存在的 module 让 init 返回 false（bdMgr 为 NULL）；调用 `getSessionComms("DAY0")`
- 影响范围: 以全天候模式（不配基础数据）启动后，任何走 IDataWriterSink 委托的代码路径都会崩；与 q05 记录的「null bdMgr 合法」语义自相矛盾
- 备注: 建议两个委托加 `_bd_mgr==NULL` 守卫，或在 init 拒绝 null bdMgr 并同步修改 q05 用例语义。

## 需要接缝/环境、留给主控裁定的面（非本 lane 新缺陷）

1. `StateMonitor::run()` 的整个状态机（L145-530）：无 `checkOnce(curDate, curMin)` 入口，只能起线程 + 墙钟；见 BUG-R5-002。
2. `UDPCaster` 的 `start/do_receive/do_broadcast` 与 `handle_send_*`：需真实 UDP socket/io 线程或 socket 工厂接缝；见 BUG-R5-001/003/004/008。
3. `ParserAdapter::init` 的插件成功段与 filter：需可注入的 `IParserApi` 工厂（当前 `init` 只认 DLL 里的 `createParser`）；`initExt` 可测但不走 filter/成功装配。
4. `IndexWorkerMgr` 的工厂成功段与 `poolsize>0`：需可注入 `IIndexWorkerFact` 注册表（`_factories` private 且无 setter）或允许加载真实指标 DLL。
5. `DataManager` 的写手成功段：需可注入 `IDataWriter`（`_writer` private，只能经 DLL 的 `createWriter` 获取）。
6. `ShmCaster` 的 `init(active=true)` 与写入体：需真实 mmap 共享内存；按任务令留白。
