## 观察 1：跨类型缓存守卫使委托/成交读取跳过装载（已有相关登记）

- 位置:
  - `src/WtDataStorage/WtDataReader.cpp:690`（`readOrdDtlSlice` 查 `_his_ordque_map`）、
    `:847`（`readTransSlice` 同）、`:741-743`、`:898-900`
  - `src/WtDataStorage/WtRdmDtReader.cpp:701`、`:876`、`:1050`（三个 ByRange 入口同型）、
    `:913-915`、`:1087-1089`
- 现象: 只要同一 `stdCode-endTDate` 的队列读取曾在 `_his_ordque_map` 留下 key
  （包括短文件/坏文件失败后留下的空块），委托/成交入口就跳过自己的文件装载，
  直接在空的自有 map 上返回 NULL。
- 与本 lane 的关系: 用例 1/2 只提供 8 字节坏队列文件，**没有**创建合法 DTL/TRANS
  目标文件。即使移除错误守卫，缺失目标数据也应返回 NULL；因此这两条 PASS 不能证明
  “目标文件存在却被跳过”。错误查错类型 map 的源码路径成立，但动态影响仍需目标文件
  对照测试。`WtDataReader` 侧与 BUG-R74-001 重复；`WtRdmDtReader` 侧对应
  `R1_wtdatastorage.md` §2 与 R185 观察 3。`BUG-R100-001` 是 AD reader 的日线/分钟线
  `endBarTime` 问题，不属于本条跨类型 cache key 缺陷，不应作为此处主编号。
- 修复方向: DTL/TRANS 分别查询自身 cache map；测试用例应先放入可成功解码的 DTL、TRANS
  文件，触发同 key 的队列缓存后读取，并断言各自记录可见，避免仅以缺失文件返回 NULL
  作为缺陷证据。
- 交叉引用: `bugs/R74.md` BUG-R74-001、`bugs/R1_wtdatastorage.md` §2、
  `bugs/R185.md` 观察 3、`bugs/R112.md`、`bugs/R162.md`。

## 观察 3：WtDataWriterAD `_async_task` 仍未初始化（既有 BUG-R162-001）

- 位置: `WtDataStorageAD/WtDataWriterAD.h:245`；`WtDataWriterAD.cpp:375`（消费点）、
  `:110-113`（release join）、`:368/376-414`（异步任务体）
- 复核: 构造函数与 `init` 均未赋值；基线 profile 中 `:368`、`:376-414` 仍为 0。
  因执行模式未初始化，不能把现有数据描述成“同步路径”已运行 143 次；`:368` 的
  `curTick->release()` 计数为 0 可能涉及行表/内联归因，现有用例不能确定其执行线程或

  `_async_task` 未初始化，因此该 PASS 不能证明执行模式是同步，也不能排除读取未初始化
  bool 的未定义行为；用例不覆盖线程 join。
