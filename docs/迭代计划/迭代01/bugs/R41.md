## BUG-R41-001 `WtEngine::load_fees` 未写 `_fee_map`，直接 `calc_fee` 恒返回 0

- 状态: 已合并（BUG-R130-001，同一 `WtEngine::load_fees` 未填 `_fee_map` 缺陷；子类另填 map 的情况不在此主张内）
- 严重级别: Minor（公开 API 结果错误；当前仓内没有活动生产调用点）
- 模块/文件: WtCore / `src/WtCore/WtEngine.cpp:843-877, 879-916`（`load_fees` / `calc_fee`）
- 相关测试: `r41_engine_base_test.cpp` 的
  `R41CalcFeeFallsBackToZeroBecauseFeeMapIsNeverFilled`
- 输入:
  - fees 模板 JSON：`{"SHFE.rb":{"open":2.0,"close":2.0,"closetoday":3.0,"byvolume":true,"margin":0.12}}`
  - `cfg.fees` 指向该文件，`cfg.product.session="TRADING"`
  - 调用 `engine.calc_fee("SHFE.rb2310", 3500.0, 5, 0)`
- 期望: 按成交量模式返回 `2.0 * 5 = 10.0`（与 `WTSCommodityInfo::calcFee` 同一口径）。
- 实际: 返回 `0.0`。`load_fees` 只把费率写到 `WTSCommodityInfo`（第 870-871 行），
  `_fee_map` 在整个 `src/WtCore` 中只有读（883/884 行）和日志（876 行），没有任何
  `insert/emplace/operator[]` 写入点，因此 `calc_fee` 永远走“Fee template not found”
  分支并返回 0。
- 复现步骤:
  1. 用上面的 fees 文件初始化任意 `WtCtaEngine`；
  2. `_bd->commodity()->calcFee(3500,5,0)` 得到 10.0（证明模板确实加载）；
  3. `engine.calc_fee("SHFE.rb2310",3500,5,0)` 得到 0.0。
- 影响: 直接调用公开 `WtEngine::calc_fee` 且仅通过 `load_fees` 配置的消费者会得到 0。
  `CtaStraBaseCtx.cpp:1465,1512` 的同名调用已注释，当前未找到 WtCore 活动生产调用点，
  因此不能据此断言仓内实盘/回测已产生手续费偏差。`load_fees` 日志的 map size 也与实际
  已写入的 commodity 费率不符。
- 复核结论: 与 BUG-R130-001 是同一源码路径、根因和公开 API 影响，故合并，不重复计数。
  `_fee_map` 在 `src/WtCore` 没有写入点是源码证据；R41 活动测试
  原测试把当前 `0.0` 写成预期；现已改为 `R41CalcFeeUsesLoadedTemplateAndDefaultsWithoutOne`，商品计算为 10、引擎仍为 0，重建后单例 FAIL；无模板返回 0 的控制通过。未验证外部消费者。
  修复方向见 BUG-R130-001：解析每个有效商品后填充 `_fee_map[fullPid]`，并保留 `load_fees` 到 `calc_fee` 的正向契约测试。

## BUG-R41-002 `sub_tick` 无规则标签分支的复权标记取错下标，前复权被当成后复权

- 状态: 待审核（源码路径确认；关联复现用例禁用，本次未运行）
- 严重级别: 中（前复权行情分发错误）
- 模块/文件: WtCore / `src/WtCore/WtEngine.cpp:825-837`（`WtEngine::sub_tick` 的 else 分支）
- 相关测试: `r41_cta_engine_test.cpp` 的
  `DISABLED_R41PlainQfqSubscriptionDispatchesFrontAdjusted`
- 输入: 普通标准代码（无 `@`/自定义规则标签）带前复权后缀：
  `engine.sub_tick(ctxId, "SHFE.rb2310-")`，随后
  `engine.on_tick("SHFE.rb2310", tick)`。
- 期望: 对此输入，订阅标记应为 `flag=1`（前复权），策略上下文回调代码为 `"SHFE.rb2310-"`。价格缓存/复权乘因子不由该测试断言。
- 实际: 第 828-834 行先把 `length` 自减，再判断 `stdCode[length - 1]`，读到的是后缀
  前一位数字（'0'），因此对该输入 `flag==2`；上下文收到的是后复权代码 `"SHFE.rb2310+"`。
  对比 791-795 行的有规则标签分支使用的是 `stdCode[length]`（正确）。
- 复现步骤（用例已定义，未运行）:
  1. 初始化 CTA 引擎并 `on_session_begin()`；
  2. 给同一上下文 `sub_tick(id, "SHFE.rb2310-")`；
  3. 喂一笔 `SHFE.rb2310` 的 tick；
  4. 检查策略回调代码应为 `SHFE.rb2310-`；当前源码分支会生成 `SHFE.rb2310+`。
- 影响: 使用“无自定义规则标签 + 前复权订阅”的策略会按后复权分支收到代码；后续价格变换影响由 `WtCtaEngine::on_tick` 的 flag 分支源码可见，但 R41 禁用用例只验证回调代码，本次未验证价格数据或乘因子。
- 证据边界: `DISABLED_R41PlainQfqSubscriptionDispatchesFrontAdjusted` 默认禁用，只断言回调代码；本次未运行。修复方向：确认末尾字符为 `-`/`+` 后读取后缀位置 `length`，并增加可运行的无规则标签前/后复权分发断言。

## BUG-R41-003 `EventNotifier::notify(WTSOrderInfo*)` retain 后从不 release，逐单泄漏

- 状态: 待审核（异步任务中 retain/release 不平衡由源码确认；未动态验证）
- 严重级别: 低（长时间运行的内存泄漏）
- 模块/文件: WtCore / `src/WtCore/EventNotifier.cpp:214-230`
- 相关测试: `r41_event_notifier_test.cpp` 的
  `ActiveNotifierPublishesAllJsonPayloads`（需要构建目录存在 `libWtMsgQue`）
- 输入: `notifier.init(active=true)` 成功后调用
  `notifier.notify("R41_TRADER", 12, "SHFE.rb2310", ordInfo)`。
- 期望: post 的 lambda 在 `orderToJson`/`publish` 结束后调用 `ordInfo->release()`，
  与成交单重载（第 205-211 行，lambda 末尾 `trdInfo->release()`）保持一致。
- 实际: 第 221 行 `ordInfo->retain()` 后，lambda（第 222-227 行）只做序列化和发布，
  没有 `release()`；每次委托通知都会让 `WTSOrderInfo` 引用计数 +1。
- 复现步骤:
  1. 构造 active 的 `EventNotifier` 并成功加载 WtMsgQue；
  2. 反复调用 `notify(trader, localid, code, ordInfo)`；
  3. 传入对象引用计数只增不减（可用 `WTSObject` 引用计数或 Instruments 观察）。
- 影响: 每次已投递的委托通知增加一个引用；调用方按常规释放自己的引用后，lambda 缺失的 release 会留下额外引用，阻止对象归零。高频下的累计内存曲线尚未测量。

- 证据边界: 成交重载有 `retain()`/lambda 末尾 `release()`（:202-211），委托重载只有
  `retain()`（:221）且 lambda 无对应释放（:222-227）；对已排队并执行的委托任务，这是源码级
  引用所有权不平衡。现有关联测试可能因缺 `libWtMsgQue` 而 `GTEST_SKIP`，即使执行也只检查
  JSON 发布，不检查引用归零或对象析构。本次未运行它，不能报告为运行时复现。
  修复方向：用作用域清理确保每个已 retain 的对象在异步任务结束时恰好 release 一次，覆盖
  序列化/发布失败路径；补生命周期计数器测试，不依赖长期内存曲线作为唯一判据。
