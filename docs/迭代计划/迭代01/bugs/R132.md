## BUG-R132-001

- 状态: 待审核
- 严重级别: Major（源码存在条件性悬垂写/未定义行为；本轮没有动态复现，触发频度未测）
- 模块/文件: `src/WtDataStorage/WtDataReader.cpp`
  - `readOrdQueSlice` 历史 CMP_V2 解压后重建缓冲区：L565-581
  - `readOrdDtlSlice` 同型：L722-738
  - `readTransSlice` 同型：L879-895
- 测试用例: `src/TestUnits/coverage/q03_storage3/r132_reader_his_test.cpp`
  - `DISABLED_R132ReaderHisCompressibleQueueDanglingWrite`（默认不跑，
    `--gtest_also_run_disabled_tests` 可复现）
  - 启用对照：`R132ReaderHisHftCompressedRoundTrip`（用不可压缩随机载荷，避免触发重分配）
- 输入/前置条件:
  - 历史队列文件 `his/queue/SSE/20240109/600040.dsb` 为 CMP_V2，
    测试夹具载荷为两条规则化 `WTSOrdQueStruct`（`q03::make_ordque`）；夹具意图构造高压缩率
    输入，但实际压缩长度和目标 std::string capacity 未记录。
  - 只有当 `sizeof(HisOrdQueBlock) + 解压长度` 超过 `_buffer` 当前 capacity 时，后续旧指针
    写才会变成悬垂写；当前材料尚未测定该条件是否由该样本满足。
- 复现步骤（需补 capacity/ASan 观测以确认触发条件）:
  1. 按上述路径写入 CMP_V2 队列文件；
  2. 调用 `WtDataReader::readOrdQueSlice("SSE.STK.600040", 2, 20240109150000000)`；
  3. 运行 `--gtest_also_run_disabled_tests --gtest_filter=*CompressibleQueueDanglingWrite*`。
- 期望行为: 返回 2 条切片，进程不崩溃。
- 源码行为与证据边界:
  - `tBlockV2` 在修改 `_buffer` 前指向其内部存储。`resize` 缩短字符串后，L578 的
    `append(buf)` 若使最终长度超过当前 capacity，会重新分配并使 `tBlockV2` 失效；
    随后的 L579 仍经旧指针写 `_version`，构成条件性未定义行为。是否扩容取决于压缩
    输入、解压长度和当前标准库 capacity，原记录中的“500+ 字节 / capacity 小于 500”
    没有运行时采样支撑，不作已测事实。
  - `DISABLED_R132ReaderHisCompressibleQueueDanglingWrite` 默认不运行；R132 manifest 未
    记录测试二进制执行，故目前只有源码路径与夹具意图，没有该用例的动态复现/ASan 证据。
  - 原记录称 `R74ReaderResidualTest.R74ReaderHftHisPathsUseSinkClock` 崩溃，但当前仓库留存的
    `build-cov/coverage/rc/CoverageTests/R74ReaderResidualTest_R74ReaderHftHisPathsUseSinkClock.rc`
    和对应日志均为 PASS。该用例使用 CMP_V2 数据并走相同类路径，但普通通过不能排除未定义
    行为，也不能作为悬垂写崩溃的证据；应删除原 `CRASH(rc=139,sig=11)` 说法。
- 影响范围: 三种逐笔历史 CMP_V2 解压分支都采用相同的“先缩短、再 append、再写旧指针”
  顺序；当 append 扩容时发生悬垂写。崩溃或数据损坏是可能后果，未由当前记录中的动态证据
  证明，也未测生产文件触发率。
- 修复方向（仅供参考，本迭代不改）: 在改动 `_buffer` 前把需要的头字段复制到局部值；
  调整到最终大小后将解压载荷复制到新缓冲区，再从新缓冲区取头指针写 `_version`。
  不要在任何 `resize/append` 后继续使用旧的 `tBlockV2` 指针。

## BUG-R132-002

- 状态: 待审核
- 严重级别: 中（同键读取顺序会使明细/成交接口返回 NULL；下游影响及动态触发未验证）
- 模块/文件: `src/WtDataStorage/WtDataReader.cpp`
  - `readOrdDtlSlice` 缓存命中判断：L690-691（`_his_ordque_map.find(key)`）
  - `readTransSlice` 缓存命中判断：L847-848（同样用了 `_his_ordque_map`）
  - 受影响返回点：L743 / L899（`tBlkPair._block == NULL` 直接返回 NULL）
- 测试用例: `src/TestUnits/coverage/q03_storage3/r132_reader_his_test.cpp`
  - `DISABLED_R132ReaderHisQueueCachePoisonsDetail`（默认不跑）
  - 启用对照 `R132ReaderHisHftCompressedRoundTrip` 对队列、明细、成交使用不同 stdCode，
    主动避开该同键情形，不能证明同键序列正常。
- 输入/前置条件:
  - 同一 stdCode + 交易日（`SSE.STK.600041` + 20240109）同时存在队列文件与明细文件，
    两者都是合法 CMP_V2、各 2 条记录；
  - 先调用 `readOrdQueSlice` 让 `_his_ordque_map[key]` 建立缓存项（key 为
    `"stdCode-endTDate"`）。
- 复现步骤:
  1. 写入 `his/queue/SSE/20240109/600041.dsb` 与 `his/orders/SSE/20240109/600041.dsb`；
  2. `readOrdQueSlice("SSE.STK.600041", 2, 20240109150000000)`；
  3. `readOrdDtlSlice("SSE.STK.600041", 2, 20240109150000000)`；
  4. 运行 `--gtest_also_run_disabled_tests --gtest_filter=*QueueCachePoisonsDetail*`。
- 期望行为: 明细读取返回文件中的 2 条记录。
- 源码行为与证据边界:
  - L690/L847 检查 `_his_ordque_map`；若同一 `stdCode-endTDate` 的队列项已存在，就跳过
    明细/成交文件加载。之后分别从 `_his_orddtl_map[key]` / `_his_trans_map[key]` 取块；
    若未另行装载，该项是默认空项并在 `_block == NULL` 处返回 `NULL`。
  - `DISABLED_R132ReaderHisQueueCachePoisonsDetail` 定义了同键复现输入，但默认不运行；
    启用对照刻意使用不同 stdCode。当前结论来自源码控制流，未有该同键用例的动态运行证据。
- 影响范围: 同一合约同一交易日先读队列、再读明细/成交时，后者可能返回 `NULL`，且调用方
  无法仅凭该返回值区分“文件不存在”与“被错误 map 命中”。是否因此静默丢数取决于调用方
  如何处理 `NULL`，不把静默丢失作为已观察结果。
- 备注: `readOrdQueSlice` 自己用的是 `_his_ordque_map`（正确），明细/成交应为
  `_his_orddtl_map` / `_his_trans_map`，判断与后文取缓存的 map 保持一致即可。
  本波启用的用例通过“队列/明细/成交各用不同 stdCode”避开该缺陷，不把错误行为固化成断言。
- 修复方向（仅供参考，本迭代不改）: 明细与成交分支分别用自己的缓存 map 判断命中；补一个
  同 `stdCode-endTDate` 先读队列、再读明细/成交并检查记录数量的启用用例。
