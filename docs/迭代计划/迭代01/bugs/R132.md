## BUG-R132-001

- 状态: 待审核
- 严重级别: Major（堆悬垂写，UB；实测旁证为崩溃）
- 模块/文件: `src/WtDataStorage/WtDataReader.cpp`
  - `readOrdQueSlice` 历史 CMP_V2 解压后重建缓冲区：L565-581
  - `readOrdDtlSlice` 同型：L722-738
  - `readTransSlice` 同型：L879-895
- 测试用例: `src/TestUnits/coverage/q03_storage3/r132_reader_his_test.cpp`
  - `DISABLED_R132ReaderHisCompressibleQueueDanglingWrite`（默认不跑，
    `--gtest_also_run_disabled_tests` 可复现）
  - 启用对照：`R132ReaderHisHftCompressedRoundTrip`（用不可压缩随机载荷，避免触发重分配）
- 输入/前置条件:
  - 历史队列文件 `his/queue/SSE/20240109/600040.dsb` 为 CMP_V2，
    载荷是两条高度可压缩的 `WTSOrdQueStruct`（q03::make_ordque 的规则化字段）；
  - 文件大小 = `sizeof(HisOrdQueBlockV2)` + 压缩长度，压缩后长度明显小于解压后的
    两条记录（约 500+ 字节）。
- 复现步骤:
  1. 按上述路径写入 CMP_V2 队列文件；
  2. 调用 `WtDataReader::readOrdQueSlice("SSE.STK.600040", 2, 20240109150000000)`；
  3. 运行 `--gtest_also_run_disabled_tests --gtest_filter=*CompressibleQueueDanglingWrite*`。
- 期望行为: 返回 2 条切片，进程不崩溃。
- 实际行为:
  - L574 `buf = uncompress_data(...)` 得到约 500+ 字节；
  - L577 `hisBlkPair._buffer.resize(sizeof(HisOrdQueBlock))` 把大小缩到 12，
    但 `std::string` 仍保留原来的小 capacity（约 20+压缩长度，可能 < 500）；
  - L578 `append(buf)` 需要扩容，`_buffer` 重新分配，`tBlockV2` 变成悬垂指针；
  - L579 `tBlockV2->_version = BLOCK_VERSION_RAW_V2;` 向已释放的旧缓冲区写入；
  - L581 之后才用新的 `_buffer.c_str()` 建立 `_block`。悬垂写属于未定义行为，
    堆状态被破坏后可能在后续 `delete/release` 时段错误。
  - 旁证：`R74ReaderResidualTest.R74ReaderHftHisPathsUseSinkClock` 走同一路径，
    在 `build-cov/coverage/rc/CoverageTests/` 中记录为 `CRASH(rc=139,sig=11)`，
    且该用例覆盖的队列成功路径（L574-611）在 10:24 报告中仍为 0 命中。
- 影响范围: 任意历史逐笔队列/明细/成交 CMP_V2 文件，只要压缩后长度小于解压后记录长度
  （行情数据高度重复时很常见），读取即可能破坏堆；表现为随机崩溃或静默数据错乱。
- 修复方向（仅供参考，本迭代不改）: 先 `resize` 到目标总长度，再 `memcpy` 解压数据到
  `&_buffer[sizeof(HisXxxBlock)]`；或在 `append` 之后重新取 `tBlockV2`/头部指针再写
  `_version`。

## BUG-R132-002

- 状态: 待审核
- 严重级别: Major（静默丢数据，非崩溃）
- 模块/文件: `src/WtDataStorage/WtDataReader.cpp`
  - `readOrdDtlSlice` 缓存命中判断：L690-691（`_his_ordque_map.find(key)`）
  - `readTransSlice` 缓存命中判断：L847-848（同样用了 `_his_ordque_map`）
  - 受影响返回点：L743 / L899（`tBlkPair._block == NULL` 直接返回 NULL）
- 测试用例: `src/TestUnits/coverage/q03_storage3/r132_reader_his_test.cpp`
  - `DISABLED_R132ReaderHisQueueCachePoisonsDetail`（默认不跑）
- 输入/前置条件:
  - 同一 stdCode + 交易日（`SSE.STK.600041` + 20240109）同时存在队列文件与明细文件，
    两者都是合法 CMP_V2、各 2 条记录；
  - 先调用 `readOrdQueSlice` 让 `_his_ordque_map[key]` 建立缓存项（key 为
    `"stdCode-endTDate"`）。
- 复现步骤:
  1. 写入 `his/queue/SSE/20240109/600041.dsb` 与 `his/orders/SSE/20240109/600041.dsb`；
  2. `readOrdQueSlice("SSE.STK.600041", 2, 20240109150000000)`；
  3. `readOrdDtlSlice("SSE.STK.600041", 2, 20240109150000000)`；
  4. 运行 `--gtest_also_run_disabled_tests --gtest_filter=*QueueCachePoisonsDetail*`。
- 期望行为: 明细读取返回文件中的 2 条记录。
- 实际行为:
  - L690 查的是 `_his_ordque_map`，第 2 步已把同一 key 放进去，于是 L691 判定“已缓存”，
    整段文件加载被跳过；
  - 紧接着 L741 取 `_his_orddtl_map[key]`，这是默认构造的空项，`_block == NULL`，
    L743 直接 `return NULL`；
  - 明细文件完全没有被读过，调用方拿到 NULL，无法区分“文件不存在”和“缓存键撞车”。
  - 成交路径 L847/L899 同型：只要同键先读过队列，成交流也会被同样短路。
- 影响范围: 同一合约同一交易日先读队列、再读明细/成交的调用序列会静默丢失逐笔数据；
  实盘/回测中只要策略同时订阅 L2 队列与逐笔委托/成交就可能触发。
- 备注: `readOrdQueSlice` 自己用的是 `_his_ordque_map`（正确），明细/成交应为
  `_his_orddtl_map` / `_his_trans_map`，判断与后文取缓存的 map 保持一致即可。
  本波启用的用例通过“队列/明细/成交各用不同 stdCode”避开该缺陷，不把错误行为固化成断言。
