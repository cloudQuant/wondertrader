## BUG-R143-001 订单通知异步任务缺少配对 release

- 编号: BUG-R143-001
- 模块/文件: `src/WtUftCore/EventNotifier.cpp:214-227`
  （`ordInfo->retain()` 在 L221；lambda 内 L226 发布后没有对应 `release()`）
- 相关测试: `R143UftNotifier.postsOrderJsonWithStateAndVolumeFields`
  （`src/TestUnits/coverage/q04_uftcore3/r143_uftcore_notifier_test.cpp`）。源码可确认 retain 后任务体没有
  release；该用例只立即断言 retainCount 为 2，随后固定等待 50ms 并在清理时释放当前计数，未对任务完成后的
  retainCount 作断言，因此没有独立动态证明“worker 执行后仍为 2”。
- 输入/前置条件: `EventNotifier` 以 `inproc://` 成功 init；传入一个 `WTSOrderInfo*`
  （创建时 retainCount=1）调用 `notify(trader, localid, stdCode, ordInfo)`
- 期望行为: 与成交通知 `notify(..., WTSTradeInfo*)` 对称（L204 retain、L210 release）：
  worker 执行 `orderToJson` 并发布后释放该引用，调用方持有的对象最终可回收
- 实际行为（源码核对）: L221 `ordInfo->retain()` 后，lambda 调用 `orderToJson` 和可选的
  `_publisher`，任务体退出前没有 `ordInfo->release()`。若任务已执行完，额外引用仍留在对象上；
  每个被处理的订单通知都会多留一个引用，累计内存影响取决于订单流量与对象回收路径，尚未量化。
- 复现步骤:
  1. 准备可加载的 `libWtMsgQue.dylib`，`WTSVariant` 设 `active=true`、
     `url=inproc://...`，`EventNotifier::init` 返回 true；
  2. `WTSOrderInfo* ord = WTSOrderInfo::create();` 此时 `retainCount()==1`；
  3. `notifier.notify("uft1", 1, "SHFE.ag2406", ord);`；
  4. 用例当前只观察到同步 retain 后计数为 2；等待 50ms 与 notifier 析构 join 不是任务完成屏障，且没有
     在任务完成后断言计数。隔离复核应加入确定性的任务完成观测，再确认计数是否回到 1；
  5. 当前用例按观察到的当前计数释放对象，仅用于避免测试结束后残留对象，不构成修复或动态断言
- 严重级别: Major（源码可确认每个已执行订单任务保留额外引用；高频累计影响未测量）
- 状态: 待审核

## BUG-R143-002 MQ 服务创建失败无法经当前接口可靠反馈

- 编号: BUG-R143-002
- 模块/文件: `src/WtUftCore/EventNotifier.h:18`（一参 `FuncCreateMQServer`）、
  `src/WtUftCore/EventNotifier.cpp:32-35`（`on_mq_log` 空实现）、`:94-111`（调用 creator 后
  不检查错误并返回 true）；插件接口 `src/WtMsgQue/WtMsgQue.h:32` / `WtMsgQue.cpp:32` 为
  `create_server(const char*, bool)`，`src/WtMsgQue/MQManager.cpp:6-17` 忽略 `MQServer::init`
  的返回值并始终返回新分配的 server id。
- 相关测试: 静态核对 + `R143UftNotifier.*`（init 成功分支的正常对照）；
  无直接失败断言可写——`_mq_sid` 是 private，失败时五个 notify 入口都静默返回
- 输入/前置条件: `active=true`，`WtMsgQue` 模块可加载，但 `nn_socket/nn_setsockopt/nn_bind`
  失败。当前插件的 `create_server` 并不会把此失败转换为 0：`MQServer::init` 返回 false 后，
  `MQManager::create_server` 仍登记对象并返回其非零 id。
- 接口契约问题: `EventNotifier` 将导出函数声明成一参函数指针，却按该类型调用；插件实际导出
  `create_server(const char*, bool)`。通过不兼容函数指针调用且未提供 `confirm` 参数属于未定义行为，
  而且当前 typedef 的 `unsigned long` 返回类型与插件 `WtUInt32`（`unsigned int`）也不一致；
  因此不兼容不只在参数个数，当前二进制接口未统一前，不应对 `confirm` 或运行时精确结果作确定性断言。
- 期望行为: 统一 `EventNotifier` 与 `WtMsgQue` 的函数签名；插件把 socket/bind 初始化失败传回
  可判定状态，`EventNotifier::init` 应返回 false 或明确进入不可用状态；错误回调应可见。
- 实际行为（静态核对）: 当前实现即使 server 初始化失败也会收到非零 id，继续打印 initialized、
  建 worker 并返回 true。通知入口因 id 非零会继续调用 publisher；未初始化的 `MQServer::publish`
  会记录“not initialized”并丢弃数据，但该日志仍经过 `on_mq_log` 空回调而不可见。现有成功初始化
  测试没有失败绑定断言，未动态验证该失败场景。
- 复现步骤: 现有 `R143UftNotifier.*` 只验证正常初始化；要动态复核失败路径，需在已统一 ABI 的前提下，
  用无效/占用地址并断言 init 返回值、可用状态、publisher 结果和日志回调。当前一参/两参不匹配使旧
  二进制下的失败测试结果不能作为稳定接口证据。
- 严重级别: 中（绑定失败时通知服务可能被报告为已初始化并静默丢弃；动态失败路径尚未验证）
- 状态: 待审核
