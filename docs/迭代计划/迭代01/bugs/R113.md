## BUG-R113-001 TraderMocker 的 connect/login 非幂等，第二次调用对 joinable std::thread 做 reset 触发 std::terminate

- 编号: BUG-R113-001
- 迭代02第二轮前状态（历史）: - 状态: 待审核
- 状态: 已撤回（迭代02：TEST，原产品主张不成立）
- 审查结论: 产品缺陷（静态源码确认；本轮未动态复现）
- 模块/文件/行: `src/TraderMocker/TraderMocker.cpp:689-703`（`connect`，`_thrd_worker.reset(new StdThread(...))` 在 `693`）、
  `:723-743`（`login`，`_thrd_match.reset(new StdThread(...))` 在 `725`）、
  `:640-657`（`release` 在 `_terminated` 为 true 时早退）
- 相关测试: `src/TestUnits/coverage/t_TraderMocker/r113_mocker_login_retry_test.cpp`
  `R113MockerLoginRetry.DISABLED_SecondLoginOrConnectTerminates`（崩溃类，保留 DISABLED；本轮未运行）。
  测试先重复 `login()` 再重复 `connect()`；如果前一个路径按源码预期 abort，后一个调用不可达，
  因此它只描述了两种意图，没有分别证明两种触发。
- 输入/前置条件:
  1. `TraderMocker api; WTSVariant* cfg = ...; api.init(cfg); api.registerSpi(&sink);`
  2. `api.connect(); api.login("", "", "");`（首次成功，`_thrd_worker`/`_thrd_match` 均 joinable）
  3. 在首次 `login()` 后单独再次 `login()`，或在首次 `connect()` 后单独再次 `connect()`。
- 期望行为: 重复 connect/login 要么幂等返回，要么按明确定义的状态机安全拒绝；不得因析构仍
  joinable 的 `std::thread` 而终止进程。
- 实际行为: `StdThreadPtr` 是 `std::shared_ptr<std::thread>`（`src/Share/StdUtils.hpp:23-24`）。
  `login()` 每次都在 `:725` 覆盖 `_thrd_match`；`connect()` 每次都在 `:693` 覆盖
  `_thrd_worker`。旧 `std::thread` 只要尚未 join/detach，销毁其最后一个 shared_ptr 就会
  触发 `std::terminate()`；线程函数是否已结束不改变 `std::thread::joinable()` 状态。
  `release()` 后再 login 的情形另受 `_terminated` 和 worker 清理语义影响，当前 DISABLED 用例
  没有覆盖，不能并入上述两种调用的动态证据。
- 复现步骤: 上述分别调用会触发 joinable `std::thread` 析构是静态推导；本轮没有运行崩溃用例。
  若恢复动态测试，应把 repeat-login 与 repeat-connect 拆为独立用例，避免第一个 abort 遮蔽第二个路径。
- 影响范围: 使用 `TraderMocker` 的宿主若在未完成清理时重试登录或连接，可能直接终止进程。
  正式宿主是否会对同一实例重复调用、以及具体错误呈现方式，本轮未验证。
- 严重级别: Major（在重复调用前置条件下进程 abort；触发频率待验证）
- 备注: 修复方向：明确定义连接/登录状态机。重复调用应安全拒绝或作为幂等操作返回；若支持
  重新启动，先取消 socket/停止相应事件循环与撮合循环，再 join 并重建线程/`io_context`。
  不要对持续运行的 `_thrd_match` 直接 `join()`，也不要只 `detach()` 规避 terminate。
  与 BUG-R60-001（disconnect 后 release 跳过 worker 清理）属不同触发路径的线程生命周期问题，
  不是同一条代码路径。

## BUG-R113-002 `TraderMocker::splitVolume` 重置 C 全局 PRNG；仿真可重放契约待确认

- 编号: BUG-R113-002
- 状态: 待审核
- 审查结论: 代码行为静态确认；产品缺陷性质待产品契约确认（本轮未运行测试）
- 严重级别: 待定（若仿真要求可重放则为低严重度缺陷；否则按隔离全局状态的设计改进评估）
- 模块/文件/行: `src/TraderMocker/TraderMocker.cpp:52-80`（`splitVolume`，`srand((uint32_t)time(NULL));` 在 `63`）
- 相关测试:
  - `src/TestUnits/coverage/t_TraderMocker/r113_mocker_match_long_test.cpp`
  - `src/TestUnits/coverage/t_TraderMocker/r113_mocker_match_short_test.cpp`
  - `src/TestUnits/coverage/t_TraderMocker/r113_mocker_partial_cancel_test.cpp`
  （只断言总成交量/持仓/状态，不依赖具体拆量序列）
- 输入/前置条件: 任意一次成交量 > `minQty` 的撮合（本 lane 的开多 5 手、开空 4 手）
- 期望行为: 若产品要求可重放仿真，应由接口/配置提供稳定 seed，并隔离各实例的随机状态；
  目前没有找到此要求的接口说明或测试契约，故此期望仍待确认。
- 实际行为: `splitVolume` 是全局函数，每次 `vol > minQty` 都以秒级 `time(NULL)` 重置 C
  全局 `rand()` 状态。源码能证明该进程级状态被改写；同一秒、同一参数且无并发/外部随机调用
  干扰时，调用从相同 seed 开始并产生相同随机数前缀。不能仅据此断言多线程调用存在数据竞争：
  `rand()` 的实现同步语义依赖运行库；全局状态和调用序列相互影响仍然成立。
  “仿真报告无法复现”属于契约影响，现有证据未证明产品承诺固定 seed 或逐笔成交序列稳定。
- 复现步骤: 同秒同输入的重复 seed 结论是对 `srand(time(NULL))` 与 `rand()` 的静态推导，
  本轮没有运行撮合或观测成交拆分。现有 R113 撮合用例只验证总成交量、订单状态和持仓，
  不断言每笔拆量或进程后续 `rand()` 序列，因此不能证明或反驳确定性契约。
- 影响范围: 进程内其他使用 C `rand()` 的组件会共享被 `srand()` 重置的状态；多个调用之间
  的随机序列受同秒 seed 和交错调用影响。对仿真可复现性的业务影响取决于产品要求，待确认。
- 备注: 修复方向：若需可重放，优先采用显式 seed 的 per-instance RNG 并通过测试固定成交拆分；
  若只需随机拆单，也建议使用独立 RNG，避免改写宿主全局 PRNG。先确认是否将该功能纳入产品
  确定性契约再按 bug 定级。`curVol==0` 的无限循环仅在 helper 被传入 `minQty==0` 时可能触发；
  `TraderMocker::init` 会把配置的 0 归一为 1（`:531-535`），常规撮合输入不触达该条件，
  不把它作为本条已确认缺陷。
