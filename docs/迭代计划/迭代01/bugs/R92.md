## BUG-R92-001 HftMocker / UftMocker 的挂单 entrust 任务在订单成交并 erase 后解引用空指针

- 编号: BUG-R92-001
- 状态: 待审核
- 严重级别: **Critical**（进程 SIGSEGV；回测进程内会连带吞掉同可执行体后续用例的覆盖率计数）
- 模块/文件/行:
  - `src/WtBtCore/HftMocker.cpp:628-631`（`stra_buy` 的 `postTask` lambda）
  - `src/WtBtCore/HftMocker.cpp:831-834`（`stra_sell` 的 `postTask` lambda）
  - `src/WtBtCore/HftMocker.cpp:391-422`（`on_tick` 的非 `match_this_tick` 分支：
    先 `procOrder` 成交并 `_orders.erase(localid)`，再 `procTask()` 排空队列）
  - `src/WtBtCore/UftMocker.cpp:629-633`、`670-674`、`731-735`、`792-796`
    （`stra_enter_long/stra_enter_short/stra_exit_long/stra_exit_short` 的 `postTask` lambda）
  - `src/WtBtCore/UftMocker.cpp:265-286`（同样的「先撮合 erase，再 procTask」顺序）
- 相关测试:
  - 既有 `src/TestUnits/coverage/p03_btcore_mockers2/r72_hft_uft_paths_test.cpp`
    - `R72HftUftPaths.HftMarketOrderFillsAndDumps`（最新覆盖运行 **CRASH**，见下）
    - `R72HftUftPaths.UftMarketOrderFillsAndCloses`（最新覆盖运行 **CRASH**，见下）
  - 本 lane 的启用用例通过「`match_this_tick=true`」或「Loader 对手量=1 的部分成交」
    绕开该缺陷（`R92MockerResidual.UftMatchTickFillSellAndCover` /
    `HftPartialFillEraseAndQueries` / `HftMatchTickErrorsZeroPriceAndT1`）；
    没有新增会主动崩溃的用例。
- 输入/前置条件（最小复现，公开 API）:
  1. `HisDataReplayer` 用 `IBtDataLoader` 准备一笔 tick：`askqty>0`，价格可成交；
  2. `HftMocker hft(&rp, "x"); rp.register_sink(&hft, "x"); rp.prepare();`
  3. `hft.stra_buy(code, 0.0, 2.0, "tag");`（市价单会一次性全部成交）
  4. `hft.handle_tick(code, tick, 0);`（默认 `_match_this_tick=false`）
  UftMocker 把第 3 步换成 `stra_enter_long(code, 0.0, 2.0)` 即可。
- 期望行为: 订单在 `on_tick` 内被全部成交并 erase 后，队列里的 entrust 任务仍应安全执行
  （要么检查订单是否还在册，要么在 erase 前先排空任务）。
- 实际行为:
  - `stra_buy` 投递的 lambda 是
    `const OrderInfoPtr& ordInfo = _orders[localid]; on_entrust(...)`；
  - 非 `match_this_tick` 的 `on_tick` 先遍历 `procOrder`，全部成交时返回 true 并把
    `localid` 从 `_orders` 中 `erase`；
  - 随后才调用 `procTask()`；lambda 里的 `_orders[localid]` 在订单已删除时是
    `std::map::operator[]`，会插入一个**默认构造的空 `shared_ptr`**，紧接着
    `ordInfo->_code` / `ordInfo->_usercode` 解引用空指针 → SIGSEGV。
  - `match_this_tick=true` 时顺序反过来（先 `procTask` 再 `procOrder`），所以不崩；
    这也是为什么既有 p08 订单装配用例（不成交）和 R62 生命周期用例（直接 `on_trade`）
    没有暴露该缺陷。
- 复现证据（2026-10-28 最新覆盖运行，`CoverageTests_btcore` 逐用例执行）:
  - `build-cov/coverage/rc/CoverageTests_btcore/R72HftUftPaths_HftMarketOrderFillsAndDumps.rc`
    → `CRASH(rc=139,sig=11) R72HftUftPaths.HftMarketOrderFillsAndDumps`
  - `build-cov/coverage/rc/CoverageTests_btcore/R72HftUftPaths_UftMarketOrderFillsAndCloses.rc`
    → `CRASH(rc=139,sig=11) R72HftUftPaths.UftMarketOrderFillsAndCloses`
  - 两个用例的 `.log` 都停在 `[ RUN ]`，没有任何断言输出，说明崩溃发生在第一次
    `handle_tick` 内部；同文件里不成交的 `HftPendingLimitCancelAndEmptyCallbacks` /
    `UftPendingLimitCancelAndQueries` 均 PASS，排除夹具/初始化问题。
- 影响范围: 任何「默认配置 + 市价单/首笔即可成交的限价单」的高频/UFT 回测都会在第一次
  `handle_tick` 崩溃；这是最常用的回测姿势。修复方向（不实施）：lambda 先 `find` 订单，
  不存在则直接返回；或在 `on_tick` 中把 `procTask()` 移到 `procOrder` 之前。
- 备注: 该缺陷与 `UftMocker::on_session_begin/on_session_end/stra_enum_position` 的
  `_strategy` 空指针（BUG-R72-001 / BUG-P08-001）无关，是**任务队列与订单生命周期**的
  独立问题。R92 的启用用例只走不触发该崩溃的输入，未放宽任何断言。
