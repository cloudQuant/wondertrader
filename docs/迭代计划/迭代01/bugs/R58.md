## BUG-R58-001 `WtSelEngine` 构造函数不初始化 `_tm_ticker`，析构读取未初始化指针（复核 BUG-R42-001）

- 状态: 已合并（主记录 BUG-R42-001；本条不另计）
- 严重级别: Major（源码确认的未定义行为；重复条目）
- 产品文件: `src/WtCore/WtSelEngine.cpp:33-37`（构造函数初始化列表只有 `_terminated`、`_cfg`）、
  `:45-56`（`release()` 中 `if (_tm_ticker) { stop(); delete; }`）；成员声明
  `src/WtCore/WtSelEngine.h:94`（`WtSelRtTicker* _tm_ticker;` 无默认值）
- 相关测试: `src/TestUnits/coverage/n02_wtcore_engines/r41_ticker_test.cpp`
  的 `R41EngineFixture.R41SelTickerOnTickFeedsSelEngine`（当前测试改为堆分配且不 delete）；原缺陷占位另见
  `src/TestUnits/coverage/p02_wtcore_engines2/r42_sel_ctx_test.cpp::DISABLED_DestroyWithoutInitReadsUninitializedTicker`
- 输入/前置条件: 构造 `WtSelEngine` 后调用 `init`、不调用创建 `_tm_ticker` 的 `run`，再析构；当前 R41 测试为避开该析构而不 delete 引擎
- 期望行为: `_tm_ticker` 初值为 `nullptr`；未启动 ticker 时析构安全返回
- 实际行为: 析构 `release()` 静态读取未初始化的 `_tm_ticker`，构成未定义行为。既有 R41 记录为 **rc=137（sig=9）**，日志在 `[ RUN ]` 后停止并于 60 s 超时；这只证明 case_runner 超时后发出 kill，不能证明根因是指针解引用，也不能据此排除死锁、等待或其他故障。未初始化指针风险来自源码，不来自该 rc 归因。
- 复现: `WtSelEngine* e = new WtSelEngine(); e->init(...); delete e;`（不启动 ticker）
- 影响: 若析构读到非空垃圾指针，会调用野指针方法或 delete 野指针，具有崩溃/内存破坏风险；该 R41 超时进程的覆盖率计数不可用，但根因尚未由动态证据定位。
- 测试侧处置: R41 将引擎改为堆分配且**故意不 delete**，使析构不执行；断言全部保留。这只是隔离手段，不是修复；正解仍是构造函数补 `_tm_ticker(NULL)`（与 HFT 版本一致）。
- 备注: 与 `bugs/R42.md` 的 BUG-R42-001 是同一构造/析构路径及同一缺陷，不保留为独立问题；R42 是 canonical。新增的 timeout 观察不构成新的产品缺陷或根因证明。

## BUG-R58-003 `HisDataReplayer::init` 忽略基础数据装载失败，仍返回 true

- 状态: 待审核（配置错误传播缺口由源码确认；文件必需性及运行后果需契约确认）
- 严重级别: 条件性 Major（仅对明确声明为必需却无法装载的基础文件）
- 产品文件: `src/WtBtCore/HisDataReplayer.cpp:171`（`init` 入口）、`:231-290`（basefiles 装载）、
  `:299`（无条件 `return true`）；失败点在 `src/WTSTools/WTSBaseDataMgr.cpp:243-247`
  （`loadSessions` 文件不存在只打 error 并返回 false）
- 相关测试: 本 lane 的 8 条 R43 用例曾使用错误仓库根；该夹具问题已由 RC-R58-05 修正。它们不是对“显式配置缺失的必需 session 文件”这一条件的动态验证。
- 输入/前置条件: `basefiles.session/commodity` 指向不存在的文件
- 期望行为: 对配置中声明为必需的基础文件，装载失败应让 `init` 返回 false；可选文件应有明确的降级语义，不能仅凭任意 loader 的 false 推断整个回测必须失败。
- 实际行为: `loadSessions` 对不存在文件返回 false 并记录 error；`HisDataReplayer::init` 丢弃该结果并最终返回 true。源码确认错误传播缺口，但 `basefiles.session` 的必需性契约未在此处声明。
- 复现: 配置 `cfg.basefiles.session` 指向不存在路径时，源码上 `init` 仍会继续并返回 true；本次没有运行该用例。旧 R43 测试的失败来自夹具仓库根错误，不能作为该配置错误路径的动态证据。
- 影响与修复方向: 若 session 文件是必需项，调用方可能在数据不完整时继续；修复应先定义必需/可选配置项，再对必需项传播 false 并测试显式缺失文件。不要把原 R43 的 fixture typo 等同于产品缺陷复现。

## 复核结论（测试侧，不是产品缺陷）

### RC-R58-01 R41 夹具标准代码格式（三段式）

- 状态: 测试输入错误（已统一改为三段式）
- 结论: 标准代码必须是 `EXCHG.PRODUCT.MONTH`（如 `SHFE.rb.2310`）。两段式
  `SHFE.rb2310` 会被 `CodeHelper::extractStdCode` 解析成 `product="rb2310"`，
  `getCommodity("SHFE","rb2310")` 查不到品种，进而令换手/手续费/目标仓位断言失败。
  主控已统一为三段式；本轮复核未再发现两段式残留。

### RC-R58-02 `closes.csv` 没有 `CLOSE` 字面量

- 状态: 测试断言目标文件错误（已改为分别检查 closes/trades）
- 结论: `WtEngine::log_close`（`WtEngine.cpp:1230-1236`）写的是
  `code,direct,opentime,openprice,closetime,closeprice,qty,profit,totalprofit`，
  `direct` 只有 `LONG`/`SHORT`；`CLOSE` 只出现在 `trades.csv` 的 `log_trade`
  （`:1221-1228`）。旧用例在 `closes.csv` 找 `CLOSE` 属于测试查错文件，
  已改为查 `"SHFE.rb.2310,LONG,"` 与 `trades.csv` 的 `CLOSE`。

### RC-R58-03 R41 归零调用把 `+3` 写成 `+8`

- 状态: 测试输入与注释错误（已修正）
- 结论: 旧用例在「-3 → 0」一步调用 `handle_pos_change("r41_stra", kCode, 8.0)`，
  目标是 `-3 + 8 = +5`，所以 `datas.json` 最终 volume=5；要归零应为 `+3`。
  这是测试输入错误，不是产品持仓逻辑错误。改为 `+3.0` 后最终 volume=0。
  旧用例上方的注释还写着「2 -> 7」「7 -> -1」「-8 -> 0」，与实际初始 0 仓不符，
  已一并改成「0 -> 5」「5 -> -3」「-3 -> 0」。

### RC-R58-04 `handle_push_quote` 的虚分派

- 状态: 测试调用面错误（已改为显式调用基类实现）
- 结论: `WtCtaEngine` 重写了 `handle_push_quote`，`_tm_ticker == NULL` 时直接返回
  （`WtCtaEngine.cpp:423-427`）。旧用例想验证基类的热合约扇出却调用了虚函数，
  已改为显式 `engine.WtEngine::handle_push_quote(tick)`。属测试调用面错误。

### RC-R58-05 R43 仓库根定位依赖 `__FILE__` 绝对路径

- 状态: 测试夹具根路径错误（已补一级；绝对 `__FILE__` 依赖仍是测试可移植性风险）
- 结论: 旧 helper 少上溯一级，落到 `<repo>/src`，导致 `dist/common/*.json` 全部不存在；
  8 条 R43 红用例由此产生（查询为 NULL、回放为空、`CtaMocker::on_schedule` 空 session 崩溃）。
  已补一级到仓库根。残余风险：helper 依赖构建系统把 `__FILE__` 展开成绝对路径
  （当前 `build.ninja` 确实如此）；若改为相对源路径，需要改成按可执行文件路径定位。

### 复核：BUG-P02-003 `WtEngine::get_adjusting_flag` 丢弃返回值（既有条目，不重复编号）

- 状态: 已合并（主记录 BUG-P02-003；本段只保留交叉复核）
- 结论: `WtEngine.cpp:771-777` 中 `if (_data_mgr) _data_mgr->get_adjusting_flag();`
  丢弃返回值并恒 `return 0`。原来将该现状作为预期的断言不能证明正确性；应以数据管理器
  返回的非零值作为对照，检查引擎是否转发。建议修复为
  `return _data_mgr ? _data_mgr->get_adjusting_flag() : 0;`。
  详见 `bugs/p02_wtcore_engines2.md` 的 BUG-P02-003。
