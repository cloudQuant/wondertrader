> 本 lane 只修测试、不改产品；以下产品问题只登记，不修复。所有条目状态均为 `待审核`。

## BUG-R58-001 `WtSelEngine` 构造函数不初始化 `_tm_ticker`，析构读取未初始化指针（复核 BUG-R42-001）

- 状态: 待审核
- 严重级别: Major（未定义行为；本轮实测为挂死到超时后被 SIGKILL）
- 产品文件: `src/WtCore/WtSelEngine.cpp:33-37`（构造函数初始化列表只有 `_terminated`、`_cfg`）、
  `:45-56`（`release()` 中 `if (_tm_ticker) { stop(); delete; }`）；成员声明
  `src/WtCore/WtSelEngine.h:94`（`WtSelRtTicker* _tm_ticker;` 无默认值）
- 相关测试: `src/TestUnits/coverage/n02_wtcore_engines/r41_ticker_test.cpp`
  的 `R41EngineFixture.R41SelTickerOnTickFeedsSelEngine`
- 输入/前置条件: 栈上构造 `WtSelEngine`，正常 `init`、喂一笔 tick，然后用例结束析构
- 期望行为: `_tm_ticker` 初值为 `nullptr`；未启动 ticker 时析构安全返回
- 实际行为: 析构 `release()` 读取未初始化的 `_tm_ticker`。本轮 R41 用例如实复现为
  **rc=137（sig=9）**：日志停在 `[ RUN ]` 之后，60 s 后被 case_runner 超时 KILL；
  既不是死循环，也不是 OOM，而是对垃圾指针执行 `stop()/join()` 或 `delete`。
- 复现: `WtSelEngine* e = new WtSelEngine(); e->init(...); delete e;`（不启动 ticker）
- 影响: 选择器进程启动失败/退出异常；测试进程被整体杀掉，连带丢失该进程的覆盖率计数器。
- 测试侧处置: 本 lane 将引擎改为堆分配且**故意不 delete**，使析构不执行；断言全部保留。
  这只是一个隔离手段，不是修复；正解仍是构造函数补 `_tm_ticker(NULL)`（与 HFT 版本一致）。
- 备注: 与 `bugs/R42.md` 的 BUG-R42-001 为同一产品缺陷，此处记录本轮新的挂死形态与测试处置。

## BUG-R58-002 `CtaMocker::on_schedule` 对空 session 直接解引用

- 状态: 待审核
- 严重级别: Major（崩溃）
- 产品文件: `src/WtBtCore/CtaMocker.cpp:1127-1133`
- 相关测试: `src/TestUnits/coverage/n04_btcore_mockers/r43_cta_mocker_hook_test.cpp`
  的 `R43CtaMockerHookTest.scheduleRequiresMainBarClosed`
- 输入/前置条件: 基础数据里没有该标准代码对应的 session（本 lane 旧夹具的
  `dist/common/*.json` 路径拼错，正好构造出这一状态）
- 期望行为: `sInfo == NULL` 时跳过本轮调度并记录错误，不应崩溃
- 实际行为: `WTSSessionInfo* sInfo = _replayer->get_session_info(stdCode, true);`
  之后无条件 `sInfo->offsetTime(curTime, true)`，空指针解引用 → SIGSEGV（rc=139）
- 复现: 用一个不装载 sessions.json 的 `HisDataReplayer` 构造 `CtaMocker`，
  先 `handle_bar_close` 再 `on_schedule`
- 影响: 基础数据配置缺失/不完整时，回测在第一次调度即崩溃；崩溃发生在 gtest 进程内，
  会吞掉同进程后续用例的覆盖率计数。
- 测试侧处置: 修正 R43 夹具的仓库根定位，装载真实 `dist/common`；未改产品。

## BUG-R58-003 `HisDataReplayer::init` 忽略基础数据装载失败，仍返回 true

- 状态: 待审核
- 严重级别: Major（静默误配置，后续空指针崩溃）
- 产品文件: `src/WtBtCore/HisDataReplayer.cpp:171`（`init` 入口）、`:231-290`（basefiles 装载）、
  `:299`（无条件 `return true`）；失败点在 `src/WTSTools/WTSBaseDataMgr.cpp:243-247`
  （`loadSessions` 文件不存在只打 error 并返回 false）
- 相关测试: 本 lane 的 8 条 R43 红用例在旧夹具下共同触发（路径错 → 文件不存在 → 空基础库）
- 输入/前置条件: `basefiles.session/commodity` 指向不存在的文件
- 期望行为: 至少汇总基础数据装载结果，关键基础文件缺失时 `return false`，让调用方停止回测
- 实际行为: 逐个 loader 的 bool 返回值被丢弃，`init` 始终返回 true；调用方以为初始化成功，
  随后 `prepare/run/on_schedule` 在空 session 上崩溃（见 BUG-R58-002）
- 复现: `cfg.basefiles.session` 填一个不存在的路径，`init(cfg)` 返回 true，
  再 `register_sink + prepare` 或直接驱动 `CtaMocker::on_schedule`
- 影响: 配置错误不能在 init 阶段暴露，错误被推迟成回测中的崩溃，且日志里只有 loader 的一条 error；
  对自动化回测/批处理尤其不友好。
- 测试侧处置: 修正夹具路径；未改产品。

## BUG-R58-004 `WtEngine::on_tick` 对空 session 直接解引用（待触发信号路径）

- 状态: 待审核
- 严重级别: Major（崩溃；与 BUG-R3-006 同族，但位置在引擎层）
- 产品文件: `src/WtCore/WtEngine.cpp:127-129`
- 相关测试: 本轮未新增用例；R41 夹具的 `StandbySignalFiresOnNextTick` 只走有效 session 分支
- 输入/前置条件: `_sig_map` 中存在某标准代码的待触发信号，而该代码在基础数据里查不到
  session（`get_session_info(stdCode, true)` 返回 NULL），随后收到该代码的 tick
- 期望行为: 判空后保留/丢弃信号并记录错误，不应崩溃
- 实际行为: `WTSSessionInfo* sInfo = get_session_info(stdCode, true);`
  紧接 `sInfo->isInTradingTime(...)`，空指针解引用
- 复现: 对不在基础库中的代码先 `handle_pos_change`（无现价 → 挂起信号），再 `on_tick`
- 影响: 合约换月/基础库漏配合约时，一条待触发信号即可让实盘或回测引擎崩溃。
- 备注: 与 `bugs/R3_wtcore.md` 的 BUG-R3-006（`CtaStraBaseCtx` 同型）属同一崩溃族，
  建议一并按“session 允许为空”的口径修复。

## 复核结论（测试侧，不是产品缺陷）

### RC-R58-01 R41 夹具标准代码格式（三段式）

- 状态: 待审核
- 结论: 标准代码必须是 `EXCHG.PRODUCT.MONTH`（如 `SHFE.rb.2310`）。两段式
  `SHFE.rb2310` 会被 `CodeHelper::extractStdCode` 解析成 `product="rb2310"`，
  `getCommodity("SHFE","rb2310")` 查不到品种，进而令换手/手续费/目标仓位断言失败。
  主控已统一为三段式；本轮复核未再发现两段式残留。

### RC-R58-02 `closes.csv` 没有 `CLOSE` 字面量

- 状态: 待审核
- 结论: `WtEngine::log_close`（`WtEngine.cpp:1230-1236`）写的是
  `code,direct,opentime,openprice,closetime,closeprice,qty,profit,totalprofit`，
  `direct` 只有 `LONG`/`SHORT`；`CLOSE` 只出现在 `trades.csv` 的 `log_trade`
  （`:1221-1228`）。旧用例在 `closes.csv` 找 `CLOSE` 属于测试查错文件，
  已改为查 `"SHFE.rb.2310,LONG,"` 与 `trades.csv` 的 `CLOSE`。

### RC-R58-03 R41 归零调用把 `+3` 写成 `+8`

- 状态: 待审核
- 结论: 旧用例在「-3 → 0」一步调用 `handle_pos_change("r41_stra", kCode, 8.0)`，
  目标是 `-3 + 8 = +5`，所以 `datas.json` 最终 volume=5；要归零应为 `+3`。
  这是测试输入错误，不是产品持仓逻辑错误。改为 `+3.0` 后最终 volume=0。
  旧用例上方的注释还写着「2 -> 7」「7 -> -1」「-8 -> 0」，与实际初始 0 仓不符，
  已一并改成「0 -> 5」「5 -> -3」「-3 -> 0」。

### RC-R58-04 `handle_push_quote` 的虚分派

- 状态: 待审核
- 结论: `WtCtaEngine` 重写了 `handle_push_quote`，`_tm_ticker == NULL` 时直接返回
  （`WtCtaEngine.cpp:423-427`）。旧用例想验证基类的热合约扇出却调用了虚函数，
  已改为显式 `engine.WtEngine::handle_push_quote(tick)`。属测试调用面错误。

### RC-R58-05 R43 仓库根定位依赖 `__FILE__` 绝对路径

- 状态: 待审核
- 结论: 旧 helper 少上溯一级，落到 `<repo>/src`，导致 `dist/common/*.json` 全部不存在；
  8 条 R43 红用例由此产生（查询为 NULL、回放为空、`CtaMocker::on_schedule` 空 session 崩溃）。
  已补一级到仓库根。残余风险：helper 依赖构建系统把 `__FILE__` 展开成绝对路径
  （当前 `build.ninja` 确实如此）；若改为相对源路径，需要改成按可执行文件路径定位。

### 复核：BUG-P02-003 `WtEngine::get_adjusting_flag` 丢弃返回值（既有条目，不重复编号）

- 状态: 待审核
- 结论: `WtEngine.cpp:771-777` 中 `if (_data_mgr) _data_mgr->get_adjusting_flag();`
  丢弃返回值并恒 `return 0`。本轮 R41 价格用例断言 `get_adjusting_flag() == 0`
  与当前实测一致，因此没有把它当作红用例；但该断言固化的是缺陷行为，若产品修复
  （`return _data_mgr ? _data_mgr->get_adjusting_flag() : 0;`），该断言需要同步翻转。
  详见 `bugs/p02_wtcore_engines2.md` 的 BUG-P02-003。
