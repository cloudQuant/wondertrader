# lane R130 疑似缺陷记录（WtCore 残余公开面）

## BUG-R130-001

- 状态: 产品缺陷（模板加载后的引擎计算本机复现）
- 严重级别: Minor（`calc_fee` 与 `load_fees` 模板表不一致；
  仓库内无活动生产调用点且外部消费者影响未知）
- 模块/文件: `src/WtCore/WtEngine.cpp` L843-876（`load_fees`）、L879-916（`calc_fee`）、
  `src/WtCore/WtEngine.h` L247-260（`FeeItem` / `_fee_map`）
- 相关测试: `src/TestUnits/coverage/q01_wtcore3/r130_engine_fee_test.cpp`
  - 原启用用例把引擎返回 0 当通过条件，另一个正确性用例被禁用；现合并为 `R130EngineFee.LoadFeesMakesTemplateAvailableForEngineCalculation`，以商品费率 3 为对照并要求引擎计算一致，不固定内部 `_fee_map` 结构。
  - 重建后该用例单独运行 FAIL：商品费率正控为 3，`calc_fee` 实际为 0；无模板控制未失败。
  - `R41EngineFixture.R41CalcFeeUsesLoadedTemplateAndDefaultsWithoutOne` 已修正旧的零费率断言，重建后单例 FAIL：相同模板下商品计算为 10、引擎计算为 0；无模板控制返回 0。
- 输入/前置条件:
  1. 配置中的 `fees` 是 fee JSON 文件路径，或测试子类直接调用 `load_fees(path)`；文件内容为
     `{"SHFE.ag":{"open":1.5,"close":1.2,"closetoday":1.0,"byvolume":true}}`；
  2. `load_fees` 走完解析（品种存在，`commInfo != NULL`）；
  3. 调用 `calc_fee("SHFE.ag.2512", 3500.0, 2.0, 0)`。
- 期望行为: `load_fees` 应把每条模板写入 `_fee_map`（键为 `交易所.品种`），
  `calc_fee` 命中模板后按 `_by_volume` 分支返回 `1.5*2 = 3.0`。
- 实际行为: 源码中 `load_fees` 只执行 `commInfo->setFeeRates(...)` /
  `setMarginRate(...)`；`src/WtCore` 内没有 `_fee_map` 写入点。由此可推得，在模板表未被
  派生类或外部代码另行填充时，`calc_fee` 走 L883-888 的未命中分支并返回 0.0。
- R130 本地复现（上述 R41 另有本机证据）:
  1. 如当前 R130 测试所做，初始化 engine 后经测试子类调用 `reloadFees(path)`；
  2. 断言 `comm->calcFee(3500,2,0)==3.0`（通过，说明品种费率已写入）；
  3. 断言 `calc_fee(...)==3.0`（本机 FAIL，实际 0.0）。
- 影响范围: 直接调用 `WtEngine::calc_fee` 且只通过 `load_fees` 配置模板的消费者会得到
  0 手续费。`calc_fee` 的声明是 public，但在仓库当前生产代码中未找到活动调用点；因此
  不能据此声称现有 WtCore 实盘/回测链路已发生手续费损失。算术分支测试通过测试子类注入
  `_fee_map`，不验证公开加载路径。
- 备注: `src/WtCore/CtaStraBaseCtx.cpp` L1465/L1512 对 `calc_fee` 的调用已被注释，
  当前 WtCore 实盘链路未使用。复核结论：`load_fees` 与 `calc_fee` 的源码不一致可确认；
  但预期二者应对同一已加载模板给出一致手续费，来自字段/方法用途推断而非显式接口文档，且无活动
  生产调用点，故产品调用契约与实际影响仍需核实。已有本地定向运行结果，不代表线上路径已受影响。
  若确认应支持该路径，可在校验品种有效后将 open/close/closetoday/byvolume 写入
  `_fee_map[fullPid]`，或让引擎计算使用已加载商品费率；保留按外部结果断言的回归。本 lane 按纪律
  不改生产代码。

## BUG-R130-002

- 状态: 待审核
- 严重级别: Minor（配置引用泄漏源码确认；失败后复用限制的契约尚不明确）
- 模块/文件: `src/WtCore/ParserAdapter.cpp` L95-99（`if (_cfg != NULL) return false;` /
  `_cfg = cfg; _cfg->retain();`）、L41-43（析构空实现）、L214-226（`release` 不释放 `_cfg`）、
  `src/WtCore/ParserAdapter.h` L103
- 相关测试: `src/TestUnits/coverage/q01_wtcore3/r130_misc_tail_test.cpp`
  `TEST(R130MiscTail, ParserInitFailsWhenModuleCannotBeLoaded)`
- 输入/前置条件:
  1. 栈上 `ParserAdapter adapter`；
  2. `cfg.module = "R130NoSuchParserModule"`，`instDir` 指向不含该插件的临时目录；
  3. 调 `adapter.init(...)`（返回 false），随后 `adapter.release()`。
- 期望行为: `init` 失败路径应释放本次 retain 的 `_cfg`（或把 `_cfg` 置回 NULL）。若契约
  允许失败后重试，同一实例应恢复可初始化状态；`release()` 后不应残留引用。
- 实际行为: L98-99 先 retain，再在 L117-121 模块装载失败处直接 `return false`；
  `_cfg` 保持非空。析构函数为空、`release()` 只处理 `_parser_api`，源码中没有
  `_cfg->release()`。因此该对象持有的配置引用没有对应释放点。L95-96 还会拒绝同一
  实例的后续 `init`；失败后是否应允许重试需由生命周期契约明确。
- 测试证据: 当前用例只断言不存在插件时 `init` 返回 false，随后释放调用方持有的 `cfg`；
  它不调用 `adapter.release()`、不复用 adapter，也不检查引用计数或泄漏。该用例未证明
  后三种行为。
- 影响范围: `init` 成功或失败后，adapter 持有的 `_cfg` 引用都没有释放路径；若 adapter
  被反复创建/销毁，配置对象可能持续保留。失败后不可在同一实例重试是源码行为，是否构成
  API 违约尚无明确契约证据。
- 备注: `WtCore/WtDtCore/WtUftCore` 各有一份 `ParserAdapter`，本记录针对 `src/WtCore`。
  复核结论：源码确认存在未配对 retain；现有用例只验证失败返回，未做动态泄漏检查。
  修复方向：失败路径回滚本次 retain；成功生命周期在 `release`/析构中恰好释放一次并
  置空。若支持同实例重试，还需在失败清理后恢复可初始化状态，并为模块 API 指针定义
  一次性释放/重新初始化规则。
