## 2. 量级：为什么这张表直接关系到 95%

- 到 95% 还需再覆盖 **44,155 行**（`FIRST-PARTY lines=68,284 / missed=47,569`，本轮实测）。
- 上表直接涉及的未覆盖行数，给两个口径，因为 B-2 已被 R2 实测推翻一半：
  - 修正前（旧算式）：1,513 + 2,672 + 947 + 386 + 1,611 + 1,556 = **8,685 行**；
  - 修正后（B-2 只计 R2 点名的仍被挡住子面 235+275+290 = 800 行）：
    1,513 + 800 + 947 + 386 + 1,611 + 1,556 = **6,813 行**，即缺口的 **≈15.4%**（旧口径 19.7%）。
  另收发族正路径含在 10,367 行的 A 桶内，不重复相加。
- 一个更宽的启发式统计（只作上界参考，不作结论）：在 lane 的 manifest/bug 里找「接缝/留给主控/不可达/进不去/全 private/无条件起线程/阻塞」这类措辞，
  并在其 ±260 字符窗口里出现的文件名计入，命中 **55 个文件、22,265 未覆盖行 ≈ 缺口的 50.4%**。
  这个口径**偏松**：文件只要出现在阻塞措辞附近就会被算进来（例如某条目把「不是阻塞、只是没样例」的文件也提了一句），
  所以它只能读成「lane 在这一带写过『进不去』字样的面积」，不能读成「这些行都不可测」。

## 3. 需要主控二选一的三个具体决定

1. **同步化接缝**：`WtDataWriter::init()` 无条件起线程 → 是否允许加 `asyncproc=false` 的同步路径或测试 friend 钩子（值 ≈1,513 行）。
2. **私有面接缝**：`HisDataReplayer` 的 `bin/cache*FromBin`、`TraderMocker::match_once`/`extract_buffer`/`handle_read` 等
   → 是否允许加最小可见性钩子（值 ≈2,672 + 947 行；这一类是单文件最大缺口）。
3. **环境替身**：真实 shm 映射（ParserShm 92-269）、厂商 API 创建器（`m_funcCreator` 恒 NULL）
   → 是否允许在测试侧引入 shim/桩库链接选项（值覆盖收发族 A 桶 10,367 行的正路径部分）。

三项都不批准的话，按本轮实测水位（30.34%）与逐桶敏感性（见 `覆盖率95目标可行性-20261027.md`），
95% 需要把剩余未覆盖行的 92.8% 全部执行到，而其中至少上面这几千行是**确定进不去**的。

## 4. 维护方式

- 每波 lane 收口后，把其 manifest 里新的「未进入的面」并入本表（第 1 节只收有原文与行号的条目）。
- 第 2 节的启发式数字每次重算并在本文里保留算法说明，不手写。
- 本表不构成排除申请；`覆盖排除清单` 里那些条目要单独走批准流程。
