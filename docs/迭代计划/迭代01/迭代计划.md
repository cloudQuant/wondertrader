# WonderTrader 测试覆盖率提升迭代计划（迭代 01）

> 目标：在可审核、可复现、可回滚的前提下，把第一方产品代码的行覆盖率提升到 **100%**。
> 本文件是迭代 01 的总计划；覆盖率基线见 [覆盖率基线.md](./覆盖率基线.md)，排除范围见 [覆盖排除清单.md](./覆盖排除清单.md)，缺陷记录规则见 [bugs/README.md](./bugs/README.md)。

## 1. 覆盖率口径

- 主指标：`llvm-cov` 的 **行覆盖率（Line Coverage）**。
- 辅助指标：函数覆盖率、分支覆盖率（记录但不作为本迭代的硬门槛）。
- 统计范围：仓库 `src/` 下的第一方产品代码。
- 100% 的准确含义：**已批准范围内的 100%**。第三方代码、平台专属不可达分支、必须依赖外部柜台/行情服务的适配层，需要逐项审批后排除；不能在未审批的情况下自行降低门槛。
- 测试代码本身（`src/TestUnits/**`）不计入产品覆盖率。

> 未获得审批的排除项不得从报告中删除；报告中必须显式列出“已排除”和“未覆盖但未排除”两类。

## 5. 迭代阶段与门槛

### 阶段 0：测试基础设施（本迭代先做）
- 覆盖率插桩构建（已完成 `WT_ENABLE_COVERAGE`）；
- 每个工作流的独立测试目标与公共 gtest 入口；
- `tools/coverage.sh` + `tools/coverage_report.py`；
- 缺陷记录模板与清单模板；
- 建立“生产代码只读”约束。

### 阶段 1：纯逻辑与数据层（WS01–WS07）
- 目标：这些模块的行覆盖率达到 100%（已批准范围）。
- 先做无外部依赖的 Share/Includes/WTSTools/WTSUtils，再做需要数据 fixture 的存储层。

### 阶段 2：引擎、回测、策略与服务（WS08–WS17）
- 目标：使用 fake 适配器/fixture 驱动引擎与回测，覆盖正常路径、边界和错误路径。
- 引擎的线程/网络路径用可控 fake 时钟、fake socket、临时目录。

### 阶段 3：适配器与工具（WS18–WS20）
- 目标：对可在本机模拟的解析器/交易接口建立 fake SDK/fake server；不能模拟的接口逐项申请排除。
- 进程级工具用临时配置和 fixture 启动、断言退出码/输出/落盘文件。

### 阶段 4：100% 收敛
- 按覆盖率报告逐文件清零遗漏行；
- 对每一个未覆盖行记录：不可达原因、外部依赖原因、或待补测试；
- 评审排除清单，生成最终覆盖率报告。

## 6. 子代理协作规范

- **只读生产代码**：禁止编辑 `src/**`（测试目录除外），禁止“顺手修 bug”。
- **写入范围**：只能写 `src/TestUnits/coverage/<工作流>/**`、`docs/迭代计划/迭代01/manifests/<工作流>.md`、`docs/迭代计划/迭代01/bugs/<工作流>.md`。
- **禁止修改共享文件**：`CMakeLists.txt`、`docs/迭代计划/迭代01/迭代计划.md`、基线文件、排除清单、其他工作流目录一律不改；由主代理统一集成。
- **测试要求**：gtest；确定性；不访问外网/真实柜台；临时文件写入系统临时目录或测试专属目录；不依赖执行顺序；覆盖公开 API、边界、错误路径。
- **编译验证**：子代理只允许做语法检查（`clang++ -fsyntax-only`）；完整构建和覆盖率运行由主代理串行执行，避免并发构建冲突。
- **交付物**：
  1. 测试 `.cpp` 文件；
  2. `manifests/<工作流>.md`：模块/文件、已覆盖函数、未覆盖行及原因、测试清单；
  3. `bugs/<工作流>.md`：发现的问题（不修）。
- **禁止读取/修改**：不要读取其他工作流的 bug 文件或测试文件来“对齐答案”；每个工作流独立覆盖自己的模块。

## 7. Bug 管理规范（本迭代不改 bug）

- 发现疑似 bug 时，只在 `bugs/<工作流>.md` 追加记录，状态一律为 `待审核`。
- 禁止修改生产代码、头文件、构建脚本；禁止为了让测试变绿而放宽断言。
- 每条记录必须包含：编号、模块/文件/行、测试用例、输入、期望、实际、复现步骤、严重级别。
- 修复流程：评审通过后单独开修复提交；本迭代的测试提交不得包含源代码修复。
- 如果测试无法通过且确认是产品缺陷，测试可标记为 `DISABLED_` 或在清单中记录为“待审核缺陷”，但不能删除测试。

- `bugs/<工作流>.md` 已记录所有发现的问题；

## 9. 工具链与命令

```bash
# 1) 覆盖率构建
cmake -S src -B build-cov -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug \
  -DWT_ENABLE_COVERAGE=ON \
  -DCMAKE_POLICY_VERSION_MINIMUM=3.5
cmake --build build-cov -j 8

# 2) 运行测试并生成 profraw（每个测试可执行文件单独设置文件名）
LLVM_PROFILE_FILE="$PWD/build-cov/coverage/test.profraw" \
  ./build-cov/build_x64/Debug/bin/TestUnits/TestUnits < /dev/null

# 3) 合并与报告
xcrun llvm-profdata merge -sparse build-cov/coverage/*.profraw \
  -o build-cov/coverage/coverage.profdata
xcrun llvm-cov report <测试可执行文件或对象列表> \
  -instr-profile=build-cov/coverage/coverage.profdata > build-cov/coverage/report.txt
python3 docs/迭代计划/迭代01/tools/coverage_report.py build-cov/coverage/report.txt
```

## 10. 风险与待决事项

1. **100% 的字面含义**：外部柜台/行情适配器、平台专属分支、Demo 工具能否排除，需要评审确认。
2. **适配器 mock 成本**：WS19/WS20 可能需要 fake CTP/XTP/Femas SDK 或 fake server；这是迭代 03 的主要工作量。
3. **并发子代理**：20 个子代理只写各自测试目录；完整构建/覆盖率必须串行，避免共享 build 目录和 ctest 数据文件竞争。
4. **测试数据**：行情/合约/费率/交易日历 fixture 需要统一管理，避免各工作流重复造数据。
5. **缺陷不修**：测试发现的产品缺陷会阻塞对应行的 100% 覆盖；按第 7 节记录并等待审核，不纳入本迭代的修复提交。
